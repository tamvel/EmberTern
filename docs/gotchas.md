## Never lose information / correctness-over-convenience

37. **`RestoreExpandState` must treat folders and connections asymmetrically because their `IsExpanded` defaults differ.** Folders default expanded (true), connections default collapsed (false). A single verbatim `IsExpanded = set.Contains(id)` rule looks symmetric but is wrong for connections: it force-collapses any connection not in the set, which clobbers a freshly-connected node that auto-expanded but isn't persisted yet. The correct split: connections only-set-true (absence already == their collapsed default), folders verbatim (force-false needed to persist a collapse against their expanded default). **Rule**: any "apply a persisted boolean to rebuilt VMs" pass must account for each VM type's *default* value of that boolean — only force the non-default direction.

114. **`RDB$PROCEDURE_SOURCE` is the procedure BODY only (no header).** It's exactly the text after `AS` — DECLARE section + BEGIN…END. So a structured "easy" editor for a procedure needs **no parsing to load**: take params from `RDB$PROCEDURE_PARAMETERS` and the body verbatim from `RDB$PROCEDURE_SOURCE`. Parsing is required ONLY to turn a user-edited *full* `CREATE OR ALTER PROCEDURE` text back into parts (the Source→Easy direction), and that's a bounded header parser (name + two param lists + locate the body-`AS`), never a full PSQL grammar. The reverse (parts→text) is a deterministic generator. Keep the round-trip's risky direction (text→parts) non-destructive: on parse failure, keep the last-good model and warn — don't discard the user's edits.

117. **In PSQL, distinguish `CASE…END` from `BEGIN…END` by statement scope, not by counting `END`.** A naive BEGIN/END counter is corrupted by `CASE…END` (and `END IF`-less Firebird control flow). The robust rule: a statement runs to its top-level `;`; a `CASE…END` expression has no `;`, so it is contained entirely within one statement. Format by recursing on *units* (statement | BEGIN-block | IF/WHILE/FOR), where a block only consumes `END`s seen at unit-start position — a CASE's `END` is mid-statement and never reaches the block loop. This also makes the formatter idempotent (structure comes from BEGIN/END/`;`, never from whitespace) and is the same insight behind the body scanner's subprogram skipping.

**Item-4 architecture analysis (the held migration plan).** *Current:* all DDL → `FirebirdDdlExecutor.ExecuteAsync` → the **metadata working tx** (manual Commit). *Consumers:* TableDetail structure edits (Pola/Ograniczenia/Indeksy — rely on Rollback-to-undo), Opis/View/Procedure descriptions, New Table CREATE, View/Procedure Compile, SQL-Editor DDL (F5 → metadata lane). *Desired:* every DDL auto-commits; transactions only for data. *What breaks:* Rollback-of-structural-edit + atomic multi-statement structural edits (⚠️ ADD FIELD-with-generator emits CREATE GENERATOR + CREATE TRIGGER + ALTER — must stay one autonomous tx, not per-statement) + the metadata Commit/Rollback UI. *Can the metadata tx be removed?* The **working transaction yes** (DDL → autonomous auto-commit on a transient connection — the proven `ExecuteAdminBatchAsync` path; reads use the implicit per-command read tx); the metadata **connection stays** (C2 read isolation from the data working tx). *Migration (phased, no screen breakage):* **A** `FirebirdDdlExecutor.ExecuteAsync` → one autonomous tx per apply (atomic multi-statement); **B** SQL-Editor metadata DDL → same; **C** remove metadata Commit/Rollback buttons + bar, narrow `CommitAll`/`RollbackAll` + `ShowTransactionButtons` to data; **D** shrink the metadata `TransactionService` to connection+lock only. Data lane (Dane edit, Procedure Execute, SQL DML/SELECT) unchanged. Risk: medium; each phase independently shippable.

128. **DDL statement splitting cannot rely on BEGIN/END counting alone — `CASE … END` introduces `END` tokens that are not block terminators.** When splitting a multi-statement Firebird PSQL payload on top-level `;`, a naive `BEGIN +1 / END -1` counter is corrupted by `CASE … END` (the CASE's `END` drops the counter with no matching `BEGIN`), so a later in-body `;` is mistaken for a statement separator and the procedure is truncated before its final `END` → `Unexpected end of command`. The robust splitter: count CASE as an opener (END closes whichever opener is innermost), AND skip opaque runs entirely — string literals, quoted identifiers, line comments, block comments — so their `;`/BEGIN/END/CASE tokens are never inspected. This is the same structural class of bug as formatter gotcha #117; audit any code that counts `END` tokens for the same context-blindness. **Generalized + consolidated into a shared scanner — see gotcha #129.**

129. **PSQL block-region scanning is a recurring defect class — never hand-roll a BEGIN/END counter; route through the shared `SqlScanHelpers` CASE-aware scanner (or avoid END-counting entirely).** Any scanner that delimits a `BEGIN…END` region by counting `END` tokens is wrong unless it ALSO counts `CASE` as an opener and skips opaque runs (strings, quoted idents, line/block comments) — because `CASE … END` produces an `END` with no matching `BEGIN` (gotchas #117/#128 were two instances; the audit found two more). Two correct strategies exist in this codebase: **(a)** the shared CASE-aware counter — `SqlScanHelpers.FindOuterBeginEndContent` (region range) / `SqlScanHelpers.SkipToEndOfBlock` (advance past a block); **(b)** avoid END-counting entirely — collect to the top-level `;` (the `SqlFormatter` PSQL path) or take the region verbatim to its terminator (`ProcedureSignatureParser`/`ViewSignatureParser`/`ProcedureBodySplitter.Split`). **Rule:** new code that needs a `BEGIN…END` boundary MUST use (a) or (b) — do not write a fresh `BEGIN +1 / END -1` loop. If you must (some new shape the helpers don't cover), extend `SqlScanHelpers` so there's still ONE implementation, and pin it with a CASE-in-body test.

161. **A cell-derived "filter by value" string must ROUND-TRIP through the value converter, or an exact `=` misses its own row.** `GridCellFilter` builds the filter operand as text (later parsed back by `GridValueConverter.TryConvert` for the client comparison AND the SQL `FbParameter`). `Convert.ToString(dateTime, culture)` uses the "G" format, which **drops sub-second precision** — so a Firebird `TIMESTAMP` stored as `…:00.1234567` became `…:00`, and the exact comparison (client `DateTime.Compare` / server bound param) never matched → "Filter by value" on a timestamp returned 0 rows. Fix: format `DateTime` cells with an invariant, sub-second-preserving form (`yyyy-MM-dd HH:mm:ss.FFFFFFF`, fraction only when non-zero so whole-second values stay clean). **Rule:** any value you stringify for later re-parse (filter operands, persisted keys) must survive the format→parse round-trip at full precision; verify with a round-trips-exactly test AND a negative test that documents the lossy form.

176. **Firebird trigger DDL grammar: `FOR <table>` comes FIRST, then `[ACTIVE|INACTIVE] {BEFORE|AFTER} <events> [POSITION n]`; a database-level trigger has NO `FOR`/`BEFORE`/`AFTER` — it's `[ACTIVE|INACTIVE] ON <event> [POSITION n]`.** Emitting `[INACTIVE] FOR table …` (INACTIVE before FOR) is `-104 Token unknown … FOR` for any INACTIVE relation trigger. DB-level triggers use `RDB$TRIGGER_TYPE` 8192=ON CONNECT, 8193=ON DISCONNECT, 8194=ON TRANSACTION START, 8195=ON TRANSACTION COMMIT, 8196=ON TRANSACTION ROLLBACK (read the type as `long` — DDL triggers carry values > `short`). A DB-level/DDL trigger has a NULL relation and no BEFORE/AFTER, so the relation-trigger Easy model can't represent it — disable Easy mode (`CanUseEasyMode`), keep it Source-only, and make `BuildFullSource` return the loaded source verbatim so a stray Easy⇄Source toggle can't fabricate `FOR TABLE_NAME BEFORE INSERT`.

178. **A `.sql` script written for Firebird `isql` / IBExpert must be UTF-8 WITHOUT a BOM — and `File.WriteAllText(path, s, Encoding.UTF8)` EMITS a BOM.** `Encoding.UTF8` is `UTF8Encoding(encoderShouldEmitUTF8Identifier: true)`, so it prepends `EF BB BF`; `isql -i` and IBExpert's script executor then choke on the first statement (`<BOM>CREATE …` → parse error), while Notepad/Notepad++/VS Code read it fine either way. Write with `new UTF8Encoding(encoderShouldEmitUTF8Identifier: false)` (the app's `SqlFileWriter.Utf8NoBom`). Polish/Unicode round-trips losslessly regardless — the in-memory string is already correct UTF-16; the BOM is the only variable. Pin it with a byte-level test (`bytes[0..2] != EF BB BF`) so a refactor can't silently reintroduce `Encoding.UTF8`.

190. **For a text-reproducing consumer riding a lexer, reconstruct by copying SOURCE SPANS, not by concatenating token text.** O4 (`TraceSqlInliner`) must be byte-identical outside the substituted `?` (§0 Paramount Law). Rather than trusting `concat(token.Text)` to reproduce the input (which depends on the lexer's trivia model being perfectly lossless), the migration collects the positional-`?` tokens and rebuilds as `source[lastEnd..markStart]` (verbatim gap — includes trivia, literals, comments, other params) + `formatValue` + advance. Every non-substituted character is copied straight from the original string, so byte-identity is guaranteed *by construction* — independent of any lexer subtlety. This is the safe template for the two deferred §0-critical reproducers (O1 the formatter, O5 the DDL splitter): a lexer/parser tells you WHERE the interesting spans are; you copy everything else from the source. Complementary guard: pin the lexer's own losslessness with a round-trip test (`concat(leadingTrivia+text) == source`) over a real corpus.

191. **Overlay the AST on a lossless token stream so the §0 round-trip is decoupled from grammar completeness.** Retain the full lexer token list at the tree root (`SqlScript.Tokens`), give every node only a `(Start, Length)` span (no stored source string), and reconstruct the source by concatenating each token's leading trivia + text. Then `ToSourceString() == input` holds byte-for-byte **regardless of how deeply any statement was parsed** — a `RawStatement`, a shallow statement, and a fully-modelled one all round-trip identically. This is the mechanism that lets the parser be error-tolerant and grown incrementally over years without ever risking data loss: the tree is a *structural overlay*, and "never lose information" is guaranteed by the token stream, not by the parser being complete. Pin it with a round-trip test over a broad corpus (incl. unterminated/garbage inputs — the parser must handle every one without throwing).

192. **Migrate a §0-critical text-reproducer (the DDL splitter) onto the parser ONLY behind a permanent inlined-legacy differential test — and replicate the legacy's exact boundary offsets.** The O5 splitter's output IS the DDL sent to the server, so it must stay byte-for-byte identical to the previous char-based splitter. Two parts: (1) make the parser's statement spans reproduce the legacy scanner's exact end-offset rules — a `;`-terminated statement ends at the `;`'s end (include the `;`); a run to EOF ends at `text.Length` (include trailing trivia, later trimmed); a PSQL body closing at `END` with no `;` ends right after `END` (exclude trailing trivia) — then apply the identical trim/strip-`;`/drop-empty post-processing, so equal offsets ⇒ identical output by construction. (2) Gate the switch on a differential test that keeps an **inlined verbatim copy of the legacy algorithm** as the permanent "before" reference and asserts `new == old` over a large corpus (pinned cases + generated DDL + pathological inputs). If any case can't be reconciled to byte-identity, keep the old impl and report — never ship a risky §0 change. The token stream also simplifies the port: strings/quoted-idents/comments are already opaque tokens/trivia, so the boundary scanner needs no separate string/comment-skipping.

193. **An AST-based formatter at "statement skeleton" depth = AST *statement dispatch* + token-level *interior*, reusing the proven interior logic — NOT a from-scratch tree walk.** With statements as leaves (token lists, no clause/PSQL-body child nodes), the parity-safe, low-regression way to build the formatter is: parse → dispatch each statement by node kind (Raw/Empty verbatim; PSQL-def/ExecuteBlock/AnonymousBlock → PSQL body emitter; DML+other → clause-break emitter), and render the interior by porting the existing, test-pinned layout algorithms onto the single lexer's tokens (comments from leading trivia, whitespace dropped, a blank-before flag for PSQL). This kills the classification heuristics (`IsPsql`/`FindBodyStart`/keyword-hashsets → replaced by AST kind + `FirebirdSyntax`) while keeping the byte-for-byte-tested interior behavior. Reserve deep clause/PSQL-body AST nodes (and the structural improvements they enable, e.g. breaking `SET`, wrapping `VALUES`) for a later etap. Keep the formatter's line-break/keep-space *style* sets in the formatter (layout policy ≠ the `FirebirdSyntax` keyword catalog).

194. **The parser's `RawStatement`-verbatim rule (§0) means the AST formatter cannot reformat an unrecognised fragment — and that's correct.** A selection/snippet that isn't a recognised statement (e.g. `a , b , c`, a bare expression, a partial clause) parses to a `RawStatement` and must be emitted byte-for-byte (never lowercased, re-spaced, or line-broken) — the Paramount Law wins over prettiness. So "format a fragment" only reshapes fragments the parser recognises; unrecognised fragments come back unchanged. When a real formattable shape currently falls to `RawStatement` but SHOULD format (the bare `BEGIN…END` body editor was the one real case), fix it by ADDING a precise statement kind in the parser (here `AnonymousBlockStatement`) — never by making the formatter reformat `RawStatement` (that reintroduces a heuristic and risks §0). Verify the addition changes only classification, not segmentation/spans, so the DDL-splitter diff-gate stays green.


## Firebird transactions, connections & locking

10. **Maximizing a window mid-session would otherwise destroy the Restore-rect on save.** Avalonia 12 doesn't expose `RestoreBounds`. The fix is to snapshot `_lastNormalBounds` from Position/ClientSize changes whenever `WindowState == Normal`, and persist that snapshot regardless of the closing-state. Persist the current `WindowState` separately so the next launch can re-maximize if needed. **Rule**: any session-persisting window-state code must track the Normal-bounds independently of the current bounds.

22. **Borrow-or-begin transaction pattern for any reader on a shared `FbConnection`.** Firebird/managed driver disallows parallel transactions on one connection. Any reader that opens its own `BeginTransactionAsync` will throw on every call once a user transaction goes active. The fix is to optionally accept a `TransactionService`, check `ActiveTransaction`, and reuse it when present — only start your own when there's no active user tx, and only commit/dispose what you own. `FirebirdDdlReader` and now `FirebirdTableDetailReader` both follow this; `FirebirdMetadataReader.ListAsync` / `ListColumnsAsync` still don't — they're called only during sidebar load (no user-tx pressure today), but should adopt the same pattern if that changes.

24. **Per-step error isolation in any multi-step `LoadAsync`.** When `LoadAsync` runs N sequential queries against the same connection, a single outer `try/catch` is wrong: a failure in step 2 silently kills steps 3-N too. Wrap each step in its own try/catch (`SafeLoadAsync` helper in `TableDetailTabViewModel`) that traps the expected exception type, accumulates the first error into a tab-level `ErrorMessage`, and lets the rest proceed. Compound with **surface errors in the view itself** when an out-of-band error channel (e.g. the Messages tab) might be hidden on the current tab kind — otherwise the user sees blank data with no explanation.

25. **Toolbar + bottom panel + Saved Queries panel visibility ALL gate on a small set of computed VM properties.** `IsQueryTabActive` (true when `SelectedWorkspaceTab.Kind == Query`) is the master switch for SQL-execution chrome — Execute / Cancel / Commit / Rollback / Format / New / Toggle panel / Clear, plus the transaction bar, the Saved Queries panel (combined as `ShowQueryPanel = IsQueryPanelVisible && IsQueryTabActive`), and the bottom Results/Messages/Output panel (via the inner-wrapper `IsVisible`). `IsClosableTabActive` (DDL or TableDetail) gates the Close-tab button. All of these notify off `_selectedWorkspaceTab`'s `NotifyPropertyChangedFor` chain — adding a new tab-kind-aware control means adding the property to that chain, not a new event or subscription.

26. **Borrow-or-begin alone is not enough — concurrent owned-tx Begins still collide.** The original gotcha #22 covers user-tx-vs-reader-tx, but two readers racing each other (or a reader racing the F5 executor) still hit "Parallel transactions are not supported" because neither one knows the other has an owned tx in flight (`TransactionService.ActiveTransaction` stays null for reader-owned txs by design — we don't want metadata browsing to bump the user's working-tx state). The fix is a `SemaphoreSlim` on `FirebirdConnectionService` that gates every `BeginTransactionAsync` (whether owned by a reader or by `TransactionService`). Held by the owner across the tx's lifetime; borrowers don't acquire it. **Rule**: any future `BeginTransactionAsync` caller on the shared `FbConnection` MUST go through `_connectionService.TransactionGate` — borrow-or-begin without the gate is a latent race.

27. **Fire-and-forget background work from `SelectTab` is a liability after reconnect.** `LoadWorkspaceFor` kicks off `EnsureLoadedAsync` on the active TableDetail tab via `_ = detail.EnsureLoadedAsync()`. The user sees the tab is selected, doesn't realize a load is running in the background, and clicks something else. Anything that needs the connection (another TableDetail, F5, even a DDL view) hits the race. The TransactionGate (gotcha #26) is the *correct* fix for this — fire-and-forget itself is fine as a UX pattern, but the underlying resource access must be serialization-safe. Don't reach for "await before yielding to UI" — UI thread can't await without freezing. Lock the resource, not the call site.

31. **`FbConnection` is single-threaded — application MUST serialize commands.** The managed `FirebirdSql.Data.FirebirdClient` driver does NOT internally serialize concurrent `ExecuteReaderAsync` calls on the same connection. Two fire-and-forget paths firing simultaneously will either throw "There is already an open DataReader associated with this Connection which must be closed first" or hang waiting on the previous command's implicit-tx commit. The fix is a connection-wide `SemaphoreSlim` (we expose `FirebirdConnectionService.CommandLock`) acquired around every command body. Every reader, the query executor, and `TransactionService.BeginTransactionAsync/CommitAsync/RollbackAsync` must hold it for their whole wire-touching operation. **This is independent of transactions** — even with the "readers attach to user tx or run with implicit per-command tx" pattern from the prior milestone, you still need the lock because the driver doesn't queue concurrent commands. **Rule**: any new code that does `await cmd.ExecuteReaderAsync` / `ExecuteScalarAsync` / `ExecuteNonQueryAsync` / `connection.BeginTransactionAsync` / `tx.CommitAsync` / `tx.RollbackAsync` on the shared connection MUST acquire `_connectionService.CommandLock` first.

53. **Avalonia DataGrid CellTemplate rebuild on `CellEditEnding` lets us paint optimistic local writes without `INotifyPropertyChanged` wrapping the row.** The DataGrid tears down the editing element and re-applies `CellTemplate` synchronously after `CellEditEnding` returns. With a `FuncDataTemplate<object?[]>` reading `row[columnIndex]`, mutating that cell *before the first await* in the async commit handler means the post-edit rebuild paints the new value immediately. For failure rollback (the new value didn't survive the DB UPDATE), revert + force a row swap via `EditableRows[idx] = cloneOfRow` to trigger an ItemsControl replace, then migrate any per-row tracking dictionaries (`_pkSnapshots`, `_newRows`) to the clone. **Rule**: prefer optimistic local mutation + swap-on-failure over wrapping `object?[]` rows in an observable shape — works with the existing data model and keeps the DataGrid path identical to the read-only case.

60. **Refresh-after-transaction hook na `Active→Idle`** wymaga zachowania `_previousTransactionState`. CommunityToolkit emitter `TransactionStateChanged` nie carry'uje "from/to" w EventArgs (`EventArgs.Empty`). Wzorzec: trzymać `_previousTransactionState` w polu, porównać z `_transactionService.State` na entry handler'a, aktualizować na końcu. Bez tego nie odróżnisz Active→Idle (commit/rollback completed) od Idle→Active (begin) od Active→Active (statement-count tick).

82. **A toolbar button gated on a sub-tab-specific flag is invisible on the other sub-tabs — check every sub-tab can reach the actions it needs.** `ShowTransactionButtons` was `IsQueryTabActive || IsDataTabActive || IsFieldsTabActive`, hiding Commit/Rollback on Indeksy / Opis / Ograniczenia — but those sub-tabs all open the working transaction (Add/Drop index, Save description, Add/Drop constraint). Gate on the broad `IsTableDetailTabActive` so the commit path exists from every sub-tab. **Rule**: when an action on sub-tab X opens a transaction, the Commit/Rollback affordance must be visible on sub-tab X.

85. **`IsolationLevel.ReadCommitted` on `FirebirdSql.Data.FirebirdClient` maps to a TPB ending in `isc_tpb_WAIT`.** The ADO.NET `IsolationLevel` enum can't express the wait/nowait or rec_version axes, and the driver's default for ReadCommitted is `wait` — so EmberTern blocked indefinitely on lock conflicts. To match IBExpert (and to fail fast), build an explicit `FbTransactionOptions { TransactionBehavior = Write | ReadCommitted | RecVersion | NoWait }` and pass it to `BeginTransactionAsync(options)`. **Rule**: never start a Firebird transaction from a bare `IsolationLevel` — always go through explicit `FbTransactionOptions` so wait/nowait and rec_version are deliberate. The single transaction-creation site is `TransactionService.BeginTransactionAsync`; any new one must do the same. Confirm the live TPB via `MON$TRANSACTIONS.MON$LOCK_TIMEOUT` (0 = nowait) — `EMBERTERN_TX_DIAG=1` logs it on every begin.

89. **The managed FirebirdClient forbids two transactions on one `FbConnection`, but the engine supports many per attachment — so "two transaction profiles at once" REQUIRES two physical connections.** The profile split could not be done on a single connection without silently tearing down/recreating the user's working tx on every context switch. C2 (a second `FbConnection` to the same DB) is the enabling mechanism; the split is impossible before it. Open the second attachment best-effort and alias it to the first when it can't open, so a server connection limit degrades instead of breaking.

90. **Give each reader/executor its connection + lock + transaction from ONE source (its `TransactionService` lane), never mix sources.** A reader that takes `connection` from `connectionService.RequireOpenConnection()` (data) but `tx` from a metadata service would attach a metadata transaction to a command on the data connection — a cross-lane bug. `TransactionService` exposes `RequireOpenConnection()` + `CommandLock` resolved by its own role (with degraded aliasing), so a reader that uses only its txService for all three can't desync — and degraded-mode fallback happens automatically. `FirebirdTableDetailReader` is the one reader that legitimately spans both lanes (structure → metadata, data preview → data): it holds two TransactionService references and each method picks the matching one.

91. **Degraded-mode forwarding belongs in `TransactionService`, not at every call site.** When the metadata attachment is unavailable, the metadata `TransactionService` (which carries a `fallback` to the data service) forwards its entire public surface to the data service via a single `ShouldDelegate` guard. Readers, executors, the VM's commit/rollback, and the transaction bar all keep calling the metadata service as if it were independent; the forwarding makes it transparently share the data lane's single transaction. The VM only checks `MetadataIsIndependent` for one thing: whether to render the metadata lane as a *separate* UI group (hidden in degraded mode so it doesn't duplicate the data lane).

94. **Avalonia headless allows ONE `HeadlessUnitTestSession` per test process — a second `StartNew` test class collides with the first.** `ConnectionExpandBindingProbe` already owns the process's headless session; adding a second headless probe class (each calling `HeadlessUnitTestSession.StartNew`) made BOTH fail when the full suite ran, though each passed in isolation. **Rule**: if you need a headless integration probe, add it to the existing headless probe class (share the one session), don't spin up a second session-owning class. For new App-side glue, prefer deterministic Core unit tests + an isolated manual probe run over a permanent second headless session.

98. **`LaneLock()` / any lane-resolving accessor must be captured ONCE per acquire/release pair.** If the lock object is recomputed at release time and the lane (`MetadataIsIndependent`) changed in between, you release a different `SemaphoreSlim` than you acquired — permanently leaking the held one. Because these semaphores live on the long-lived `FirebirdConnectionService`, a leak survives reconnect and only a process restart clears it. `var commandLock = LaneLock();` then use that variable for both `WaitAsync` and `Release`.

101. **For admin maintenance (e.g. `SET STATISTICS INDEX`) that must auto-commit, use a transient dedicated connection, not the working-tx lanes.** The managed `FbConnection` allows only one transaction at a time, so you can't open a short auto-committed admin tx on a connection that may hold a working tx. Open a transient `FbConnection` from the active profile, run each statement in its own begin→exec→commit, close it. Fully independent of the C2 Data/Metadata working transactions; nothing left pending for the user to Commit (IBExpert behaviour). This is the ONE sanctioned auto-commit path — it's admin maintenance, not user DML/DDL, so it doesn't violate the "no autocommit" rule for the user's work.

102. **A pure-DML (data-lane) commit must NOT trigger a structure refresh.** Data edits can't change the schema (DDL goes through the metadata lane), so re-fetching fields/constraints/indexes/dependencies after a data Commit is pure waste — and tearing down the Fields model transiently flips `HasPrimaryKey` false ("only INSERT available"). Route post-transaction refresh by lane: metadata-settled → full structure reload; data-settled → data-preview reload only (`ReloadDataPreviewAsync`, which keeps Fields/PK intact and reverts optimistic writes on rollback).

109. **On a database with an `ON TRANSACTION_COMMIT` (or START/ROLLBACK) trigger, every transaction a tool commits re-fires that trigger — so "huge activity after commit" can be the user's own DB infrastructure, not the tool.** Before chasing a refresh loop, separate the tool's attachment from others in the trace (the `EXE:pid` line) and COUNT the tool's distinct transactions + statements. Here: 2 EmberTern transactions, 0 RDB$ reloads, 579 functions all inside the user's `XXX_WS_TRANS_ON_COMMIT` audit trigger. The only tool-side lever is committing fewer transactions — hence "a COMMIT never refreshes" (the UI is already current; only ROLLBACK must re-read). Verify with `EMBERTERN_REFRESH_DIAG=1`: a clean commit now logs `Commit (no post-commit refresh)` and NO `RefreshStructure begin`.

**Verification vs. IBExpert (trace-compared, sprint complete).** The user captured the same field-edit-then-commit in IBExpert. IBExpert's post-edit refresh runs ~8 metadata queries (RDB$RELATION_FIELDS+RDB$FIELDS, RDB$RELATIONS format, RDB$DEPENDENCIES, fields again, PK/FK/UNIQUE constraints) EACH in its OWN short `CONSISTENCY|WAIT|READ_WRITE` transaction → `XXX_WS_TRANS_ON_COMMIT` fires ~8×, **0 ms every time** because the gate `RDB$GET_CONTEXT('USER_TRANSACTION','TABLE_ID_NAGL_ORDERSTATUS'/'…ORDERPAYMENT')` is unset (those context vars are set only by the ERP's NAGL business operations, never by a metadata edit). The trigger is cheap unless that context is present. **EmberTern now runs the equivalent metadata reads INSIDE the working tx at apply-time (every structural edit calls `RefreshStructureAsync` — 12 call sites) and commits ONE transaction → the trigger fires once.** So EmberTern fires the on-commit trigger FEWER times than IBExpert (1 vs ~8) and, like IBExpert, never with the context set during a metadata edit — it cannot hit the expensive path more often than IBExpert. The earlier 579-function storm ran entirely on the post-commit refresh transaction (`TRA_95413`); removing that transaction (commit ⇒ no refresh) removes the storm regardless of which gated object produced the functions. Final checks PASS: (1) no secondary transaction after a user commit (post-commit code is UI-only); (2) one commit ⇒ one trigger fire; (3) no stale metadata — all 12 structural-edit paths refresh at apply-time within the working tx, so the tab reflects the change before the user commits; (4) behaviour comparable-to/leaner-than IBExpert. 118. **Firebird's metadata-update "object in use" check is cross-attachment — an autonomous DDL transaction on a separate connection does NOT isolate it from a working transaction that holds the object.** A selectable-procedure `SELECT * FROM proc(…)` holds the procedure "in use" for its transaction's lifetime; `ALTER PROCEDURE` (even on a fresh `Pooling=false` attachment) fails until that transaction ends. "Isolated metadata compile" only avoids lock contention on the working tx's *data*, not the engine's object-in-use guard. To diagnose which attachment/transaction pins an object, dump `MON$TRANSACTIONS ⋈ MON$ATTACHMENTS` from a transient connection at the moment of failure (gated by `EMBERTERN_TX_DIAG`).

119. **A transaction settle must NEVER blanket-refresh every open TableDetail tab — scope it to the object that was actually touched.** A full `RefreshStructureAsync` is ~7 heavy `RDB$` queries, EACH an implicit auto-committed transaction. On a database with an `ON TRANSACTION_COMMIT` (or START/ROLLBACK) trigger, every one of those commits re-fires the trigger — so refreshing N unrelated tabs after one settle produces an N×7 transaction storm that re-runs the user's audit trigger N×7 times. Since structure DDL is autonomous + self-refreshing (Phase A), the only legitimate post-settle refreshes are: the **active** tab on a metadata rollback (raw F5 DDL), and **tabs with pending data edits** on a data rollback (revert optimistic writes). Route through a pure `SelectRefreshTargets` selector + a re-entrancy guard; never `foreach (WorkspaceTabs) Refresh…`. This is the deeper, permanent form of gotchas #102/#108/#109 — "refresh only what changed, like IBExpert."

121. **A "designer" surface (grids that show pending edits before Apply) buffers in the VM — the grids must project the WORKING MODEL, not the live catalog.** The bug was a *half-buffered* state: inline cell edits queued (`EnqueueRowEdits` → `PendingChanges`) while toolbar ops executed immediately, so the shared ⚡ Compile button looked dead (nothing fed the queue from the toolbar path). The fix is uniformity: EVERY structural op queues a `PendingDdlChange` AND mutates the bound collection with a pending marker (`FieldRowViewModel.PendingKind`; `ConstraintInfo`/`IndexInfo.PendingState`), `Compile` applies the whole queue in ONE autonomous transaction, `Discard` reprojects from catalog truth with no DB hit. Keep the catalog-truth collection (`Fields`) untouched so `RefreshStructureAsync`'s column-set comparison (gotcha #107) still skips the data-preview reload when columns are unchanged. Distinguish this from **code-object** surfaces (view/procedure source), which are *edit → Compile → auto-commit* (no buffering — there's a single text artifact, not a multi-row model).

122. **Firebird holds a procedure (and likely function/package) "in use" at the ATTACHMENT level — DDL must run on the same attachment that used the object, or no attachment may be using it.** EXECUTE (or COMPILE) of a procedure loads it into that attachment's metadata cache; the cache is released only when the attachment disconnects or itself ALTERs the object. A *different* attachment's `ALTER`/`DROP` fails `object … is in use` even after the executing transaction committed (a transient per-call connection for DDL is the worst case — guaranteed cross-attachment). So Compile/structure DDL must run on the SAME connection as Execute (co-location — `ExecuteDdlAsync` on `_activeConnection`), never a transient. This supersedes the incomplete earlier gotcha #118 (cross-attachment in-use). gotcha #89 still applies: that one connection allows one tx at a time, so settle the working tx before the autonomous DDL tx.

123. **For "edit an object used by other sessions", the lever is dropping `isc_tpb_nowait` (i.e. WAIT) — NOT `write` or `consistency`.** Traces showed IBExpert and EmberTern both ALTER on identical `read_committed + rec_version + nowait + write` TPB; the difference that lets an in-use object be altered is WAIT, so the ALTER waits for the holder to release (lock-manager blocking AST) instead of failing immediately. `consistency`/table-stability is the dangerous red herring (locks whole tables — the historical production-blocking cause), so it is removed from the product entirely. EmberTern's Developer Mode therefore applies **WAIT + a bounded lock timeout to the DDL path ONLY**; data operations always stay NOWAIT (never make a client wait). Build the DDL `FbTransactionOptions` explicitly — the managed driver's default `BeginTransactionAsync(ct)` silently picked NOWAIT and ignored any configured profile (reinforces gotcha #85: never start a Firebird tx from a bare default/IsolationLevel — always explicit `FbTransactionOptions`).

132. **Per-tab editor UI state belongs in `WorkspaceTab`, not in a global preference — use the hybrid rule (global seeds new, per-tab restores reopened).** When an editor surface (View/Procedure/Table detail) has view-state the user expects to survive restart (Source/Easy mode, active sub-tab, grid-edit toggle), add nullable fields to `WorkspaceTab`, write them in `SnapshotCurrentTabs`, and re-apply them in `LoadWorkspaceFor` AFTER the factory applied the global default — so a restored tab keeps its own state while a freshly-opened object uses the latest global preference. A single global preference (the original Procedure approach) cannot represent two open objects in different modes and silently rewrites what every reopened tab restores as. Code-behind-owned *layout* flags (window bounds, sidebar, results height/maximized) stay in `WorkspaceState` globals set in `OnWindowClosing` / read in `ApplyLayoutFromPendingRestore`, separate from VM-owned per-tab state.

146. **`RDB$GENERATORS.RDB$INITIAL_VALUE` / `RDB$GENERATOR_INCREMENT` don't exist on Firebird 2.5 — version-gate the SELECT, don't issue it and catch.** Those columns were added in FB3 (empirically confirmed present on FB3 and FB5). Issuing a SELECT that references them on FB 2.5 throws `FbException` ("column not found"), and a failed command mid-transaction can mark an active working tx for rollback (readers attach to the working tx when one is open). So gate on `FirebirdDdlReader.ParseServerMajor(connection.ServerVersion) >= 3`: read the columns on FB3+, default initial=0 / increment=1 below. The current value (`GEN_ID(name, 0)`) is version-independent (best-effort try/catch for system sequences). Same "don't run a doomed catalog query" discipline as the FB-version gates for procedure/function source.

147. **Firebird sequence `START WITH` / `RESTART WITH` changed semantics in FB4 — and a sequence has TWO distinct numbers (definition vs runtime). Set the runtime counter with `SET GENERATOR … TO`, never `RESTART WITH`.** FB3: the stored counter equals the typed `START WITH`/`RESTART WITH` value (first generated value is `+increment`). FB4+ (SQL standard): the stored counter is `typed − increment`, so the first *generated* value equals the typed value, but `GEN_ID(,0)` reads `typed − increment` (a fresh `START WITH 10000` reads 9999; `START WITH 0` reads −1). `SET GENERATOR name TO v` sets the raw counter directly to `v` on ALL versions — the only version-independent "make `GEN_ID(,0)` exactly v". The two numbers: **definition** = `START WITH` / `INCREMENT BY` / `RDB$INITIAL_VALUE` (set at CREATE, read-only after — FB3 can't ALTER them) vs **runtime** = `GEN_ID(name,0)` (changeable via `SET GENERATOR`). To make a new generator's runtime Current Value equal its Initial Value across versions (the classic Firebird model the user expects), the New flow emits `CREATE … START WITH <initial>` (forceStartWith, so `RDB$INITIAL_VALUE` is recorded even for 0) **then** `SET GENERATOR … TO <initial>` — pinning the counter to the SAME initial value is correct and intentional. The earlier −1 bug was different: it appended a RESTART/SET to an UNRELATED value (the default 0, not the initial), which destroyed the initial value — never do that. A negative `GEN_ID(,0)` (pre-first-use sentinel) must still be displayed as 0. Verify any sequence-DDL assumption against BOTH FB3 and FB5 with `isql` (incl. single-transaction execution) — they genuinely differ.

172. **A magnitude visualization must be scaled to the threshold that makes it matter — never show the internal proportion, or a normal value looks alarming and contradicts the verdict.** The transaction-gap bar drew the OIT→OAT→Next *proportion* and coloured the "pinned" segment a permanent orange, so a healthy 59-transaction gap rendered as a ~full orange bar next to a "Healthy / GC Risk 0" verdict — the two disagreed. Fix: render the measured value (OAT lag) as a **fraction of the danger threshold the engine itself uses** (`LargeGapThreshold`), colour by that same threshold (calm grey below half, orange approaching, red at/over), and add a plain-language status. Extract the severity/fraction decision into a pure helper so a test pins that the gauge and the engine's Healthy/Watch/AtRisk verdict use one shared line and cannot drift. This is the "scale before alarm" principle (from Performance Analysis) applied to a gauge — a small/normal value must LOOK small.

173. **A reader must NEVER hardcode `cmd.Transaction = null` — always borrow the lane's working transaction (`TxFor(role)` / `_transactionService?.ActiveTransaction`).** `cmd.Transaction = null` runs in an implicit per-command transaction ONLY when the connection has no pending local transaction; if it does (the DATA connection always does after a SQL-Editor execute auto-begins the working tx, since there's no autocommit), FirebirdClient throws *"Execute requires the Command object to have a Transaction object when the Connection object assigned to the command is in a pending local transaction."* This is the read-side mirror of gotcha #22-revised: attach to the active working tx when the connection has one (null only when it genuinely doesn't). For a MON$/CURRENT_CONNECTION read this is still correct — the metadata lane normally has no working tx so `TxFor` is null → a fresh snapshot; the only read that hits the pending-tx data connection is the self-attachment-id lookup, and an attachment id is transaction-invariant. Any new reader that touches the shared connection with `cmd.Transaction = null` is a latent crash the moment the user has an open transaction.

181. **A multi-select `ListBox`/`TreeView` collapses its selection on RIGHT-click by default — if a context-menu action reads that selection, the right-click that opens the menu destroys it first.** This is the INVERSE of gotcha #16/#99 (there we WANT right-click to select the row under the cursor; here we must NOT let it collapse a multi-selection). The trigger "Selected" bulk op is invoked from the group node's context menu but acts on the leaf multi-selection held in the VM (`_selectedTriggers`, fed by `SelectionChanged`); a right-click anywhere (especially on the *group*, a different row than the selected leaves) re-selects one row and clears the multi-selection before the command runs → the op sees 0 or 1 items. Fix in the Tunnel `PointerPressed` handler: on `IsRightButtonPressed`, set `e.Handled = true` to suppress the ListBox's own selection change **when preserving the selection is what the menu needs** (clicked row already in the selection, or it's the "aggregator" node that acts on the selection) — the ContextMenu still opens because it fires on release/RightTapped, after PointerPressed. Corollary: a context-menu action that operates on "the current multi-selection" should read a VM field snapshotted on `SelectionChanged`, and the right-click must be prevented from mutating that field.

182. **To reflect a small property change (e.g. a trigger's active state) in a virtualized tree, mutate the existing node VM in place — do NOT call a full `RefreshAsync`/reload.** A full metadata refresh reloads every loaded/expanded group (`LoadGroupAsync` → `Children.Clear()+Add`), which makes the FlatTree controller `RebuildRows()` (`Rows.Clear()` + re-add) → the ListBox loses scroll position AND selection (the reported "tree jump" after activate/deactivate). Since the change is only a display attribute on ONE (or a few) known leaves, flip it on the existing node instances (swap the immutable `Object` via `obj with { … }` behind a `private set`, raise PropertyChanged for the derived display props) — no collection mutation → no reproject → scroll + selection + expanded groups are all preserved for free, and it's faster (no catalog re-query). Reserve the full `RefreshAsync` for changes that actually alter the leaf SET (add/drop/rename) or where you can't identify the affected nodes. Corollary: don't try to fix the jump by snapshotting/restoring the ListBox scroll+selection across a reproject — avoid the reproject. For a BATCH of such changes, flip every affected node (e.g. the batch's per-step `SuccessfulObjects`), not just the one whose context menu opened. Two traps that broke the batch path: (a) `Dispatcher.UIThread.InvokeAsync` to "drain" marshaled `Progress<T>` results hangs unit tests (no dispatcher pump) — and is unnecessary since the modal batch dialog already pumps all results before it closes; (b) gating the flip on a `BatchResultsViewModel.CancellationToken` that the batch runner always `RequestCancel()`s as cleanup → the flip never runs → nothing updates. Read the results list directly (complete on return); don't gate on that token.

213. **A Firebird transaction CANNOT use an object it created but has not committed — `CREATE TABLE T …; INSERT INTO T …;` in ONE transaction fails the INSERT with `Table unknown` (-204).** Measured on FB5 (Lab DB), through the production classes. This is the engine, not the driver and not us. Consequence: **Firebird cannot both (a) let a transaction use an object it created and (b) keep that object rollbackable — you must choose.** `isql` and IBExpert choose (a), via `SET AUTODDL ON`, which commits each DDL statement immediately; that single setting is the entire reason mixed migration scripts "just work" there. So a "classic SQL console" for Firebird that runs one honest transaction with no autocommit *cannot* run `CREATE TABLE …; INSERT …;` as one script — the user must Commit between the DDL and the dependent DML, and that is correct, expected behaviour (EmberTern's SQL Editor is deliberately this). Two corollaries: (1) any tool that promises "all-or-nothing mixed DDL+DML migration" in a single transaction is making a promise Firebird will not keep — `FirebirdScriptExecutor` made exactly this claim in its docstring and is **known-broken** for mixed scripts as a result (deferred to its own sprint); (2) uncommitted DDL is also invisible to *other* attachments, so an object created in the SQL Editor appears in the metadata tree only after Commit (the metadata lane reads with implicit per-command transactions) — that visibility rule is a feature of honest transaction semantics, not a refresh bug.

214. **The cross-attachment `object … is in use` that appears to forbid DDL from a second attachment is a TRANSIENT metadata-cache lock — it bites only a NOWAIT transaction. A WAIT transaction clears it in ~10 ms.** Measured on FB5 (Lab DB): attachment A executes `SP_X`, commits, and merely stays OPEN; attachment B's `ALTER PROCEDURE SP_X` then fails NOWAIT with *"lock conflict on no wait transaction / object PROCEDURE SP_X is in use"* — but succeeds in ~10 ms with WAIT and a bounded lock timeout, with no prior NOWAIT attempt to "nudge" it. The holding attachment releases its cached metadata on demand; it is not a permanent pin. **This supersedes the conclusion drawn in gotcha #122**, which read the NOWAIT failure as "DDL must be co-located on the attachment that executed the object" and forced Compile onto the main/data connection — a workaround that then required the *"Commit or roll back the active transaction before running DDL"* guard (because one `FbConnection` allows one transaction, gotcha #89, so the user's open SELECT blocked Compile). The real fix was always the TPB: **DDL ⇒ WAIT with a bounded timeout, wherever it runs.** With that, DDL runs happily on its own dedicated attachment, independent of every user transaction. Separately measured: an *unrelated* open transaction on another attachment never blocked DDL at all, and an uncommitted INSERT firing a trigger did not block that trigger's DDL — so the co-location premise was over-broad in both directions. Rule: never conclude "Firebird forbids X across attachments" from a NOWAIT failure; re-test with WAIT before designing around it.

215. **A statement classifier that decides *where/how* a statement executes is a hidden semantic switch; one that decides *whether to refresh the UI* is harmless. Keep the classifier, but never let it steer execution in an interactive console.** EmberTern's SQL Editor used to auto-route each F5 by `SqlStatementClassifier`: DML to the data attachment, DDL/DCL to the *metadata* attachment — which silently auto-began a **second working transaction** with its own Commit/Rollback that the user never asked for. The result: "Commit" was ambiguous (which transaction?), a mixed script split across two transactions and two attachments (so dependent statements couldn't see each other), and the app had to *log which lane it chose* on every execute because the behaviour was otherwise unknowable. Classifying by the FIRST statement only compounded it (`SELECT …; DROP TABLE …;` was routed as "Data"). **Fix: the console executes everything on one attachment in one transaction; the classifier is demoted to a refresh hint** ("did this transaction change the catalog, so reload the tree on Commit?") — it changes no execution semantics, so it cannot surprise anyone. Intelligent, DDL-aware execution (AUTODDL, commit-after-DDL, WAIT, deployment policies) belongs in a *deliberate* tool (the Script Executor), where the smartness is visible and opt-in per run. General rule: an interactive console must never surprise; a deployment tool is allowed to be smart. Do not delete the classifier when you remove the routing — the routing was the bug, the classifier is reusable infrastructure.

230. **A left-open working transaction is INHERITED by whatever "begins" one next — `TransactionService.BeginTransactionAsync` early-returns when a transaction is already active. So a component that begins the SHARED working transaction with a non-default TPB and leaves it open silently redefines transaction semantics for every component that runs afterwards.** Found while giving the Script Executor a Developer-Mode WAIT policy (gotcha #214's TPB) instead of the working transaction's NOWAIT default. The Script Executor and the SQL Editor share ONE working transaction by design; the executor's Manual mode deliberately leaves it OPEN for the user to review and Commit. So `Manual + WAIT` would mean the user's *next F5 in the editor* joins a WAIT transaction it never asked for — an invisible breach of the console's "never wait, never block" contract, reachable only by a specific ordering of two unrelated features. The fix is to take the non-default TPB **only** in a mode that settles the transaction inside its own run (`AutoCommitOnSuccess`), so the policy cannot outlive the operation that chose it. General rule: **a TPB is a property of a transaction, not of the operation that started it** — before giving a shared transaction a special policy, ask who else can still be holding that transaction afterwards. Corollary: `BeginTransactionAsync`'s early-return is not just an optimisation, it is a *join*, and every caller is really saying "ensure a transaction exists", not "make me one". (Related: #89 one tx per connection; #215 the console must never surprise — which, notably, *endorses* exactly this kind of WAIT policy in a deliberate deployment tool, where it is opt-in per run.)

237. **Firebird's PSQL exception atomicity is per-REQUEST, not per-block: an unhandled exception leaving a procedure undoes THAT procedure's DML, but an exception caught by a `WHEN` handler does NOT undo the block's earlier statements. Two different rules; measured, because guessing either way is plausible.** Probed on FB5.0.3: (a) `BEGIN INSERT…; 1/0; WHEN ANY DO … END` → the INSERT **survived** (`ROWS_SURVIVED=1`) — a `WHEN` block has no implicit "undo the block" savepoint; (b) a procedure that INSERTs then raises an unhandled exception, called from a caller that catches it → the procedure's INSERT was **gone** (`SURVIVED=0`) even though the caller carried on. So the engine's undo unit is the **request** (the routine invocation), not the syntactic block. Two consequences worth carrying: **anything that re-hosts PSQL statements as separate top-level statements loses (b) silently** — the caller's handler then runs against a database state real execution would never produce, which is exactly why the debugger design reconstructs it with a `SAVEPOINT` per simulated frame (rollback-to on unhandled exit) rather than per block or per statement; and **a `WHEN` handler is not a transactional boundary**, so PSQL that "cleans up" in a handler must undo its own partial work — Firebird will not. `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` are verified working through `FirebirdClient` 10.3.4 if you need to impose a boundary the engine doesn't give you. **Rule: before relying on "Firebird will roll that back", identify the *request* boundary — block structure is not it.** *(design: `docs/design/firebird-debugger.md` §4.5 + §15.2; related #213 uncommitted DDL, #85 TPB)*

236. **#31 is a CONCURRENCY limit, not a multiplexing one — one `FbConnection` happily holds an open cursor while you run other commands on it, as long as you never do so in parallel. Measured; do not re-derive the pessimistic reading.** #31 ("`FbConnection` is single-threaded — application MUST serialize commands", quoting the driver's *"There is already an open DataReader associated with this Connection which must be closed first"*) is easy to read as "an open reader blocks the connection", which would make a whole class of designs impossible — e.g. the future debugger's Cursor Bridge, which must hold a `FOR SELECT` cursor open **across** many statements in the same transaction. That reading is wrong. Firebird's protocol is statement-handle based and supports many statements per attachment; `FirebirdClient` 10.3.4 exposes that. Probed directly (throwaway console app, FB5.0.3, one `FbConnection` + one `FbTransaction`): a reader was left open mid-fetch → an `EXECUTE BLOCK` **ran fine on the same cn+tx** → the original reader **resumed and fetched its next row** → and a **second reader opened simultaneously** alongside the first (nested `FOR SELECT`). What #31 actually forbids is two commands touching the wire **at the same time** (fire-and-forget racing), which is why the fix was a `SemaphoreSlim`, not a "close the reader first" rule. **The trap is #31's other half:** its rule says a command holds the `CommandLock` *"for its whole wire-touching operation"*. Applied literally to a long-lived cursor, that would hold the lock for the cursor's **lifetime** and deadlock every statement inside the loop. So an interleaving consumer must take the lock **per wire operation** (each `Read()`, each execute) — a narrower discipline that still satisfies #31's actual invariant (never two commands on the wire at once) while permitting interleaving. **Rule: "serialize" ≠ "one at a time forever" — distinguish *concurrent* access (forbidden) from *interleaved* access (fine). Before concluding the driver forbids a shape, probe it: #31's failure mode is a thread race, and a sequential interleave never triggers it.** *(design: `docs/design/firebird-debugger.md` §7 + §15.3; clarifies #31, related #89)*

184. **To wrap exceptions inside a C# async iterator (`async IAsyncEnumerable<T>` with `yield`), keep every `yield` OUTSIDE any `try` that has a `catch` — put the risky `await` (ExecuteReaderAsync / ReadAsync) in its own `try/catch` with no yield inside, then `yield` the buffered result after the try.** C# forbids `yield` inside a try-with-catch, so you can't wrap the whole read loop; the idiom is: open the reader in a catch-wrapping try (no yield), then `while (true) { try { has = await reader.ReadAsync(ct); } catch (FbException ex) { throw new QueryExecutionException(...); } if (!has) break; ...; yield return row; }`. Validate arguments (empty SQL) in a non-iterator wrapper method that returns the iterator, so the throw is eager. Release the connection `CommandLock` in a `finally` around the whole iterator body (covers cancel + completion + the wrapped throw). `OperationCanceledException` propagates raw (the caller distinguishes cancel from error).

29. **Case-matching at insertion time, not at display/sort time.** Tempting to lowercase the entire completion list on display when the user's prefix is lowercase. Don't — the prefix can change between keystrokes, and CompletionList's prefix-filter would re-run incorrectly if `Content`/display text and `Text` (insertion) drift apart. The pure transformation lives in `EmberTern.Core.Sql.CaseMatcher` so it's unit-testable without AvaloniaEdit.

46. **`RDB$DEPENDENCIES` is not the FK catalog.** It records compile-time PSQL-style dependencies: view source bodies, trigger bodies, procedure bodies, computed-column expressions, default-value expressions, domain CHECK constraints. Foreign keys are stored exclusively in `RDB$REF_CONSTRAINTS` joined to `RDB$RELATION_CONSTRAINTS`. Any "Related Tables" view that pulls from `RDB$DEPENDENCIES` will surface accidental shared-domain / shared-expression links while missing every actual FK relationship. The right shape: source Tables ONLY from `RDB$REF_CONSTRAINTS` joins, source everything else (Views, Procedures, Triggers, Domains, Packages, Functions, Exceptions, Generators) from `RDB$DEPENDENCIES`. 113. **A stored procedure is NOT a relation — the View/Table detail readers do not apply to it.** View Detail reused `FirebirdTableDetailReader.GetDescriptionAsync` / `GetDependenciesAsync` because a view lives in `RDB$RELATIONS` and its dependency rows are `RDB$*_TYPE = 0` (Relation) — identical to a table. 135. **Lazy tree-load means filter and type-ahead have nothing loaded to search — give them a shared session name cache (names, not VMs).** Deferring leaf-VM creation to first-expand is right for connect speed, but it leaves the search features blind: a filter can't show `Views (1)` for an un-expanded category, and type-ahead can't find an object you never expanded. 136. **Contextual type-ahead = match the growing buffer INCLUSIVE-from-anchor with wrap, NOT from the top of the index.** (Supersedes the original "from the top" advice — that was a stepping stone, kept only as the no-anchor fallback.) The incremental growing buffer (`K→KO→KON→KONT→KONTR`, ~1 s idle reset, no repeat-a-letter cycling) is correct and stays. What was wrong was the SEARCH SCOPE: scanning from index 0 every keystroke means the globally-first match wins, so a keystroke flings the user out of the category they're in (Procedures → Tables). Fix = anchor the search on the current position and search forward with wrap: `FindFromAnchor(index, buffer, anchorIndex)` starting AT `anchorIndex` (inclusive) modulo count. Inclusive is mandatory — the first keystroke must check the current selection FIRST and stay if it still matches (IBExpert/VS feel), not advance to the next match (Windows-Explorer feel; explicitly rejected by the user). Two subtleties: (a) map the selected node to an index via a pure `FindAnchorIndex` (structural → reference on `DirectNode`; leaf → `(group, name)` + `Group.Children.Contains` to disambiguate duplicate names; not found → -1 → from-top fallback); (b) a GROWING buffer must anchor on a View-held `_typeAheadAnchor` (the previous match), NOT `tree.SelectedItem`, because selection is applied asynchronously (`Dispatcher.Post`) and a fast refine would otherwise read a stale selection — only a FRESH buffer re-reads `tree.SelectedItem` (to honour a manual click). The search domain is still the FULL flat index (keeps cross-category reach into never-expanded categories via the name cache — #135); only the start point moved from 0 to the anchor.

139. **`RDB$TRIGGER_SOURCE` may or may not begin with the `AS` keyword — it's database/tool-dependent.** Some Firebird databases store the trigger source starting at `AS` (`AS\nDECLARE…BEGIN…END`), others store just the body (`DECLARE…BEGIN…END` or `BEGIN…END`). 140. **DDL statement splitting must treat a PSQL `CREATE/ALTER/RECREATE {PROCEDURE|TRIGGER|FUNCTION|PACKAGE}` as one unit — its DECLARE-section semicolons are at block-depth 0, BEFORE the BEGIN.** A BEGIN/END-depth splitter (gotchas #55/#128) correctly keeps body semicolons together but still cuts at a top-level `DECLARE VARIABLE …;` because that `;` precedes the first BEGIN (depth 0) → the server gets a truncated `CREATE … AS DECLARE VARIABLE x` → "Unexpected end of command". The fix is statement-shape detection: when a statement starts with a PSQL header, scan it whole — skip to `AS` (skipping balanced parens so `CAST(x AS y)` doesn't false-match), then ignore all `;` and terminate at the `END` that closes the outermost `BEGIN` (CASE-aware; peek past a subprogram's `END`); a header `;` before any `AS`/`BEGIN` terminates a no-body declaration (UDR/EXTERNAL). Views (`CREATE VIEW … AS SELECT`) are NOT PSQL — they split on `;`. The managed FbCommand runs a single CREATE-with-internal-`;` fine (no SET TERM); the splitter only needs to avoid over-splitting.

150. **Firebird `ALTER DOMAIN` supports TYPE, the type's CHARACTER SET (char types), SET/DROP NOT NULL, SET/DROP DEFAULT, ADD CHECK/DROP CONSTRAINT, and TO (rename) — only COLLATION is unchangeable.** Re-verified on FB 5.0.3 (correcting the overly-restrictive gotcha #148). 151. **A Firebird package has TWO source artifacts and is NOT a relation — give it a focused two-editor VM, not the source-object base.** `RDB$PACKAGES.RDB$PACKAGE_HEADER_SOURCE` + `RDB$PACKAGE_BODY_SOURCE` each store the text after `AS` (like `RDB$PROCEDURE_SOURCE`, gotcha #114), so reconstruction is `CREATE OR ALTER PACKAGE name AS <header>` / `RECREATE PACKAGE BODY name AS <body>` (FB has no `CREATE OR ALTER PACKAGE BODY` — RECREATE is the idempotent body form), with `StripLeadingAs` as the defensive guard (gotcha #139). Members are catalog rows (`RDB$FUNCTIONS`/`RDB$PROCEDURES` WHERE `RDB$PACKAGE_NAME`) — never parse the source for the list; only *locate* a known member for navigation. The `SourceObjectDetailTabViewModel` base assumes one source + an Easy toggle, which a package can't satisfy — model it on `ViewDetailTabViewModel` (focused, reuse at the reader/helper level) and treat the package as one logical object: a single Compile that does header-then-body and stops if the header fails.

152. **The PSQL formatter must treat a bare leading `FUNCTION`/`PROCEDURE` inside a PACKAGE BODY as a subprogram DEFINITION, not a statement.** A packaged routine (`FUNCTION name(...) [RETURNS …] AS BEGIN … END`) has no terminating `;` and its own nested `BEGIN…END`; collecting it as a statement-to-`;` stops at the first inner `;` and then mistakes the routine's `END` for the package-body's `END`, dropping the remaining `END`s → non-compilable PSQL. Detect it by scanning at paren-depth 0 from the keyword: a top-level `AS` ⇒ definition (emit header-to-BEGIN, recurse the BEGIN…END — same shape as a local `DECLARE PROCEDURE/FUNCTION`); a top-level `;` before any `AS` ⇒ a package-header forward declaration (statement path). Key the discriminator on `AS`, NOT `BEGIN`, because a routine body may have a `DECLARE` section whose `;` precedes `BEGIN` at depth 0. This is the same defect family as the DDL splitter's package handling (gotcha #140) — both must understand that a PACKAGE BODY is a sequence of subprogram definitions, not statements. Verify formatter changes by compiling the actual output on a live FB5 engine (a scratch DB with the referenced objects), not just by eyeballing structure.

153. **A Firebird index is almost entirely read-only — the ONLY mutable properties are Active/Inactive (plain indexes only) and the description (COMMENT ON INDEX); there is no rename and no structural ALTER.** Verified on FB 5.0.3: `ALTER INDEX … ACTIVE/INACTIVE` works on a plain index but is rejected for PRIMARY/UNIQUE/FOREIGN KEY backing indexes ("Cannot deactivate index used by a … constraint"); `ALTER INDEX … TO` (rename) is a syntax error; `COMMENT ON INDEX` and `SET STATISTICS INDEX` work on every index (incl. constraint-backed); changing fields/UNIQUE/sort-direction/expression requires DROP + CREATE. So an index editor is a read-mostly form, NOT a designer: gate the Active toggle + Drop on `IsConstraintBacked` (PK/FK/UNIQUE), allow description + recompute universally, and surface a clear note explaining why constraint-backed indexes are locked. A constraint-backed index is distinguished by a matching `RDB$RELATION_CONSTRAINTS` row (PRIMARY KEY/UNIQUE/FOREIGN KEY) — note the single-index query must keep UNIQUE in that subquery (the table-grid query narrows to PK/FK, surfacing UNIQUE via `IsUnique` instead). Index *creation* belongs in the table designer (it needs the table context), not a standalone editor — don't build a second creation path. Indexes are NOT meaningfully present in `RDB$DEPENDENCIES` (only expression indexes, on their own columns), so a dependency tab isn't warranted.

198. **`Scope.ScopeAt` (and any offset→scope/AST lookup driving completion) must be INCLUSIVE at the end of

3. **Interface-typed compiled bindings in `Style.Setter` don't push back TwoWay in Avalonia 12.0.3.** Tried `Style Selector="TreeViewItem" x:DataType="vm:IExpandableNode"` with `Setter Property="IsExpanded" Value="{Binding IsExpanded, Mode=TwoWay}"` — source→target worked, target→source silently failed. **⚠️ CORRECTED — see gotcha #38.** The "fix" recorded here (one concrete-typed Style per VM type) was WRONG and was the root cause of the later auto-expand-on-connect failure: `x:DataType` does not scope a Style selector at runtime, so all the per-type Styles match every `TreeViewItem` and the last one clobbers the rest via a failed `DataContext` cast. 17. **AvaloniaEdit's `CompletionWindow.StartOffset` / `EndOffset` define the *segment that gets replaced* on selection.** Leaving `EndOffset` at default makes completion *insert* at the caret, leaving the prefix in place — selecting "SELECT" against editor text "SEL|" then produces "SELSELECT". 28. **AvaloniaEdit `ICompletionData.Content` accepts any `Control`, not just strings.** The API name suggests Content should be text. 30. **XSHD `<Keywords>` blocks are precedence-ordered — first declared wins.** When the same word appears in multiple Keywords blocks (e.g. CASE in both Function and DDL lists), the *first* block to match wins. AvaloniaEdit doesn't merge; it short-circuits on first hit. **Rule**: when splitting a single "Keyword" category into per-color categories (DML/DDL/Function/...), put the higher-priority category first in the XSHD file. 32. **Avalonia 12 `IsVisible`-toggled controls don't get a fresh `AttachedToVisualTree` event each time.** When a TextBox lives in a Panel and visibility flips via `IsVisible="{Binding IsRenaming}"`, the control stays in the visual tree the whole time. `Loaded` / `AttachedToVisualTree` fire only once. 33. **Mixed-type TreeView (folders + connections at the same level) requires `TreeView.DataTemplates`, not `TreeView.ItemTemplate`.** Same gotcha as Explorer Redesign gotcha #4 — setting `ItemTemplate` to one of the two templates breaks template lookup for the other type at every nesting level. 35. **Avalonia ListBox hover-visible row actions: `Button.cls { Opacity 0 }` + `ListBoxItem:pointerover Button.cls { Opacity 1 }`.** The hover state cascades from `ListBoxItem` down to descendants, so a Style scoped under `ListBox.Styles` with the two-selector pair makes any tagged button fade in only on the hovered row. No code-behind required, no per-item PointerEntered subscriptions. **Rule**: when adding a row-scoped affordance to an Avalonia ListBox/TreeView, prefer this pattern over `PointerEntered/PointerExited` handlers.

36. **`ReloadConnections` is the rebuild-everything boundary — anything in the tree that's user-driven and not derivable from disk state will be lost across it.** The tree is fully rebuilt: `Metadata.Connections` cleared, `Metadata.RootNodes` cleared, new VM instances allocated for every node. Anything held only in VM state (`IsExpanded`, selection, scroll position) goes back to constructor defaults. For state we want to preserve: either thread it through `_folderState` + persist on change + restore at the end of `ReloadConnections` (the pattern used by `ExpandedNodeIds` and `LastActiveConnectionId`), or hold it on the owner (`MainWindowViewModel`) where it doesn't share the tree's lifetime. **Rule**: when adding any new VM-side state on a tree node, decide explicitly which side of the rebuild boundary it lives on — defaults-restored is fine for transient flags (`IsDragging`, `IsDropTarget`), but persistence is mandatory for anything the user spent effort on.

38. **`x:DataType` on a `<Style>` does NOT scope the selector at runtime — it's a compile-time binding-typing hint only.** A `<Style Selector="TreeViewItem" x:DataType="vm:Foo">` matches *every* `TreeViewItem`, not just those whose `DataContext` is `Foo`. Multiple such styles for different VM types therefore all apply to every container, and the last one in document order wins; its compiled binding fails the `DataContext` cast for the non-matching types and clobbers the property with `UnsetValue`. **Rule**: for a container style (e.g. `TreeViewItem`) that must bind a property shared across several `DataContext` types, use ONE style with a `ReflectionBinding` (resolves by name, no cast), not N compiled-binding styles. This *supersedes the original gotcha #3*, whose "use N concrete-typed styles, one per VM type" advice was the actual cause of the auto-expand failure.

39. **When a UI binding "doesn't work", prove which of the three layers is broken before touching timing.** The three layers: (1) VM property actually changing, (2) the target control's binding receiving the change, (3) the control/container existing at all. A headless Avalonia probe (`HeadlessUnitTestSession.StartNew` + build the real window + `Dispatcher.UIThread.RunJobs()` + inspect the live control) isolates which layer fails in seconds, without a live DB or manual clicking. Reach for it instead of stacking `Dispatcher.Post` / property-toggle workarounds — those only ever paper over layer-1/2 confusion and leave the real defect in place.

40. **Pointer-event drag & drop, not the `DragDrop` API, for `TreeView` in Avalonia 12.** The built-in `DragDrop`/`DataObject` API is unreliable on a virtualized `TreeView`: item containers come and go under `VirtualizingStackPanel`, `DragOver`/`Drop` fire while the cursor is over child rows rather than the intended row, and there's no clean drop-position (before/after/into) signal. The working approach (sidebar tree): tunneled `PointerPressed` to record the drag candidate before `TreeView`'s own selection runs, an 8-px movement threshold before entering drag mode, `TreeView.InputHitTest(point)` + `FindAncestorOfType<TreeViewItem>(includeSelf:true)` to resolve the row VM under the pointer each `PointerMoved`, top/bottom-half of the target's translated `Bounds` for Before/After (folders → Into), and `PointerReleased`/`PointerCaptureLost` to commit or cancel. Visual feedback rides VM flags (`IsDragging`/`IsDropTarget`) bound to a Style class, not adorners. **Rule**: reach for pointer events whenever a drag needs per-row position resolution inside a virtualized items control.

41. **One-way converters: return `BindingOperations.DoNothing` from `ConvertBack`, never `throw new NotSupportedException()`.** WPF's idiom is to throw; Avalonia's pipeline catches it cleanly but Visual Studio's "Break when this exception type is not handled by user code" — on by default for `NotSupportedException` — surfaces it as a debugger prompt. 42. **DataGrid sorting with compiled bindings requires explicit `SortMemberPath` on EVERY column.** With `x:DataType` on the host (compiled bindings), `DataGridTextColumn.Binding` is compiled to a delegate and its path string is opaque to the DataGrid's sort engine. `CanUserSortColumns="True"` enables header-click sorting, but without `SortMemberPath` the column silently no-ops on click — no arrow, no reorder. 76. **A string `Content` on `CheckBox`/`Button` is access-key-processed — `_` becomes a mnemonic and is swallowed.** FluentTheme's `ContentPresenter` runs `RecognizesAccessKey` on string content, so `ID_NAGL` renders as `IDNAGL`. 77. **`TextSearch.TextBinding` for a templated ComboBox must use `{ReflectionBinding}`, not element-syntax `<Binding>`.** With `x:DataType` on the host (compiled bindings), a `<TextSearch.TextBinding><Binding Path="Name"/></TextSearch.TextBinding>` compiles against the WINDOW's DataType (which has no `Name`) → `AVLN2000`. 80. **A star-width (`Width="*"`) DataGrid column SUPPRESSES the horizontal scrollbar.** The star column absorbs remaining width, so the DataGrid lays its columns out to fit the viewport and never reports content wider than the viewport — fixed/MinWidth columns past the edge get cut off with no way to scroll to them. For a wide grid that must scroll horizontally, give EVERY column a fixed/`MinWidth` (no star); the content width then exceeds the viewport and the built-in horizontal scrollbar engages. **Rule**: never use a star column on a DataGrid that needs horizontal scrolling.

95. **`DataGrid.ColumnReordered` + `DataGridColumn.DisplayIndex`/`Width`/`ActualWidth`/`Header` and `MenuItem.ToggleType`/`IsChecked` are all stable in Avalonia 12.0.0 — but `Visual.GetVisualRoot()` resolved awkwardly on `DataGrid` even with `using Avalonia.VisualTree;`; use `Control.IsLoaded` for an "already attached?" check instead.** Set `DisplayIndex` sequentially in increasing target order to reorder columns programmatically. 97. **A thin (≈12px) clickable strip must NOT be a `Button` driven by `Click`.** Two failure modes: (1) `Button.Click` needs press AND release on the same control — a 1-2px pointer drift on a narrow target drops the release outside and cancels the click ("works on the Nth try"); (2) switching that `Button` to a bubbling `PointerPressed` handler fails entirely because `Button` marks `PointerPressed` handled in its own class handler before instance handlers run. 111. **`DataGrid.IsReadOnly` does NOT disable controls living inside a `CellTemplate`.** It governs only the grid's own edit-mode machinery (double-click / F2 → swap to `CellEditingTemplate`), which covers plain text/date columns. 124. **An always-visible interactive control (ComboBox/CheckBox) inside an `IsReadOnly` `DataGridTemplateColumn` bypasses the DataGrid edit cycle — `RowEditEnding`/`CellEditEnding` never fire for it.** Any "detect that the user changed this cell" logic hung off the grid's edit events will silently miss those columns. When that detection feeds a queue, make the enqueue idempotent-per-row (track + replace) so the VM-PropertyChanged path and any surviving `RowEditEnding` path can both fire without duplicating, and guard re-entrancy if the handler writes back to the row.

130. **To prompt asynchronously during window close, make `OnWindowClosing` `async void`, set `e.Cancel = true` BEFORE the first `await`, run the guard, then re-`Close()` behind a `_forceClose` flag.** Avalonia reads `e.Cancel` when the synchronous portion of the handler returns — an `async void` handler runs synchronously up to the first await, so setting `e.Cancel = true` there keeps the window open while the awaited guard/dialog runs. If the guard allows the close, set a `_forceClose` field and call `Close()` again; the re-entrant handler skips the guard and runs the persist path. 134. **Lazy COUNT-only load is what makes the existing filter safe — the filter code was never the real problem, the eager-load was.** The metadata filter already (a) cost ∝ loaded leaves (unloaded groups hold one placeholder child) and (b) only auto-expanded LOADED groups. Lesson: before rewriting a hot path, check whether an upstream eager-materialization is what makes it hot — fixing the materialization can fix the symptom without touching the path. (Avalonia `TreeView` + nested `VirtualizingStackPanel` still estimates scroll extent poorly for huge expanded branches — that's the one piece lazy-load only mitigates, not cures; `TreeDataGrid` is the cure if ever needed.) **Superseded in part by the Etap 1 follow-up below** — gotcha #134's "lazy-load makes the filter fine as-is" was incomplete: with lazy-load the filter has *nothing loaded to search*, so it needed a session name cache to show per-category match counts. 138. **The Avalonia `TreeView` container does not accept keyboard focus — focus a `TreeViewItem` instead.** `tree.Focus()` is a no-op in practice (and headless-provably so: the focused element stays unchanged); the TreeView delegates keyboard focus to its item containers. To "return focus to the tree", focus a real `TreeViewItem` — the selected row's container (`FindTreeViewItemFor(tree, tree.SelectedItem)`) if there is a selection, else the first realized `TreeViewItem` descendant. Corollary for routed-event handlers attached to the TreeView: input only routes through the TreeView (so a tunnel handler on it fires) when a descendant **item** is focused — which is the normal case after a click, and the basis of the type-to-filter redirect.

154. **Filtering a virtualized `TreeView`/`ListBox` by toggling item `IsVisible=false` does NOT fix scroll performance — the hidden items stay in the `ItemsSource`, so the `VirtualizingStackPanel` still allocates/measures a layout slot for each one and computes the scroll extent across all of them.** On a 1500-row category filtered to a handful, ~1495 zero-height containers make scrolling jerky, the thumb wrong, and selection/hit-testing laggy. The fix is to filter the **collection** the panel binds to (keep an unfiltered master list; rebuild the displayed `Children` to matches only), so the VSP only ever sees rows that are actually shown. Corollary: any consumer that needs the FULL set (autocomplete, name resolution, bulk-"all") must read the master list, not the now-filtered displayed collection.

157. **Avalonia's `VirtualizingStackPanel` estimates scroll `Extent` from the AVERAGE height of *realized* rows (`≈ averageRealizedHeight × itemCount`) — so NON-uniform row heights make the extent (and the scrollbar thumb) swing wildly as you scroll, even with virtualization working correctly.** In the sidebar TreeView (nested VSP: outer + per-item) with an 8000-row expanded category, telemetry showed `extentH` lurching 521589 → 80690 → … → 25165 (`dExtent≈-6169` per realization) as the realized window changed from mixed node types (connections/folders/category-headers ~tall) to pure leaves (~short) — the thumb was ~0.1% of the track, re-sized every frame, and collapsed below the offset near the end → blank list. This is NOT a rebuild bug and NOT broken realization (the extent reflects the full count); it's the estimator reacting to a variable average. **Fix without abandoning the control: pin every row to ONE height** so the average is constant → `Extent = rowHeight × count` is exact and stable. 212. **A "never stall" loop guard (`if (i == before) i++;`) that advances an index without ever emitting
the skipped token is a silent §0 (Paramount Law) violation, not a harmless safety net.** Found while
scoping P8; **fixed in P8 Krok 0 (Formatter Safety), 2026-07-13.** `SqlFormatter.EmitPsqlUnit` returns
without consuming `i` when it sees a stray `END` (`if (IsWordTok(sig[i], "END")) return;`) — correct ONLY
when the caller is an open-`BEGIN` loop that will itself consume that `END` as the block close.

token instead of emitting it verbatim. Net effect: malformed/incomplete PSQL with an extra/unmatched `END`
(a very ordinary mid-edit state) had that `END` silently vanish from the formatted output — real user-typed
text disappearing, the exact class of bug §0 exists to prevent. **Rule: an anti-stall guard that skips a
token must ALSO emit it (verbatim, unformatted) — "don't loop forever" and "don't drop the token" are two
separate obligations, and a fix for one must not silently reintroduce the other.** The fix has two layers:
(a) each stall guard now calls `EmitStrayToken` (emit the unplaced token verbatim on its own line, then
advance) so the emitter is lossless by construction — the same "don't understand it → reproduce it 1:1"
contract `RawStatement` gives at the statement level, applied at the token level; (b) a **checked
invariant** wraps the whole formatter: after formatting each statement its output is compared
lexeme-for-lexeme to its input tokens and, on any mismatch, the statement is kept verbatim, and a
script-level backstop returns the input unchanged if the final result still differs by even one lexeme
(covers the string-level long-line wrapping stage). §0 is now a guarantee, not a hope — the formatter
either reproduces every lexeme or leaves the fragment/document unchanged, even for input it cannot model.
Pinned by `SqlFormatterSafetyTests` (adversarial malformed corpus: lexeme-preservation + no-throw +
idempotency). **Rule: a formatter (or any code-rewriter) that re-emits from a model instead of copying the
source must VERIFY its output preserves the input, and fall back to verbatim when it doesn't — don't trust
every emit path to be individually perfect.**

216. **Trigger context variables (NEW/OLD/INSERTING/UPDATING/DELETING) are highlighted via the SEMANTIC model, not the lexical keyword catalog — because none of them are reserved words in Firebird.** A tempting "just add them to `FirebirdSyntax`" (lexical) fix would colour a legitimately-named column/table `INSERTING` or `NEW` everywhere, and would colour them even in a procedure body where they mean nothing. 217. **Uppercasing an identifier that EmberTern GENERATES is only §0-safe for a *regular* (unquoted-able ASCII) identifier — a case-sensitive/quoted one must be preserved verbatim.** Easy-mode wants generated DDL in the house UPPERCASE style (gotcha #141 already coerces typed names upper). `DdlGenerator.PresentIdentifier` folds a regular identifier to UPPER + bare — safe because Firebird folds an unquoted regular identifier to upper anyway, so only the presentation changes, never the resolved object — but leaves a leading-digit / space / non-ASCII (i.e. genuinely case-sensitive, must-quote) name verbatim and QuoteLight-quoted, because uppercasing `"myName"`→`"MYNAME"` would reference a DIFFERENT object. Keep this presentation rule (generation-only) strictly separate from `SqlFormatter` (which formats existing SOURCE and preserves its own casing — a future per-token casing option lives there, not here); the two are different responsibilities and must not reach into each other. Residual boundary (documented, accepted): an externally-created quoted-lower-case *regular* domain is presented upper — consistent with the app-wide uppercase convention, and the pre-existing code already emitted it wrongly (bare lower-case → Firebird folds → not found).


219. **"Wired in the one shared seam ⇒ every SQL surface has it" is FALSE — the main SQL Editor does not go through `SqlEditorBehavior.Attach`.** That installer is shared by the **object** editors (Procedure/Function/Trigger/View/Package detail + Script Executor); `MainWindow` hand-wires the main SQL Editor itself (its own `SqlCompletionController` + `SemanticHighlighter` / `NavigationController` / `OccurrenceHighlighter` / `EditorSearch`), because its callbacks must be null-safe against a `_currentVm` that attaches later, not a stable `vm`. Stage 7 / S3 attached `SquiggleRenderer` in `SqlEditorBehavior.Attach` only — with a comment (and commit message) asserting "every SQL surface" — so **the most-used editor in the app rendered no squiggles at all** and nobody noticed, because the manual QA pass happened in an Easy-mode procedure editor. The diagnostics were computed there the whole time (`EditorLanguageService` runs on the controller, which that editor does have); only the paint was missing — which is exactly why it was invisible in tests and in code review. **Rule: adding an editor capability means attaching it in BOTH places, and the check is `grep` for the call sites, not the comment above them.** The duplicated wiring is the root cause and deserves its own consolidation milestone; until then, treat `SqlEditorBehavior.Attach` as "the object editors' installer", never as "the seam". Same failure mode as #205/#207: the feature was correct and complete; only its *installation* was missing on one surface. **✅ RESOLVED (2026-07-17, debugger milestone D3):** the two copies are consolidated. `MainWindow` no longer hand-wires the intrinsic editor block in its ctor; it calls the SAME `SqlEditorBehavior.Attach(_editor, _currentVm)` the object editors use, once its VM arrives (first non-null `OnDataContextChanged` — the window's `DataContext` is set after construction, so the shared path, which needs a stable non-null VM, waits for it: "subscribe once the VM arrives"). The old bespoke metadata handlers (`OnMainEditorMetadataChanged` / `OnMainEditorMetadataReady` / `WarmReferencedMetadataAsync`) and the private `CreateMetadataSnapshot` / `EnsureColumnsAsync` / `EnsureRoutineParametersAsync` forwarders are deleted — the controller's own metadata hooks (bound to `vm.Metadata` inside `Attach`) took over their whole responsibility. **The intrinsic block only** was consolidated (completion / highlighting / navigation / squiggles / related-elements / language-completion / typing-ergonomics / search); the genuinely per-host wiring — `DiagnosticsPanelHost.Track` (F8 + diagnostics panel, with per-host reveal), `AmbientModelRefresh` (routine editors), `SqlSnippetDropTarget` (context varies) — stays a caller responsibility, since it truly differs per host and was never the duplication risk. The old "add it in BOTH places" rule is therefore retired: there is now **one** `Attach` seam for the intrinsic block. See `docs/history/19-firebird-debugger.md` (D3).

220. **A rule guarded by `IsEffectivelyVisible` silently inverts its meaning when its consumer lives in a SIBLING TAB.** The object editors' `ActiveEditor` is `_focusedEditor is not null && _focusedEditor.IsEffectivelyVisible ? _focusedEditor : <mode primary>` — correct for Alt+F Format (never format an editor you can't see). Reusing it to drive the **Diagnostics panel hosted as a peer tab** would have been a silent bug: selecting the Diagnostics tab *hides the editor tab*, so the guard can never hold while the panel is on screen, and the rule collapses to the mode-primary branch **always** — the Cursors/Subprograms editors could never appear in the panel, and "focus an editor → the panel retargets" would be unobservable by construction. It would have looked like it worked (the body/source case, i.e. the common one, is indistinguishable). **Rule: before reusing a visibility-guarded rule, check whether the NEW consumer can be on screen at the same time as the thing being guarded.** The fix was a deliberate, documented sibling rule (`LastFocusedSqlDocument` — sticky last-focused SQL editor, no visibility guard, cleared on mode flip / object rebind), NOT a tweak to `ActiveEditor`, because the two encode genuinely different intents. Bonus: dropping the guard also removed a dependency on how Avalonia's TabControl realizes hidden tab content. See `docs/design/editor-stage7-diagnostics.md` §8.2.1.

221. **`DispatcherPriority.Background` is BELOW `Input` — so any state a repeated keypress reads as its anchor must be written SYNCHRONOUSLY, never inside the posted continuation.** The established "jump to an offset in another tab" idiom (`PackageDetailTabView.OnNavigateToMember`) posts the whole caret+scroll+focus block at `DispatcherPriority.Background`, and for its trigger (a one-shot double-click on a tree node) that is exactly right: the tab switch must lay out before the target editor can scroll. Copying it wholesale into Stage 7 / S5's `F8 = next diagnostic` would have introduced a **hold-F8-does-nothing** bug: F8 picks its target by comparing the diagnostics to `editor.CaretOffset`, and Avalonia's priority order (`… > Render > Loaded > Input > Background > ContextIdle > …`) means a *queued second F8* is dispatched **before** the first jump's Background continuation runs — so the second keypress reads the pre-jump caret and re-selects the SAME diagnostic. The split that works: set the caret + selection **synchronously** (it needs no layout — it is a document operation, valid even on an unrealized editor), and post **only** `BringCaretToView()` + `Focus()`, which genuinely do need a laid-out `TextView`. **Rule: when you defer UI work, ask what the NEXT event will read. Anything that is an input handler's anchor is state, not presentation, and belongs on the synchronous path — deferring it makes rapid repeats silently idempotent.** The tell is a feature that works when clicked slowly and stalls when a key is held.

222. **A diagnostic and its explanation live on an UNRESOLVED symbol — so any "explain this squiggle" surface gated on symbol resolution shows nothing exactly where it is needed most.** `QuickInfoEngine.GetQuickInfo` is *symbol*-shaped: `ReferenceAt(offset)` → `Symbol` → card, returning **null** unless the identifier **resolved**. The Ctrl+hover tooltip inherited that gate (it keyed off `NavigationEngine.TargetAt` returning a *navigable target*), which is fine for "check this column's type" — and useless for diagnostics, because **`ET0001`/`ET0002`/`ET0003`/`ET0005`/`ET0007` all fire on references that by definition did NOT resolve**. Hovering an unknown table therefore produced *nothing*: no target, no symbol, no tooltip, precisely at the error. The fix is to change the **gate**, not the renderer: *"is there a resolved symbol **or** a diagnostic at this offset?"* — and to treat "both sections present" as the *rare* path, not the design centre (`ET0006` is the main way to reach it, since it spans a VALUES list that can contain resolved symbols). **General rule: before reusing a symbol-driven lookup for an error-driven feature, check whether the errors are ON symbols at all.** Corollary for the interaction design: Ctrl+hover *means* "this leads somewhere" — an unknown object leads nowhere, so putting the explanation behind Ctrl would attach a navigation affordance to the one thing that cannot be navigated. Information belongs on plain hover; Ctrl stays actionability (frozen §9.4, confirmed not amended). See `docs/design/editor-stage7-diagnostics.md` §15.1.1 / §15.3.

223. **A caret-driven `IBackgroundRenderer` must repaint with `TextView.Redraw()`, not `InvalidateVisual()` — and a "skip if spans unchanged" guard must skip ONLY empty→empty.** Stage 8 / M1's `RelatedElementsRenderer` (bracket / BEGIN-END matching) recomputed on caret move and repainted via `TextView.InvalidateVisual()`. Symptom (manual QA): bracket matching did **not** activate on the FIRST call the caret landed on right after connect; clicking a *different* call worked, and returning to the first then worked too. Root cause: right after connect the window is still settling, and a plain `InvalidateVisual()` can run its render pass before the `TextView` has (re)built its visual lines, so `Draw` hits `VisualLines.Count == 0` and paints nothing; once layout settles a later repaint paints, and thereafter all do. The matcher was never at fault — it is a pure function of (text, caret, model) and returns the same pair every time (proven by a headless caret-driven test), so a first-vs-later difference can only be in the paint. **Two fixes, both needed:** (a) repaint with `_editor.TextArea.TextView.Redraw()` — it invalidates measure, forcing a visual-line rebuild + render, so a background renderer always draws against valid lines (this is exactly why `SemanticHighlighter` uses `Redraw()` for its non-content repaints, while `SquiggleRenderer`'s `InvalidateVisual()` is fine because it is triggered by `ModelUpdated`, which rides an already-settled content redraw); (b) a change-detection guard that skips repaint on unchanged spans must skip **only** the empty→empty case (plain-text caret movement) — skipping an unchanged *non-empty* set turns a single missed paint into a permanent one, because the caret sitting still on the same pair recomputes the identical spans and the guard suppresses the retry until the caret visits another pair and comes back (the exact "works after I click elsewhere and return" tell). **Rule: for a caret/selection-driven overlay renderer, repaint with `Redraw()`, and never let a diffing guard skip a non-empty state.**

224. **To make Tab do something other than indent in an AvaloniaEdit editor, intercept it in a TUNNEL `KeyDownEvent` handler and set `Handled` — a bubbling `+=` handler is too late.** Language Completion (Stage 8 / Language Expansion) expands an armed construct on Tab (`if`→`if () then`). AvaloniaEdit's built-in Tab-indent runs from the `TextArea`'s own key handling (a class handler / key binding), which in the bubbling phase executes **before** any instance handler added with `editor.TextArea.KeyDown += …` — so a bubbling handler sees the tab already inserted. The completion controller gets away with bubbling `+=` for Ctrl+Space/Escape because those are not built-in editing keys; Tab is. Fix: `editor.AddHandler(InputElement.KeyDownEvent, OnPreviewKeyDown, RoutingStrategies.Tunnel)` — Avalonia's `KeyDownEvent` is registered `Tunnel | Bubble`, so the tunnel (preview) handler runs top-down before `TextArea` processes the key; setting `e.Handled = true` there preempts the indent. **Only consume Tab when a construct is actually armed** (re-derive it from text+caret in the handler) — otherwise return without handling so normal indent still works — **and bail when the completion list is open** so the list keeps Tab for accept. Same tunnel pattern already used by `SearchableComboBox` / `GlobalSearchTabView` / the window key handler. Rule: overriding a built-in editor key (Tab, Enter, Backspace) needs a tunnel handler; a bubbling subscription silently loses the race.

225. **AvaloniaEdit's `TextEditor` is NOT focusable — `editor.Focus()` is a no-op returning `false`, and keyboard focus lives on the `TextArea`.** Measured, not inferred: in a headless probe `editor.Focusable` is **`False`**, `editor.Focus()` returns `False`, and the focused element stays `null`; `editor.TextArea.Focus()` returns `True` and the focus manager then reports `AvaloniaEdit.Editing.TextArea`. Consequences: (a) a focus guard on an editor feature must read `editor.TextArea.IsKeyboardFocusWithin` (or `TextArea.IsFocused`) — `editor.IsFocused` is **always false**, so a guard written against it disables the feature permanently while compiling and testing green; (b) any test that needs to type into an editor must call `editor.TextArea.Focus()`, never `editor.Focus()`, or every subsequent key/text input goes nowhere. `editor.IsKeyboardFocusWithin` *is* true when the TextArea has focus (it is an ancestor), so it works too, but the TextArea is the precise seam. This is exactly the #199 class of bug — the member exists and compiles, but its runtime contract is not what the name suggests. Found by Language Completion's hint focus-guard: the headless probe failed on the FIRST assertion, which is the only reason the guard did not ship dead.

226. **One `HeadlessUnitTestSession` per test PROCESS is a hard requirement, not tidiness — AvaloniaEdit builds its caret/editing `KeyBinding`s as STATIC lists, owned by the thread of whichever session first constructs a `TextEditor`.** Each `HeadlessUnitTestSession.StartNew(...)` starts its own UI thread; `ConnectionExpandBindingProbe` was calling it **24 times** (once per test) and mostly got away with it, because most tests only touch per-instance objects. The moment a test sends a real `KeyDown` into a `TextEditor` from a *later* session, `TextAreaInputHandler.TextAreaOnKeyDown` → `KeyBinding.TryHandle` → `KeyBinding.get_Gesture()` → `AvaloniaObject.GetValue` throws **`InvalidOperationException: The calling thread cannot access this object because a different thread owns it`**. It is not an input-injection artefact: raising the event directly on the `TextArea` on the current thread fails identically, because the *KeyBinding objects themselves* belong to another thread — so no injection style avoids it. Fix: one `private static readonly HeadlessUnitTestSession SharedSession = HeadlessUnitTestSession.StartNew(typeof(HeadlessAppEntry));` reused by every test in the class (which is what #94 always meant). Bonus: the partition got ~3× faster (16s → 5s) with 24 fewer UI threads. **Rule: never call `StartNew` per test; share one session for the whole process.**

227. **A completion window's "don't show an empty list" guard must test the FILTERED view (`CompletionList.CurrentList`), not the candidate set (`CompletionList.CompletionData`) — the filter runs AFTER the guard.** `SqlCompletionController.FinishWindow` checked `CompletionData.Count == 0`, then called `window.Show()`, then `ApplyInitialFilter` → `CompletionList.SelectItem(prefix)`, which narrows the list to the already-typed prefix (itself a necessary step — see the comment there: AvaloniaEdit only filters on a subsequent `CaretPositionChanged`, so a window opened with text before the caret would otherwise show everything). So the emptiness check ran on the full candidate set and the narrowing that empties it happened afterwards: a prefix matching **nothing** produced a visible, empty, bordered rectangle over the code that still owned Tab/Enter. Latent for a long time and only exposed when `BEGIN` left the keyword vocabulary (it had always matched `begi` before). Two fixes: after the initial filter, close if `CurrentList.Count == 0` — but **only when a filter actually ran**, since with no prefix `CurrentList` is not the list's state yet and checking it would close every legitimate full list (Ctrl+Space); and on typing into an open window, re-check (the caret moves before `TextEntered`, so AvaloniaEdit's filter has already run by then). Read `CurrentList` rather than re-deriving the match rule — `GetMatchQuality` is private, and any re-implementation would silently disagree with what the list actually draws. **Rule: when a control filters after you populate it, "is it empty?" must be asked of the control's own post-filter view.** **⚠ SUPERSEDED (2026-07-17, #232):** both mechanisms this entry describes — `ApplyInitialFilter` and `CloseIfNarrowedToNothing` — are **deleted**. The controller now pre-filters through `CompletionMatcher` and switches AvaloniaEdit's filter OFF, so nothing filters after we populate: there is no unfiltered moment to patch up, and "the filter emptied it" cannot happen because an empty match result means the window never opens. The *rule* still stands wherever a control does own its own filtering; it just no longer applies here. Note the shape of the lesson, though — this was a workaround for a foreign filter we had not yet taken ownership of, and taking ownership deleted it rather than adding to it.

228. **Splitting responsibilities by VOCABULARY does not split them by KEYSTROKE — the other tool can still own the same keys through data you did not filter.** Language Completion owns SQL constructs, so `CompletionEngine` stopped offering their trigger words (`select`, `where`, …) as keywords. That looked like separation and wasn't: typing `select` still popped the identifier list, because a **procedure named `SELECT_PRACOWNIKOW`** matched the prefix — a *name*, which no keyword filter would ever remove. And since an open completion list owns Tab, Tab inserted the procedure instead of expanding the construct, with the construct's hint never even shown (it suppresses itself while the list is open). The frozen design had said this all along — "*where a construct may begin, the identifier list doesn't auto-pop*" — and only the vocabulary half had been implemented. The real gate is **grammatical position**: the auto-pop path asks the same pure `LanguageConstructResolver.Resolve(text, caret)` the hint asks and returns if anything is armed (explicit Ctrl+Space still opens the list — the developer may always overrule the grammar). Two corollaries: (a) both tools must consult **one** resolver, or they will disagree about what is armed; (b) once a tool owns a word exclusively, an **under-arming** grammar gate becomes a dead zone rather than a harmless miss — the other tool is no longer there to cover it, so the gate must be verified across every position the construct may legally begin in, and should widen rather than narrow when uncertain. **Rule: before declaring one tool the owner of a keystroke, enumerate every source that can still respond to it — vocabulary, names, and the trigger paths themselves.**

229. **A line comment's trivia span ends BEFORE the newline, so a caret at its `End` is still inside the comment — a block comment's `End` is not.** `SqlTrivia` for `-- note ` covers exactly `-- note ` (the doc says so: "up to, but not including, the end of line"), so the strict `caret > Start && caret < End` test that is correct for a `/* … */` reports *false* for a caret sitting at the end of a line comment — which is precisely where a developer types. Typing Ergonomics' delimiter pairing hit this immediately: `-- note |` + `(` inserted `()` **inside a comment**, because the caret was on the boundary rather than strictly within it. The asymmetry is real and intentional, not a lexer bug: a line comment runs *to* end-of-line (everything typed at its end stays commented), while a block comment's `End` is past the `*/` and is code again. **Rule: when consuming trivia spans, treat `LineComment` as inclusive at `End` and `BlockComment` as exclusive.** Same shape as the unterminated-literal case beside it (a string the developer hasn't closed runs to the end of the text, so the caret at its `End` is still inside it) — in both, "the region extends past where its span stops". *(`DelimiterPairing.IsInsideLiteralOrComment`)*

231. **When a batch's pass/fail drives control flow, compute it from the execution loop's OWN tally — never from the batch dialog's `SuccessCount`/`FailedCount`, which are updated via `IProgress` and can lag.** Save-and-close reuses `RunBatchWithReportAsync` with a custom `executeAsync` delegate that drives each dirty editor's `SaveAsync`; the orchestrator's `progress.Report(...)` marshals through `Progress<T>` (captured `SynchronizationContext`), so `vm.AddResult` — and therefore the counters — run on a posted callback that, with no `SynchronizationContext` (headless tests), lands on the thread pool AFTER the loop returns. `SaveDirtyEditorsAsync` originally decided "may I close?" from `report.SuccessCount == count` and read stale zeros. Fix: tally `succeeded`/`firstFailedTab` inside the loop itself (plain locals) and decide from those; the VM counters are for the DIALOG only. Corollary worth knowing: `RunBatchWithReportAsync` calls `vm.RequestCancel()` immediately after `await show(vm)` returns, so **without a `BatchResultsRequested` handler the token is cancelled the instant the modal would have closed** — only *synchronously-completing* steps finish (real usage is safe because the modal `ShowDialog` blocks until the batch is done; a headless test with async steps would see them cancelled). **Rule: a batch's own progress UI is a view, not a source of truth for the caller's decision — keep the decision in the loop.** *(`MainWindowViewModel.SaveDirtyEditorsAsync`)*

232. **AvaloniaEdit's `CompletionList` filters by SUBSTRING by default, and `IsFiltering = false` is the only way to take the list back — after which the inner ListBox renders your `CompletionData` verbatim, in your order.** Its match scale (the *private* `GetMatchQuality`, no override hook) runs exact → StartsWith → CamelCase → **Contains**, and anything scoring ≥ 1 is displayed. On a metadata-heavy database that silently turns interactive completion into a catalog search: typing `cont` lists `XXX_PS_CONTRACTORMAP`, `GEN_XXX_PS_CONTRACTORMAP`, `MON$CONTEXT_VARIABLES` and every `FK_…CONTRACTOR…` index beside the `CONTAINING`/`CONTINUE` the user actually meant. **Measured**, not assumed (headless probe, 12.0.0): with `IsFiltering = false`, `SelectItem()` degrades to a selection move (`SelectItemWithStart`), `ListBox.ItemsSource` stays bound to `CompletionData`, and **AvaloniaEdit's quality re-sort stops too** — so the kind ranking you supplied survives (a table ranked 3.0 renders above a keyword ranked 1.0, where the quality sort would have floated the exactly-matching keywords first). Consequences once it is off: the list is yours to narrow on every prefix change (drive it from `Caret.PositionChanged` — it covers backspace/delete/paste/click, where `TextEntered` covers only typing), and `ICompletionData.Priority` goes **inert**, since AvaloniaEdit read it only from the filter path. **Rule: interactive completion is a PREDICTION engine (prefix), not a search engine (substring) — substring lookup over the catalog is Global Search, a different workflow and a different window.** *(`SqlCompletionController.OpenWindow`; supersedes the workarounds in #200 and #227)*

233. **A correct, unit-tested Core component that nothing calls is indistinguishable from a regression — and the green suite is what hides it.** The prefix-first `CompletionMatcher` shipped with 8 passing tests pinning exactly the behaviour the user wanted, and the user still saw substring matches for weeks: the wiring step had been deferred to a later session, so the component sat unused while AvaloniaEdit's filter did the real work. Every signal said healthy — build 0/0, suite green, the rule demonstrably implemented and reviewable in Core — because the tests asserted the *component*, never the *surface*. The user reported it as a regression, which it wasn't; nothing had ever worked. Two habits fall out: (a) when a milestone deliberately lands a foundation and defers the wiring, the parked state belongs somewhere that gets read on a bug report — CLAUDE.md's "Current state" said so, and checking it turned a hunt into a 5-minute diagnosis; (b) the pin for "Core decides X and the UI shows exactly X" must be taken **at the surface** — here a headless probe reading the *rendered* ListBox, deliberately with no fallback to the `CompletionData` we supplied, since reading your own input back asserts nothing. **Rule: a unit test proves a rule exists; only a test at the surface proves the rule is in force. If a component's whole value is being called, assert that it is called.** *(`ConnectionExpandBindingProbe.Completion_PrefixFirst_ListsOnlyStartsWithMatches`)*

234. **AvaloniaEdit's `CompletionList.CompletionData` is a plain `List<ICompletionData>`, NOT an `ObservableCollection` — mutating it after the window is shown updates NOTHING on screen.** `OnApplyTemplate` binds `ListBox.ItemsSource = _completionData`; a `List<T>` raises no `CollectionChanged`, so the rendered rows freeze at whatever was bound when the template applied, while the collection quietly reads something else. AvaloniaEdit never mutates it: `SelectItemFiltering` builds a **fresh** `List` and assigns `ListBox.ItemsSource = listBoxItems` — **that assignment IS its refresh mechanism**. So switching `IsFiltering` off (#232) silently removes the only thing that ever re-assigns `ItemsSource`, and a `Clear()`+`Add()` in its place changes the data and nothing else: typing `n.id_nagl` kept the row `ID_AKWIZYTOR` on screen while `CompletionData`, `SelectedItem` and even `ListBox.ItemsSource` all correctly read `ID_NAGL`. **The tell was `ListBox.ItemCount` frozen at its opening value** — the control had never heard of the change. Fix: after populating `CompletionData`, hand the ListBox a snapshot (`listBox.ItemsSource = new List<ICompletionData>(data)`), mirroring AvaloniaEdit's own pattern; keep `CompletionData` content-identical to it, because with `IsFiltering=false` AvaloniaEdit's `SelectItemWithStart` indexes into `CompletionData` and applies the index to the ListBox. **Rule: before mutating a control's bound collection, confirm it is observable — if the type can't broadcast, assignment is the only refresh.** *(`SqlCompletionController.Populate`; the flip side of #232)*

235. **Reading a control's `ItemsSource` proves what it was TOLD, not what it SHOWS — assert the realized containers.** The probe for #232/#233 read `ListBox.ItemsSource` and passed while the screen was visibly wrong (#234), because `ItemsSource` was the very `List` we had just mutated: the assertion was reading our own input back through the control's front door. It was written explicitly to avoid that trap ("no fallback to the `CompletionData` we supplied") and fell into it one level down — the object identity, not the property name, is what made it circular. The hook that catches it walks `ContainerFromIndex(i)` after `UpdateLayout()` and reads each realized container's item; against the stale-list bug it reported `[ID_AKWIZYTOR]` where `ItemsSource` said `[ID_NAGL]`. **Rule: for a "the UI shows exactly X" claim, the assertion must traverse the visual tree; any hook whose value can be satisfied by the data you passed in is not evidence.** Corollary: virtualization means containers are only realized for the visible window, so assert them on small fixtures and keep the ItemsSource check alongside for content. *(`SqlCompletionController.RenderedRowsForTest`; a sharper instance of #233)*

## MVVM / CommunityToolkit patterns

11. **`ObservableCollection` mutations from non-UI threads break compiled bindings.** `FirebirdConnectionService.ActiveConnectionChanged` fires on whichever thread the async work completed on (`ConfigureAwait(false)` everywhere). Touching `WorkspaceTabs.Add/Clear` from that thread crashes the binding layer for `ItemsControl` consumers. **Rule**: any service-event handler in a VM that mutates ObservableCollection (or properties bound to ItemsControl) must `Dispatcher.UIThread.Post(...)` the work. Scalar OnPropertyChanged is fine (binding layer handles it), but collection-change events go through directly.

14. **CommunityToolkit `[ObservableProperty]` + `partial void OnXxxChanged` is the right tool for paired bindings, but you MUST guard the loop with a `_suppress*` flag.** When `QueryText` writes back to `SelectedSavedQuery.SqlText` (via `OnQueryTextChanged`) and `SelectedSavedQuery` change writes to `QueryText` (via `OnSelectedSavedQueryChanged`), naive code re-enters infinitely. The guard pattern: `if (_suppressX) return;` at the top of each hook, and `_suppressX = true; try { ... } finally { _suppressX = false; }` around any line that would re-trigger the other hook. Skip the flag at your peril — diagnosing the infinite loop after the fact is harder than adding the flag prophylactically.

108. **Any VM that subscribes to a longer-lived owner's events MUST expose a `Detach()` and be detached before it's discarded — especially when a collection of such VMs is rebuilt on every load.** `EditableFields` (one `FieldRowViewModel` per column) is torn down and rebuilt on every structure load; each row hooked `owner.PropertyChanged` + `owner.AvailableDomains.CollectionChanged`. Without `Detach()`, every reload left a generation of dead row VMs still wired to the owner, accumulating across refreshes (and firing on every subsequent `AvailableDomains` mutation). Rule: rebuild helpers detach outgoing items before `Clear()`.

187. **A button/command gated on a COLLECTION-derived value (`Count`, `Any()`, `_items.Count > 0`, …) must have EVERY mutation path raise the matching `OnPropertyChanged`/`NotifyCanExecuteChanged` — correctly computing the property is not enough; the UI won't re-query it on its own.** This bit the Export button in FOUR places (Table Data, View Data, Activity Monitor, and each was the same shape): the `CanExport*` getter was right, but `IsEnabled="{Binding CanExport}"` (or a command `CanExecute`) is evaluated ONCE and only re-evaluated when a `PropertyChanged` for that name fires — so with no notification the button latches at its ctor-time value (usually `false`) forever. Two correct patterns: (a) if the gate derives from an `[ObservableProperty]` (e.g. `_dataResult`, `_currentResultVersionTag`, `_execResult`), put `[NotifyPropertyChangedFor(nameof(CanX))]` (+ `[NotifyCanExecuteChangedFor(nameof(XCommand))]` for a command) on that FIELD; (b) if the gate derives from a plain mutable collection (`_all.Count`), raise `OnPropertyChanged(nameof(CanX))` in the single choke point that already notifies the collection's other derived props (there was already a `TotalCount` raise sitting right next to the missing `CanExport` — co-locate them so the next collection-derived prop can't be forgotten). Treat this as a standing MVVM rule for all future modules: **any collection mutation → notify every state (property + command CanExecute) that reads that collection.** Diagnostic tell: "the feature works but the button is stuck disabled" ⇒ a missing notification, not broken logic.


## Settings, security & persistence

87. **Whole-file DPAPI encryption changes the failure mode from "lose the password" to "lose everything".** With per-field encryption a bad decrypt degraded only that field; with the whole file encrypted, an undecryptable `settings.dat` (e.g. copied to another Windows account/machine) yields **no settings at all**. `ApplicationSettingsStore.Load` returns null and **never overwrites** the unreadable file (it may decrypt on the right machine). This is the intended stronger "nothing leaks cross-machine" posture, but it means the store degrades to a fresh/empty state rather than a partial one — design every consumer's null-handling accordingly.

88. **A View that owns persistence must derive its store location from the VM, never hardcode the default dir — or headless tests hit the real `%AppData%`.** `MainWindow` had `private readonly WorkspaceStore _workspaceStore = new(DpapiSecretProtector.Create());` (default dir) and `_pendingRestore = _workspaceStore.Load()` in the ctor. `ConnectionExpandBindingProbe` builds the **real** `MainWindow`, so that field initializer + ctor `Load()` ran against the user's live `%AppData%\EmberTern` — and with the new unified store it triggered destructive **legacy-file migration of real data** during `dotnet test`. Fix: make `_workspaceStore` nullable and build it in `OnDataContextChanged` from `_currentVm.Store` (its dir + `Protector`), so the View's workspace section lands in the same file the VM uses — temp dir in tests, real dir in production. **Rule**: any store a View constructs for itself must be sourced from the attached VM's store location, not a hardcoded default; verify with a before/after mtime check on the real file during a test run.

92. **Whole-file `Load` returning null is NOT enough to protect a file from overwrite — the facade write path clobbers it.** `ConnectionProfileStore`/`FolderStore`/`WorkspaceStore` all do `_settings.Load() ?? new ApplicationSettings()` then `Save()`. So a `Load` that degrades a future/unreadable file to null is immediately followed by a `Save` of fresh defaults that *overwrites the very file you were protecting*. Real downgrade protection requires the guard in **`Save`** too: read the existing file, and if it's detectably from a newer build (container version, unknown encryption scheme, or future data SchemaVersion), refuse to write and leave it intact. **Rule**: any "don't overwrite a newer file" requirement must be enforced at the write boundary, not just the read boundary — a read-only guard is defeated by the next read-modify-write cycle.

163. **Persist typed dialog/input values as canonical invariant strings + re-hydrate per type — never boxed `object?` in JSON.** The Execute-params dialog holds typed values (`decimal`/`DateTime`/`TimeSpan`/`bool`/`string`); serializing `object?` through System.Text.Json is lossy/ambiguous and couples the on-disk shape to CLR boxing. Store `{ IsNull, Text }` where `Text` is invariant-culture (`yyyy-MM-dd HH:mm:ss.FFFFFFF` for TIMESTAMP so sub-seconds survive — gotcha #161; `hh\:mm\:ss` for TIME; invariant `decimal`), and parse back keyed on the known type. Ignore unparseable values on restore (a schema/type change must degrade, not crash). Per-object history is a new `UserSettings` section behind a `ParameterHistoryStore` facade (the `GridProfileStore` pattern — read-modify-write over the shared encrypted `settings.dat`, never clobbering sibling sections); key by `ConnectionId` (exact) + `ObjectKind` + `ObjectName` (case-insensitive), dedup the newest set, cap FIFO, and auto-select the newest in the VM ctor for "re-run last".


## Testing, tooling & build discipline

67. **xUnit2031 — `Assert.Single` z lambdą zamiast `Where().Single()`.** Analyzer xUnit'a flag'uje `Assert.Single(coll.Where(p))` i wymaga `Assert.Single(coll, p)` (predicate overload). Działa identycznie ale generuje lepszy error message przy fail'u (mówi ile elementów spełniało predykat, nie tylko "expected 1 got N"). Razem z `xUnit2029` (`Assert.Empty(coll.Where(p))` → `Assert.DoesNotContain(coll, p)`) trzymaj w pamięci przy pisaniu testów na collection-predicate assertions — IDE pokaże errory ale to brak zwykłych warning'ów.

238. **A debug-engine fake `IDebugExecutor` that keys scripted outcomes by a node's `Start` offset is ambiguous across frames — two PSQL bodies built the same way put their first statement at the same offset, so a cross-frame test can trigger the wrong frame's scripted raise.** The `DebugEngineTests` fake maps outcomes/conditions/routines by `statement.Start` (its only stable identity for an AST node). But each frame interprets an *independent* body parsed in its own coordinate space: `"begin a = 1; end"` and `"begin r = 1; end"` both start their first statement at offset **6** (the shared `begin ` prefix). So `Outcome(Off(calleeSql,"r = 1"), Raised)` also scripts a raise for the *root's* `a = 1` — executing the root leaf picked up the callee's outcome and the propagation test "completed at depth 0" instead of descending. This is a limitation of the test fake, not the engine (the real D2 executor runs a specific AST node, not an offset lookup). **Rule for debugger tests spanning ≥2 frames: keep the frames' scripted offsets disjoint on the *executed* path** — e.g. start the root with the call itself so the callee's raising offset is only ever descended into, never run as a root leaf. *(`DebugEngineTests.Exception_PropagatesToCaller_…`; Stage X / D1 seam b)*


## General engineering discipline & miscellaneous

5. **`FirebirdConnectionService.ActiveConnectionChanged` fires on the async-continuation thread.** Any handler that touches UI-bound state must marshal with `Dispatcher.UIThread.Post`. Only `ConnectionNodeViewModel.OnActiveConnectionChanged` needs this — the service's `ConnectAsync` / `DisconnectAsync` are normal awaitables and don't need wrapping.

9. **`Screens` may be empty before window is on a platform.** Accessing `this.Screens.All` from the constructor returns null/empty on some configurations. Sanity-checking bounds against screens must happen in `Opened` (or later) — that's why bounds restore moved out of the ctor. The check itself wraps in `try/catch` and returns `true` on failure so a platform quirk doesn't strand the user with default-sized windows forever.

12. **Test seams: prefer parameterizing the worker over mocking the service.** Driving `OnActiveConnectionChanged` end-to-end requires a real `FbConnection.OpenAsync`, which tests can't have. Solution: factor the connection-switch work into `ApplyActiveConnectionChange(string? newProfileId)` (internal). Production reads `_service.ActiveProfile?.Id` and passes it in; tests pass arbitrary string ids. No mock, no extra interface, no `IConnectionService` abstraction. Matches the codebase's "no interfaces without two implementations" rule.

21. **When a child element sets its own `DataContext` via Binding, sibling bindings on the same element resolve against the NEW DataContext — not the parent's.** First-pass markup `<views:TableDetailTabView DataContext="{Binding ActiveTableDetail}" IsVisible="{Binding IsTableDetailTabActive}" />` fails compile with `AVLN2000: Unable to resolve property … IsTableDetailTabActive on TableDetailTabViewModel` because IsVisible's binding source is the just-set DataContext (`TableDetailTabViewModel`), not the parent `MainWindowViewModel`. Fix: source IsVisible through the window's DataContext explicitly with `ElementName`: `IsVisible="{Binding DataContext.IsTableDetailTabActive, ElementName=RootWindow}"`. **Rule**: when you set `DataContext` on an element via Binding, every other binding on that same element must source explicitly (ElementName, RelativeSource) or evaluate against the new context — there is no parent-DataContext fallthrough.

**Tests** — new [FirebirdTableDetailReaderTests.cs](tests/EmberTern.Tests/FirebirdTableDetailReaderTests.cs) covering type-integer→string mapping (basic types, CHAR/VARCHAR with length, NUMERIC/DECIMAL with negative scale, INTEGER with zero scale, unknown→TYPE_n), `IsPrimaryConstraint` case-insensitivity, `StripDefaultPrefix` behavior on `DEFAULT 0` / `default 42` / null / empty, and SQL-shape regression pins for both `FieldsSql` and `IndexesSql`. **309 / 309 green** (281 → 309, +28 new). Smoke-verified: app launches, runs 5 seconds without crashing.

23. **`EnsureLoadedAsync` + `_loadTask` for idempotent lazy load.** When a VM may have its `LoadAsync` triggered by multiple call sites (e.g. tab activation fire-and-forget + an `OnOpenDdlRequested` that awaits the result), they MUST join the same task. The two-line idiom: `private Task? _loadTask; public Task EnsureLoadedAsync(CancellationToken ct = default) => _loadTask ??= LoadAsync(ct);`. First caller starts the load and assigns; later callers get the running/completed task back. Single-thread UI context means no race on `??=` assignment. Reset is free: throw away the VM instance (e.g. on reconnect) and the new one starts fresh.

47. **FirebirdSql.Data 10.x multi-reference named parameters are unreliable inside complex UNION ALL queries.** The docs say "the same @name can be used multiple times" — and for simple 2-branch unions it does work. But once a branch has an INNER JOIN further down the UNION, the driver empirically drops the parameter binding on that branch and the WHERE silently returns no rows (no exception, just zero results). Cost: a "Used by → Tables" panel that showed 6 instead of 134. The fix is mechanical: use distinct `@t2`, `@t3`, `@t4` names per branch and `AddWithValue` each one. Each branch gets its own positional parameter; the driver never has to do the name-to-multiple-positions resolution that's broken. **Rule**: any time the SQL has more than one `@name` reference, give each occurrence a distinct name. If tests need an `Assert.Contains("= @tableName", sql)` pin to stay green, keep the first occurrence as `@tableName` and rename the rest.

54. **Firebird `ROWS m TO n` pagination uses literal integers, not parameters, on FB 2.5.** Newer FB versions accept `ROWS @offset TO @end` parameter binding; FB 2.5 does not. `BuildDataPreviewSql` embeds the page bounds as literals via `StringBuilder.AppendFormat(InvariantCulture, ...)` — safe with integers, and avoids the brittle cross-version parameter-binding behavior of the `ROWS` clause. **Rule**: for pagination SQL targeting "anything from FB 2.5 onward", embed the row range as literals.

55. **Splitting multi-statement DDL on `;` must track BEGIN/END nesting.** PSQL bodies (CREATE TRIGGER / CREATE PROCEDURE) carry internal semicolons that terminate intra-block statements — splitting naively chops a CREATE TRIGGER into pieces that no longer parse on their own. The fix: a single nesting counter that increments on word-boundary BEGIN and decrements on word-boundary END (case-insensitive). Each `;` only commits a statement when the counter is zero. Enough for the shapes EmberTern emits today (no nested triggers, no procedures); revisit if we ever generate nested BEGIN/END blocks. Tests pin both the "no nesting" simple case and the "trigger body with internal `;` is preserved as one statement" case via the autoincrement DDL.

65. **Edit dialog "no-op when no change" wymaga diff'u, nie sygnału z dialogu.** Tempting: dodać `IsDirty` flag w dialog VM, gate'ować Accept na tym. Problem: użytkownik może wpisać znak i go zmazać — dialog uznałby się za dirty pomimo identycznego końcowego stanu. **Rule**: no-op semantykę implementuje pipeline DDL (BuildAlterStatements zwraca empty list dla zerowego diff'u), nie dialog. Owner woła `ExecuteEditFieldAsync` zawsze gdy user klika OK — pipeline decyduje czy cokolwiek emitować. Plus: testowalne czysto bez UI.

68. **Dialog VM-driven over dialog-loaded.** Wcześniejsze podejście (Session 2 AddFieldDialog): view-side `OpenAddFieldDialogAsync` fetch'ował domains+generators **przed** stworzeniem VM-a. Session 3 zmienia paradygmat: VM dostaje **callbacks** (Func<T1, Task<T2>>) i loaduje on-demand sam (gdy user picks target table). Plusy: (a) test'owalne synchronicznymi fake'ami, (b) tańsze open (nie blokuje na fetch'u tablistę całego DB), (c) re-fetch on user action darmowy (e.g. user changes target → fresh fields). **Rule**: dla future wizard'ów (Session 4 panel zależności, wszelkie kolejne) wybieraj callback'i over ahead-of-time fetch — szczególnie gdy dane są user-driven (target selection trigger'uje fetch).

72. **`MetadataObject` to klasa (reference type), nie struct/record-struct** — `MetadataObject? x` to nullable reference, NIE `Nullable<T>`. Brak `.Value`; dostęp przez `x!.Name`. Łatwa pomyłka w testach gdy piszesz `x.Value.Kind` z nawyku od struct-recordów.

73. **Rozszerzanie współdzielonego SQL o kolumnę jest bezpieczne gdy readery czytają po indeksie i nowa kolumna jest ostatnia.** `DependedOnBySql` używane przez table-level tree ORAZ field-panel. Dodanie 4. kolumny (`RDB$TRIGGER_TYPE`) nie zepsuło drzewa (czyta tylko 0-2, ignoruje 3). 74. **Confirm-then-execute wrapper pattern dla destrukcyjnych komend.** Gdy operacja jest wywoływana zarówno z UI (musi pytać) jak i z testów / ścieżek programmatic (nie może pytać), rozdziel na dwie metody: publiczny `XxxWithConfirmationAsync` (RequestConfirmAsync → jeśli ok → wywołaj raw) i raw `Xxx` (bez promptu). 96. **Setting only `Width=0` on a `Grid` `ColumnDefinition` does NOT reliably collapse it to 0 when a `GridSplitter` is adjacent — the column's `MinWidth`/`MaxWidth` still permit a non-zero width and the splitter's layout pass re-reserves the prior pixel width (leaving an empty gap, panel hidden but space reserved).** To force a column to exactly 0px, clamp all three: `MinWidth=0; MaxWidth=0; Width=GridLength(0)`. Restore `MinWidth`/`MaxWidth` on expand. This is correct sizing via the column's own constraints, not a visibility hack.

115. **Firebird has no incremental parameter ALTER — editing a procedure's params means recompiling the whole `CREATE OR ALTER PROCEDURE`.** There is no `ALTER PROCEDURE ADD/DROP PARAMETER`. So an "edit params in a grid" feature can't be a standalone operation; it must feed a canonical model {name, inputs, outputs, body} that Compile reassembles into the full statement (signature + body) and runs. 126. **A ChatGPT-exported "transparent" PNG may actually be opaque RGB with a baked-in checkerboard — verify the PNG colour type before trusting it as a transparent source.** A first-attempt source looked transparent (gray checkerboard) but was PNG colour type **2 (RGB, no alpha, no `tRNS`)** — the "transparency" was a literal light checkerboard (~`#F2F2F2`/`#FEFEFE`) painted into the pixels (corner pixels `A=255`). 145. **A function editor has TWO distinct "Result" concepts — never merge them.** Easy-mode **Result** = the function's return-TYPE metadata: a single, unnamed `RETURNS <type>` row (+ a `Deterministic` flag) that the user edits and that drives the generated DDL. Procedure's single top-level "Result" tab (execution output) does NOT map 1:1 onto a function — for a function the execution-output tab is renamed **"Execute Result"** so the word "Result" is free for the return-type metadata. 155. **"Open the results dialog immediately" isn't enough — the delay can be entirely in building the operation list BEFORE the dialog opens.** The batch dialog already opened up front for *execution*, yet the user still waited 10–15 s because the caller enumerated + fetched one source-per-object to build `steps` before invoking the dialog at all. Any "show progress immediately" work must cover *preparation*, not just execution — audit where the pre-work actually happens.

162. **When you relocate the only content of a toolbar "section", update that section's visibility predicate — or its separator orphans.** The unified toolbar draws a `|` between two non-empty adjacent sections (`ToolbarSepNVisible = ShowSectionN && HasFromN+1`). 165. **Once measured data exists, the plain-language summary MUST be derived from the measurement, never from a plan heuristic that can contradict it.** The Phase-1 lead asserted a plan full scan was "often why a query is slow"; measured per-table reads proved that scan cheap (285 rows) while the Findings zone correctly said "no costly full scans" — so the same panel showed an amber "Needs attention", a plan-blaming lead, and a green "nothing costly" note simultaneously. The fix is layering, not new logic: the verdict **grade** stays an honest coarse signal (time + a finding-driven bump — never suppressed, a slow query is slow), but the **narrative** (`PerformanceInsight` lead) switches to the measured findings the moment reads are available, so grade/summary/findings describe the same reality from different angles instead of fighting. **Rule:** when a richer measured signal supersedes an earlier heuristic, route the *user-facing explanation* through the measured signal and keep the heuristic only as the no-measurement fallback — don't leave two independent narrators that can disagree.

171. **Firebird trace ERROR events are `ERROR AT <function>` (multi-word) — a header regex of `[A-Z_]+` silently drops them, so errors never parse.** The trace event token is normally a single UPPER_SNAKE word (`EXECUTE_STATEMENT_FINISH`), but the `Errors` config flag emits `ERROR AT jrd8_execute` / `ERROR AT jrd8_prepare_statement` etc. A header pattern that only accepts `[A-Z_]+` fails to match those lines → the whole error block is skipped and no error ever surfaces (the downstream red-stripe/Detail/Errors-filter machinery looks broken but was never fed). Allow an optional `" AT .+"` tail in the header, capture the following status-vector lines (`-?\d+ : message`) as the error text (they also terminate SQL accumulation so the message doesn't pollute the SQL), and — since `MapKind("ERROR AT …")` returns System — derive the real kind (Statement/Procedure) in the folder from the block's SQL/object. Verify error handling end-to-end with a captured error block, not just the happy path.

197. **A resolved identifier can carry MORE THAN ONE `SymbolReference` at the exact same span — apply semantic highlighting lowest-priority-first so the stronger class wins.** A table referenced by its own name (`FROM KONTRAHENT`, no alias) records BOTH a schema-object occurrence (→ table colour) AND an implicit table-reference occurrence (implicit alias == table name → the "local" colour) at the identical span. A `DocumentColorizingTransformer` applies `ChangeLinePart` in call order and the LAST write wins for an overlapping range, so naively iterating `model.References` (object added before the table-ref) paints it local. Fix: collect the line's hits, sort by class priority (Local < Column < SchemaObject), apply ascending so the object class is painted last and wins. Non-overlapping references are unaffected. General rule for any semantic paint over the model's references: never assume one reference per offset — resolve overlap by a deliberate priority, not by iteration order.

238. **A reused `SELECT … INTO` statement inside a PSQL body surfaces NO local references from the binder — its `:`-colon refs in the `WHERE` and its `INTO` targets are not recorded (a token-walked `INSERT`/assignment/`IF` records theirs correctly).** Found while wiring the debugger's `FirebirdDebugExecutor` (D2 seam c): `ReadWriteSetAnalyzer.Analyze` over a `SELECT COUNT(*) … WHERE X = :P INTO :V;` returns **empty reads AND empty writes**, because that statement is a *reused* `SelectStatement` (Etap 6.9 / B5) bound by the query binder — which records `FROM`/columns but not the colon-refs (`:P` in `WHERE`, `:V` in `INTO`). Consequence for anything driven off the precise read/write set: the `INTO` write-back is silently dropped and the WHERE param never injected — for the debugger, the variable the statement exists to set stays unassigned, so a following `IF (:V = 0)` sees `null` and control diverges from real execution (a §F divergence, caught only by the live lab comparison, not by unit tests). **Fix in the consumer, not a second resolver:** when the model surfaces no local refs for a data statement (empty/empty), fall back to §3.5's named `ReadWriteSetAnalyzer.InScopeLocals` (inject/return ALL in-scope locals — "correct, chattier", never a guess). The precise narrowing stays in force for every statement whose refs the binder *does* surface. This is a real binder gap (it likely also means such `:vars` aren't highlighted/navigable inside a `SELECT … INTO` in the editor) — a future binder deepening that surfaces reused-`SELECT`/`INTO` refs would let the fallback stop firing; pinned by `ReadWriteSetAnalyzerTests.SelectInto_SurfacesNoLocalRefs_SoTheFallbackIsInScopeLocals`. **Rule: a precise read/write (or reference) set derived from the binder is only as complete as the binder's coverage of the statement shape — verify against a live comparison, and fall back to the safe superset rather than trusting an empty set.** *(design: `docs/design/firebird-debugger.md` §3.5 + §15.4)*

239. **When extracting a PSQL cursor query as standalone DSQL (the Cursor Bridge, D6), rewrite ONLY the `:name`/`@name` (colon/at) variable references to parameters — never the bare identifiers the binder resolved to a frame variable/parameter.** The binder resolves a *bare* name in a query to a local/parameter when one exists (locals shadow columns in its resolution order — gotcha #238's flip side: here it surfaces *too much*). Acting on that mis-rewrites a **column that shares an output-parameter name**: a routine that both `RETURNS (LINE_NO …)` and does `SELECT LINE_NO …` had the SELECT-list column `LINE_NO` rewritten to a positional `?` → `SELECT ?, …` → **`FbException` SQL -804 "Data type unknown"** (a `?` in a projection has no type context). This was invisible to unit tests (the pure builder produced "valid-looking" SQL) and only surfaced in the **live sim-vs-real fidelity run** (§2.1). **The fix is to trust Firebird's own disambiguation:** inside a query, `:VAR` is the unambiguous variable reference (and a native DSQL bind once extracted), while a bare name is a **column**. So `CursorBridge` rewrites only the lexer's `Parameter` tokens (`:name`/`@name`) and leaves every bare identifier verbatim. A bare local ref that Firebird would resolve as a variable is rare, ambiguous, and — if it cannot bind as a column — surfaces as an honest step-level "column unknown", never a silent wrong value (§F: correctness over reach). **Rule: a query lifted out of PSQL context must not inherit PSQL's local-shadows-column resolution — only the syntactically-unambiguous `:`/`@` form is a variable there.** *(`CursorBridge`; pinned by `CursorBridgeTests.ColumnSharingAnOutputParamName_NotRewritten`; design `firebird-debugger.md` §7 + §15.5)*

240. **A collapsible-panel toggle that mutates only the collapsing row will "glue" to its neighbour after a GridSplitter drag — the re-normalization must set BOTH the star row and the pixel row, every time.** Avalonia's `GridSplitter` (`ResizeBehavior=PreviousAndNext`) sitting between a `*` (star) row and an absolute-pixel row **converts the star row to an absolute pixel height** on a real drag (its Split behaviour rewrites both neighbours' sizes). If the collapse/expand code then mutates only the *pixel* row (Auto ↔ remembered height) and never touches the (now-absolute) former star row, the grid is left with **no star row**: nothing reclaims the vacated space, so collapse leaves a gap and re-expand can't restore the editor↔panel relationship — the panel appears stuck to / detached from the editor. **The debugger's bottom panel hit this; three prior fixes fiddled with the splitter double-click (a `_splitterGestureHeight` snapshot) and never touched the cause.** The SQL editor never has the bug because its `ApplyResultsRowForActiveTab`/`ApplyResultsMaximized` are a **single re-normalization point that always sets both rows** — editor row back to `*`, results row to pixel/0. **Fix + rule: make one method the sole layout-apply point and have it set every row explicitly (star + pixel) on each toggle; then the splitter's transient mutations never survive, and a double-click's spurious micro-drag is absorbed by the same re-normalization (no per-gesture snapshot needed).** *(`DebuggerTabView.ApplyBottomPanel`, mirrors `MainWindow.ApplyResultsRowForActiveTab`)*
