### Firebird routine reconstruction fixes — param defaults, DB-level triggers, packaged-routine duplicates, DEV-Mode recompile (shipped 2026-07-06)

Four DDL-reconstruction / recompile-correctness bugs surfaced by the "Recompile all" mechanism on the user's FB5 ERP. **2544 → 2570 tests** (+26 across three fix rounds), build 0/0, smoke OK. All fixes are reader/reconstruction-side; verified against the user's live DB + IBExpert reference.

**1. Procedure/function parameter default `SMALLINT = = 1`.** Firebird stores a routine-parameter default in `RDB$*_PARAMETERS/ARGUMENTS.RDB$DEFAULT_SOURCE` with its leading token **exactly as written** — for parameters that's the `= value` form (table columns/domains use `DEFAULT value`). `FirebirdTableDetailReader.StripDefaultPrefix` only stripped `DEFAULT `, so `= 1` survived, and `DdlGenerator.AppendProcedureParamLines` re-prepended `" = "` → the un-compilable `SMALLINT = = 1`. Fix: `StripDefaultPrefix` now also strips a leading `=`. Also made `FirebirdDdlReader.ReadProcedureParamsAsync` read + emit the default (the read-only DDL tab was silently dropping it). Gotcha #175.

**2. DB-level + INACTIVE triggers reconstructed as invalid DDL (recompile -104).** `FirebirdDdlReader.BuildTriggerDdlAsync` had two bugs: (a) wrong clause order — it emitted `[INACTIVE] FOR table timing`, but Firebird requires `FOR table` FIRST, then `[ACTIVE|INACTIVE] {BEFORE|AFTER} event` (so an INACTIVE table trigger produced `… name INACTIVE FOR STANMAG …` → `Token unknown … FOR`); (b) DB-level triggers (type ≥ 8192: ON CONNECT / ON TRANSACTION COMMIT …) were emitted as table triggers (`/* trigger type 8192 */` or a fabricated `FOR TABLE_NAME BEFORE INSERT` in Easy mode). Fix: corrected clause order + new `DescribeDatabaseTriggerEvent` (8192→ON CONNECT … 8196→ON TRANSACTION ROLLBACK; type read as `long`, not `short`, so a DDL trigger can't overflow). Easy mode: `TriggerHeaderInfo.IsDatabaseTrigger` + `TriggerDetailTabViewModel.CanUseEasyMode => !IsDatabaseTrigger` (disables the toggle) + force Source mode on load + `BuildFullSource` returns `SourceText` for DB-level triggers (never fabricates). `TriggerSignatureParser` already `Fail()`s on `ON CONNECT`, so Source→Easy stays non-destructive. Gotchas #176 (clause order + ON events) and the `IsDatabaseTrigger` Easy guard.

**3. Packaged routine duplicated in the tree + params merged (recompile -901 "duplicate specification").** In FB3+ a packaged procedure/function lives in the SAME catalog tables as a standalone one, keyed by the same `RDB$*_NAME` (params/args carry `RDB$PACKAGE_NAME`). None of EmberTern's by-name queries filtered `RDB$PACKAGE_NAME IS NULL`, so a packaged `ADD_NUMBERS`/`GET_MESSAGE` alongside a standalone one (a) listed twice in the top-level Functions/Procedures nodes and (b) merged its args into the reconstruction (`A INTEGER, A INTEGER, B INTEGER, B INTEGER` → `-901`). Fix: exclude packaged rows on FB3+ EVERYWHERE a standalone routine is read by name — tree LIST/COUNT (`FirebirdMetadataReader.SqlFor`/`CountSqlFor`, new `serverMajor` overloads; 1-arg kept for shape tests), DDL/Source/body reconstruction (`FirebirdDdlReader`: `ReadProcedureParamsAsync`, `ReadFunctionArgsAsync`, `RDB$RETURN_ARGUMENT`, source-blob + body fetchers), and Easy-mode (`FirebirdTableDetailReader`: params, function signature, descriptions). Shared helpers `FirebirdDdlReader.StandalonePackageFilter(serverMajor, alias)` (leading+trailing space, gated on `serverMajor >= 3` — the column is FB3+ only, so FB2.5 compat is preserved) + `InsertBeforeOrderBy`. Gotcha #177.

**4. DEV Mode (WAIT) ignored during "Recompile all".** The recompile batch (`ExecuteAutonomousBatchAsync` → `FirebirdConnectionService.ExecuteAdminBatchAsync`) opened its transient-attachment transaction with `BeginTransactionAsync(ct)` — no explicit TPB (driver default), ignoring the connection's Developer Mode. So an in-use object failed immediately instead of waiting. Fix: `ExecuteAdminBatchAsync` now accepts an optional `FbTransactionOptions`, and `ExecuteAutonomousBatchAsync` passes `BuildDdlTransactionOptions()` (Developer → WAIT + 10 s lock timeout; Standard → NOWAIT). Note: recompile still uses a transient attachment, so the cross-attachment "object is in use" (gotcha #122) is only *mitigated* by WAIT, not eliminated — routing recompile through the main connection conflicts with its continue-past-failure design and is a separate future refactor.

**Gotchas — promote to architecture lore.**

175. **Firebird stores a routine-parameter default in `RDB$*_PARAMETERS/ARGUMENTS.RDB$DEFAULT_SOURCE` with the `= value` form (NOT `DEFAULT value`), keeping the leading token exactly as the DDL wrote it.** Table columns / domains use `DEFAULT value`; procedure/function parameters use `= value`. A strip helper that only removes `DEFAULT ` leaves `= 1` intact, and any generator that re-prepends `" = "` produces the un-compilable `SMALLINT = = 1`. Strip BOTH forms (`DEFAULT ` and a leading `=`) at the single read-time choke point (`StripDefaultPrefix`) so both the grid display and the Source/DDL regeneration get the bare value. A table/domain default expression can never legitimately start with `=`, so stripping it there is safe.

176. **Firebird trigger DDL grammar: `FOR <table>` comes FIRST, then `[ACTIVE|INACTIVE] {BEFORE|AFTER} <events> [POSITION n]`; a database-level trigger has NO `FOR`/`BEFORE`/`AFTER` — it's `[ACTIVE|INACTIVE] ON <event> [POSITION n]`.** Emitting `[INACTIVE] FOR table …` (INACTIVE before FOR) is `-104 Token unknown … FOR` for any INACTIVE relation trigger. DB-level triggers use `RDB$TRIGGER_TYPE` 8192=ON CONNECT, 8193=ON DISCONNECT, 8194=ON TRANSACTION START, 8195=ON TRANSACTION COMMIT, 8196=ON TRANSACTION ROLLBACK (read the type as `long` — DDL triggers carry values > `short`). A DB-level/DDL trigger has a NULL relation and no BEFORE/AFTER, so the relation-trigger Easy model can't represent it — disable Easy mode (`CanUseEasyMode`), keep it Source-only, and make `BuildFullSource` return the loaded source verbatim so a stray Easy⇄Source toggle can't fabricate `FOR TABLE_NAME BEFORE INSERT`.

177. **In FB3+ a packaged procedure/function shares the SAME catalog tables as a standalone one (`RDB$FUNCTIONS`/`RDB$PROCEDURES` + `RDB$*_ARGUMENTS`/`RDB$*_PARAMETERS`), keyed by the same `RDB$*_NAME` + an `RDB$PACKAGE_NAME` column.** Every top-level (standalone) read MUST add `RDB$PACKAGE_NAME IS NULL` or a packaged namesake (a) duplicates the object in the top-level Functions/Procedures nodes and (b) merges its params/args into the reconstruction (`A, A, B, B` → `-901 duplicate specification`). The column is FB3+ only, so gate the filter on `serverMajor >= 3` (packages don't exist on 2.5 → nothing to exclude, and the column would error). Apply it uniformly: LIST + COUNT (tree), the DDL/Source/body reconstruction, AND the Easy-mode param/signature/description readers — anywhere a standalone routine is fetched by name. Packaged routines belong under their package (Members tab), never the top-level list — matching IBExpert.

178. **A `.sql` script written for Firebird `isql` / IBExpert must be UTF-8 WITHOUT a BOM — and `File.WriteAllText(path, s, Encoding.UTF8)` EMITS a BOM.** `Encoding.UTF8` is `UTF8Encoding(encoderShouldEmitUTF8Identifier: true)`, so it prepends `EF BB BF`; `isql -i` and IBExpert's script executor then choke on the first statement (`<BOM>CREATE …` → parse error), while Notepad/Notepad++/VS Code read it fine either way. Write with `new UTF8Encoding(encoderShouldEmitUTF8Identifier: false)` (the app's `SqlFileWriter.Utf8NoBom`). Polish/Unicode round-trips losslessly regardless — the in-memory string is already correct UTF-16; the BOM is the only variable. Pin it with a byte-level test (`bytes[0..2] != EF BB BF`) so a refactor can't silently reintroduce `Encoding.UTF8`.

**Gotchas — promote to architecture lore.**

180. **`ElementName` (and any name-scope binding) does NOT resolve inside a `ContextMenu`/`Flyout` — they live in a separate popup namescope, not the window's.** A `ContextMenu` inherits the DataContext of the control it's attached to, so `{Binding SomeCommand}` against that DataContext works; but `{Binding DataContext.X, ElementName=RootWindow}` silently binds to null (the menu item just does nothing — no error). To reach a command that lives on a DIFFERENT VM than the menu's DataContext, expose a forwarding property on the DataContext VM (`public IRelayCommand FooCommand => _owner.FooCommand;`) and bind by inheritance — never reach across with `ElementName` from inside a popup. This bit the trigger "Selected" bulk items (bound to the explorer VM via `ElementName`) — they no-op'd until re-routed through a node-VM forwarding property.

181. **A multi-select `ListBox`/`TreeView` collapses its selection on RIGHT-click by default — if a context-menu action reads that selection, the right-click that opens the menu destroys it first.** This is the INVERSE of gotcha #16/#99 (there we WANT right-click to select the row under the cursor; here we must NOT let it collapse a multi-selection). The trigger "Selected" bulk op is invoked from the group node's context menu but acts on the leaf multi-selection held in the VM (`_selectedTriggers`, fed by `SelectionChanged`); a right-click anywhere (especially on the *group*, a different row than the selected leaves) re-selects one row and clears the multi-selection before the command runs → the op sees 0 or 1 items. Fix in the Tunnel `PointerPressed` handler: on `IsRightButtonPressed`, set `e.Handled = true` to suppress the ListBox's own selection change **when preserving the selection is what the menu needs** (clicked row already in the selection, or it's the "aggregator" node that acts on the selection) — the ContextMenu still opens because it fires on release/RightTapped, after PointerPressed. Preserve conservatively (don't blanket-handle every right-click) so unrelated rows still select normally for whatever depends on selection (here: the titlebar's `SelectedConnection`). Corollary: a context-menu action that operates on "the current multi-selection" should read a VM field snapshotted on `SelectionChanged`, and the right-click must be prevented from mutating that field.

182. **To reflect a small property change (e.g. a trigger's active state) in a virtualized tree, mutate the existing node VM in place — do NOT call a full `RefreshAsync`/reload.** A full metadata refresh reloads every loaded/expanded group (`LoadGroupAsync` → `Children.Clear()+Add`), which makes the FlatTree controller `RebuildRows()` (`Rows.Clear()` + re-add) → the ListBox loses scroll position AND selection (the reported "tree jump" after activate/deactivate). Since the change is only a display attribute on ONE (or a few) known leaves, flip it on the existing node instances (swap the immutable `Object` via `obj with { … }` behind a `private set`, raise PropertyChanged for the derived display props) — no collection mutation → no reproject → scroll + selection + expanded groups are all preserved for free, and it's faster (no catalog re-query). Reserve the full `RefreshAsync` for changes that actually alter the leaf SET (add/drop/rename) or where you can't identify the affected nodes. Corollary: don't try to fix the jump by snapshotting/restoring the ListBox scroll+selection across a reproject — avoid the reproject. For a BATCH of such changes, flip every affected node (e.g. the batch's per-step `SuccessfulObjects`), not just the one whose context menu opened. Two traps that broke the batch path: (a) `Dispatcher.UIThread.InvokeAsync` to "drain" marshaled `Progress<T>` results hangs unit tests (no dispatcher pump) — and is unnecessary since the modal batch dialog already pumps all results before it closes; (b) gating the flip on a `BatchResultsViewModel.CancellationToken` that the batch runner always `RequestCancel()`s as cleanup → the flip never runs → nothing updates. Read the results list directly (complete on return); don't gate on that token.

183. **The global `Style Selector="TextBlock"` (`Foreground=ForegroundBrush`) overrides a Button's inherited `Foreground` on its label text — a `Button.primary` with a `TextBlock` child needs its OWN descendant style to color the label.** `Button.primary` sets `Foreground=OnAccentBrush`, which the ContentPresenter should pass down — but a Style setter beats inheritance, so every `TextBlock` gets the dark `ForegroundBrush` instead (the Execute label was too dark on the blue button in Light theme; the play `SvgIcon` + the "F5" hint looked right only because they set their foreground explicitly). Fix in the SHARED style, not a local override: `Style Selector="Button.primary TextBlock" { Foreground = OnAccentBrush }` (defined after the global `TextBlock` style so it wins; a child TextBlock with its own local `Foreground`, like the subtle hint, still wins over it). Same trap applies to any button-class whose content is text on a non-default fill.

**Gotchas — promote to architecture lore.**

185. **A binary OOXML (`DocumentFormat.OpenXml`) exporter needs a read+write, seekable stream — a write-only `FileStream` fails with `OpenXmlPackageException: "The stream was not opened for reading."`** The SDK reads back the zip package's central directory while writing. Open the export file `FileAccess.ReadWrite` (not `Write`). Also: XLSX is binary + file-only — it cannot use a `TextWriter` sink and cannot target the clipboard; the sink abstraction must expose a byte `Stream` for binary formats (text exporters wrap that stream in a `StreamWriter` with their per-format encoding). Use the streaming `OpenXmlWriter` (write `Row`/`Cell` elements, inline strings — no shared-string table) so a large export never materializes the whole workbook; write numbers/dates as typed invariant cells (a date needs a `numFmt` style + the OADate value) so Excel formats them per the viewer's locale.

184. **To wrap exceptions inside a C# async iterator (`async IAsyncEnumerable<T>` with `yield`), keep every `yield` OUTSIDE any `try` that has a `catch` — put the risky `await` (ExecuteReaderAsync / ReadAsync) in its own `try/catch` with no yield inside, then `yield` the buffered result after the try.** C# forbids `yield` inside a try-with-catch, so you can't wrap the whole read loop; the idiom is: open the reader in a catch-wrapping try (no yield), then `while (true) { try { has = await reader.ReadAsync(ct); } catch (FbException ex) { throw new QueryExecutionException(...); } if (!has) break; ...; yield return row; }`. Validate arguments (empty SQL) in a non-iterator wrapper method that returns the iterator, so the throw is eager. Release the connection `CommandLock` in a `finally` around the whole iterator body (covers cancel + completion + the wrapped throw). `OperationCanceledException` propagates raw (the caller distinguishes cancel from error).

**Gotcha — promote to architecture lore.**

186. **Export the user's VIEW, not the internal model.** A grid that transforms its source before display (Activity Monitor strips trace `-------` separator lines via `CleanSql`; any cleaning/formatting/reshaping) must export from the SAME transformed representation the user sees on screen — never the raw parser/DTO the grid was built from. The export projection (`ProjectRow`) must read the same cleaned VM property the cell binds to (here `ObjectExportText`, which reuses `CleanSql` but drops the grid-width elision so the file gets the full text). If a display transform exists, there are two correct forms of it — the elided on-screen form and the full-fidelity export form — both derived from the same cleaner, never bypassed back to the raw input.

187. **A button/command gated on a COLLECTION-derived value (`Count`, `Any()`, `_items.Count > 0`, …) must have EVERY mutation path raise the matching `OnPropertyChanged`/`NotifyCanExecuteChanged` — correctly computing the property is not enough; the UI won't re-query it on its own.** This bit the Export button in FOUR places (Table Data, View Data, Activity Monitor, and each was the same shape): the `CanExport*` getter was right, but `IsEnabled="{Binding CanExport}"` (or a command `CanExecute`) is evaluated ONCE and only re-evaluated when a `PropertyChanged` for that name fires — so with no notification the button latches at its ctor-time value (usually `false`) forever. Two correct patterns: (a) if the gate derives from an `[ObservableProperty]` (e.g. `_dataResult`, `_currentResultVersionTag`, `_execResult`), put `[NotifyPropertyChangedFor(nameof(CanX))]` (+ `[NotifyCanExecuteChangedFor(nameof(XCommand))]` for a command) on that FIELD; (b) if the gate derives from a plain mutable collection (`_all.Count`), raise `OnPropertyChanged(nameof(CanX))` in the single choke point that already notifies the collection's other derived props (there was already a `TotalCount` raise sitting right next to the missing `CanExport` — co-locate them so the next collection-derived prop can't be forgotten). Treat this as a standing MVVM rule for all future modules: **any collection mutation → notify every state (property + command CanExecute) that reads that collection.** Diagnostic tell: "the feature works but the button is stuck disabled" ⇒ a missing notification, not broken logic.
