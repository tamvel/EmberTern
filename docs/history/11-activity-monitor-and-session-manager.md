**Gotcha — promote to architecture lore.**

169. **Kill trace noise at the SOURCE (the server event mask), not at the display.** On a real ERP the Firebird trace stream is dominated by `EXECUTE_FUNCTION` events for built-in scalar functions (MOD/BIN_AND/…) called thousands of times by the DB's own framework PSQL — not an EmberTern bug (IBExpert emits them too). A display-level filter still pays the full cost: the events flood the bounded ring buffer (→ 16k+, dropping the STATEMENTS you actually want) before you hide them. The right fix is to not request them: `FbDatabaseTraceConfiguration.Events` without `FunctionStart|FunctionFinish` (i.e. `TraceSessionConfig.IncludeFunctions = false`) so the server never sends them. A display filter is complementary, not a substitute — reserve it for the opt-in "functions ON" profiling case, and classify built-in-vs-user via the DB's `RDB$FUNCTIONS` catalog (never a hardcoded name list). Corollary: the trace event mask is fixed at session start — a toggle that changes it "applies on next Start", not live.

**Gotchas — promote to architecture lore.**

170. **A CommunityToolkit `[ObservableProperty]` field must not generate a property name that collides with a `[RelayCommand]` method name — CS0102 in the generated file.** `[ObservableProperty] private bool _showStatements;` generates `ShowStatements`, which collided with the existing `[RelayCommand] private void ShowStatements()` (the group-mode command method — the command wrapper is `ShowStatementsCommand`, but the *method* is `ShowStatements`). Symptom: `error CS0102: already contains a definition for 'ShowStatements'` pointing at the generated `.g.cs`. Rename the observable field so its property doesn't clash (here `_showStatementEvents` → `ShowStatementEvents`). Related: a `partial void OnXxxChanged` hook MUST use the parameter name `value` (CS8826 otherwise) — the generator emits `OnXxxChanged(value)`.

171. **Firebird trace ERROR events are `ERROR AT <function>` (multi-word) — a header regex of `[A-Z_]+` silently drops them, so errors never parse.** The trace event token is normally a single UPPER_SNAKE word (`EXECUTE_STATEMENT_FINISH`), but the `Errors` config flag emits `ERROR AT jrd8_execute` / `ERROR AT jrd8_prepare_statement` etc. A header pattern that only accepts `[A-Z_]+` fails to match those lines → the whole error block is skipped and no error ever surfaces (the downstream red-stripe/Detail/Errors-filter machinery looks broken but was never fed). Allow an optional `" AT .+"` tail in the header, capture the following status-vector lines (`-?\d+ : message`) as the error text (they also terminate SQL accumulation so the message doesn't pollute the SQL), and — since `MapKind("ERROR AT …")` returns System — derive the real kind (Statement/Procedure) in the folder from the block's SQL/object. Verify error handling end-to-end with a captured error block, not just the happy path.

### Activity Monitor — V1.1 direction (analysis; items ①②③⑤ SHIPPED, item ④ PLAN → V1.2)

**① Trace noise reduction — TOP PRIORITY.** Live streams are dominated by `EXECUTE_FUNCTION` events for Firebird **built-in scalar functions** (`MOD`, `BIN_AND`, `BIN_XOR`, `SIGN`, …) — the user's audit/framework PSQL (e.g. `XXX_WS_TRANS_ON_COMMIT` → `GET_NAGL_WERDYSP`, the same objects behind the earlier refresh-storm) calls them thousands of times. Confirmed NOT an EmberTern bug (Firebird Trace really emits them). An ERP reverse-engineer wants statements / procedures / **user** functions / triggers / errors / perf — never `MOD`. **Recommendation — two layers, both cheap:**
  - **(source-level, primary) Default the preset to NOT trace functions.** `TraceSessionConfig.IncludeFunctions` already exists (`FirebirdTraceService.BuildDatabaseEvents` gates `FunctionStart|FunctionFinish` on it) — flip `DefaultPreset.IncludeFunctions` to **false**. This removes the noise at the SOURCE, which ALSO fixes the real hazard the screenshots show: the ring buffer flooding to 16k+ events (mostly `MOD`) → on a big ERP action it drops the STATEMENTS you actually want. Add an **"Include function calls" toolbar toggle (default OFF)** that re-enables them (applies on next Start — a live session can't change its event mask) for when you're profiling a specific function.
  - **(display-level, secondary) "Hide built-in functions" filter (default ON), for when functions ARE captured.** Classify built-in vs user **authoritatively via the connected DB's `RDB$FUNCTIONS` catalog** (+ packaged funcs), loaded once at Start into a `HashSet` — a function event whose name isn't a user function = built-in = hidden. (Static FB-builtin name list only as a fallback when the catalog isn't loaded.) This DB-catalog approach is version-correct and avoids a hardcoded 200-name list. Surface a **"N system events hidden"** counter (like the dropped counter) so nothing is silently lost.
  - **DEFER the Business / Infrastructure / System tri-tier classification (option D).** It's the best long-term model but "Infrastructure" (the user's own audit framework: `XXX_WS_TRANS_ON_COMMIT`, `GET_NAGL_WERDYSP`) can't be auto-detected without user config/heuristics, and mis-classifying would hide real business logic. Revisit once (a) function noise is gone and (b) a config surface exists. For now: built-in-function suppression delivers ~95% of the benefit at ~5% of the risk.

**② Parameterized SQL → inlined values ("expanded SQL").** During reverse-engineering the user wants `… WHERE ID_NAGL = 10036`, not `… WHERE ID_NAGL = ?` + a separate `param0 = 10036`. Answers to the user's questions: **(a) Safe?** Yes — strictly **presentation-only** (we compute a display string from the already-parsed SQL + `RawTraceParam` list; we NEVER execute it), so SQL-injection is a non-issue; the only correctness concern is not substituting a `?` inside a string literal / quoted ident / comment, which `SqlScanHelpers` already handles. **(b) All param types?** No — clean for the common scalars (integer/bigint/numeric/varchar/date/time/timestamp/boolean/NULL); **BLOB/array params can't be inlined** (leave the `?` with a `/* BLOB */` marker). **(c) Limitations:** trace `MaxSQLLength` truncation (a truncated SQL can't be fully reconstructed → show source only); a `?`-count vs param-count mismatch (guard: only inline when they match, else fall back to source); expanded SQL is a *reading* aid, not a re-run guarantee (usually runnable, but don't promise it). **(d) Presentation-only?** Yes, entirely — pure Core `TraceSqlInliner.Inline(sql, parameters)` over `SqlScanHelpers`, unit-testable, no DB, no execution. **Recommendation: DO IT — one of the two highest-value V1.1 items.** UX: a **"Show values" toggle** on the detail SQL (default ON — that's what reverse-engineering wants), toggling back to the parameterized source; "Copy SQL" / "Open in SQL Editor" use the *expanded* form when values are shown. Keep the Parameters section as-is for reference.

**③ Grid review.** **Resize:** already works (Avalonia `DataGrid` per-column `CanUserResize` defaults true; only the band gutter is `False`). **Reorder:** currently off (`CanUserReorderColumns="False"`) — could enable, low risk. **Persistence:** not wired — **adopt the existing `GridLayoutBehavior` + `GridProfileStore`** (the same column order/width/visibility persistence used by 8 other grids via `UserSettings.GridProfiles`; keys by header string) with a `GridId="TraceEvents"`. Low-medium effort, reuse-not-rebuild. **Sorting — the "chronology is sacred" question. Recommendation: KEEP the main grid strictly chronological (no column sort — leave `CanUserSortColumns="False"`).** The "rank by cost" need is already served in the right place: the **Statements lens** ranks fingerprints by total/avg/max, and the **Slow chip** narrows to slow rows — that IS the sorted view, without breaking arrival order. Sorting the sacred grid by Duration/Reads would silently destroy the reconstruct-what-the-ERP-did guarantee. If a per-statement ranking within a single transaction is ever needed, add it as a **temporary, clearly-flagged view** ("Sorted by Duration ↓ — chronology paused · Restore"), never a silent reorder. Net: wire layout persistence + optional reorder; do NOT add grid sorting.

**④ Valuable data we parse but don't surface (filtered to real diagnostic value, per "not just because it exists").** Highest first:

## Database Activity Monitor (Trace) — ENGINE COMPLETE (M1+M2+M2.5) (2026-07-03, branch `feat/activity-monitor`)

**A fifth pillar** alongside SQL Editor · Metadata Explorer · Performance Analysis · Session Management. A live, real-time view of everything happening on the connected Firebird database, built on the server-side **Firebird Services Trace API**. This is a full diagnostic module (a Workspace tab with its own toolbar), NOT a helper window. **Status: design frozen; the complete headless engine is built + tested — Trace-API gate PASSED (M1), Timeline-ready model + `TraceLogParser` (M2), and the engine layer (M2.5): `Core.Diagnostics` lift, fingerprinter, grouper, bounded ring buffer, streaming accumulator, and `FirebirdTraceService`. `Trace API → Parser → Diagnostics Models → Fingerprinter → Grouper → Trace Service` is done. NO UI yet (deferred to M3 by design).** Extend this design, do not redesign it. (Results + next steps: see "M1", "M2", "M2.5", and "Continuity" below.)

### Why it exists (three user workflows)
1. **Reverse-engineering an ERP (primary).** Start monitoring → perform an action in the ERP (issue an invoice, save an order, change a status) → return to EmberTern → read the exact SQL / procedures / triggers / functions the ERP fired, in execution order, to reproduce the behaviour. This is the killer use case.
2. **Performance diagnosis.** Find slow statements/procedures, redundant/duplicate calls, N+1 patterns, ordered by cost.
3. **Error diagnosis.** Find which statement raised an error and the chain of events that led to it.

### The IBExpert anti-goals (what we deliberately do NOT copy)
- **No config matrix.** IBExpert opens a dialog with ~40 checkboxes before you can trace. EmberTern V1 = one button, one opinionated preset, it just works. (A config UI is V2, never V1.)
- **No 27-column firehose grid.** IBExpert shows Database/Charset/Role/IP/Transaction-params/… EmberTern curates to ~9 meaningful columns; the rest live in the detail panel / a V2 column chooser. `Database` is removed entirely — the tool already knows the connected DB.
- **No notepad-style text view.** IBExpert's text mode has no SQL colouring, no hierarchy, no grouping. EmberTern shows syntax-highlighted SQL + a call hierarchy + grouping/fingerprinting.
- **The differentiator over IBExpert: grouping.** A flat 5867-row chronological grid is what IBExpert gives. EmberTern groups by **transaction** (each `TRA_id` = a logical unit of work) and **fingerprints identical statements** (the 300 `SELECT … FROM KONFFIRMY WHERE NUMERPARAM=?` calls collapse to one row with count + total time), and reconstructs the **call hierarchy** (triggers/functions fired inside a statement shown as its children). This turns "5867 rows" into "here are the 12 operations, here's the one that's slow, here's the redundant call fired 300×".

### Load-bearing architectural distinction — Trace ≠ Performance Analysis
They look similar (both diagnostic, both show SQL + per-table reads + plans) but their **acquisition is fundamentally different and must NOT be merged:**
| Axis | Performance Analysis | Activity Monitor (Trace) |
|---|---|---|
| Subject | EmberTern's OWN executed statement | The WHOLE database — ALL attachments (the ERP process, other users) |
| Mechanism | own prepared command's explained plan + own-attachment MON$ read delta | server-side **Services Trace API** streaming text events |
| Privilege | none (any user sees own attachment) | **elevated** (SYSDBA, or a user with the trace right) — needed to see *other* processes |
| Lifecycle | one statement, on demand | continuous stream, thousands of events, start/pause/stop |
| Data source | structured driver API + `RDB$`/`MON$` catalog | a **text stream** that must be PARSED (same format as IBExpert's `trace.txt`) |

⇒ **Separate acquisition layers. Shared domain model.** See the shared-foundation decision below.

### Shared diagnostic foundation (the answer to "don't build a parallel metrics world")
Trace, Performance, and the roadmap's Sessions/Locks/Transactions/Debugger all describe the same underlying primitives. Introduce a small shared **`EmberTern.Core.Diagnostics`** namespace (lift the already-existing shared value types out of `Core.Performance`, keep them re-exported/aliased so Performance is untouched behaviourally):
- **`SqlStatementText`** — SQL + parameters + a `Fingerprint` (normalized text, params stripped) for dedup/grouping. (Trace parses it; Performance already has `StatementIdentity`.)
- **`TableAccessStat` / `TableAccessProfile`** — Natural/Index/Update/Insert/Delete/… per table. Trace's per-table block IS this shape; Performance already has it (`Core.Performance.PerformanceAccess`). One model, two producers.
- **`PlanTree`/`PlanNode`** — already in `Core.Performance`; a trace event may carry an explained plan → reuse verbatim.
- **The advisor (`IPerformanceRule` + rules R1–R6 + `Finding`/`Recommendation`)** — a slow *traced* statement can be fed to the SAME rule engine to explain WHY it's slow. This is the **"Analyze in Performance"** bridge: select a trace row → run its SQL through the existing advisor / open it in the SQL editor. No second advisor.
Consumers: `Core.Trace` (this module), `Core.Performance` (existing), future `Core.Sessions` / `Core.Locks`. **Rule going forward:** any new diagnostic module reuses `Core.Diagnostics` value types + the advisor; it never re-models a statement, a plan, or per-table reads.

### UX — one Workspace tab, three zones (mirrors the Performance panel's zone philosophy)
**Entry point:** a new main-toolbar button (activity/radar `SvgIcon`) in a **Monitoring** slot, placed after the connection group. Click → opens (or focuses) a Workspace tab of a new `WorkspaceTabKind.TraceMonitor` — exactly like `SecurityManager` (a full-tab module, keyed as a near-singleton per connection). ### Data model — `TraceEvent` (Core.Trace)
One record per parsed trace event. Curated from IBExpert's 27 columns:
**Default-visible grid columns (9):** `#` (seq) · `Time` (clock) · `Δ` (delta ms since previous) · `Event` (badge: Statement / Procedure / Trigger / Function / Error / System) · `Duration` (ms) · `Object` (elided SQL for statements; proc/trigger/function name for routines) · `Rows` (records fetched) · `Reads` (natural+index total, with a Natural-scan warning tint) · `Tx` (short `TRA_id`).
**Detail-only fields (parsed, not gridded by default):** full SQL text · parameters · statement plan · per-table access block · Writes · Fetches · Marks · Transaction params/isolation · Statement ID · Attachment ID · User · Role · Charset · IP · Process name · PID · Trigger table/event · Procedure name · Error text.
**Removed entirely:** `Database` (tool knows it).
**Derived/computed (the workflow layer):** `Fingerprint` (normalized SQL for dedup) · `ParentEventId` (trigger/function → owning statement, for the call hierarchy) · `IsSelfActivity` (matches EmberTern's own attachment ids) · `Severity` (Error > slow-threshold > normal).

**Event-type handling (they are NOT presented identically):**
- `EXECUTE_STATEMENT_FINISH` — the workhorse; one grid row.
- `*_START` + `*_FINISH` pairs (procedure/function/trigger) — **fold the pair into one row** (FINISH carries the duration; START is a marker, never its own row). When fired inside a statement, render as an indented **child** of the owning statement under grouping.
- `TRACE_INIT` / connection / transaction events — de-emphasized "system" rows (or a status strip), hidden from the default statement view.
- Errors — red badge, pinned, never filtered out.

### Architecture (design; NO implementation yet)
Follows the `App → Firebird → Core` one-way rule; Core stays Avalonia-free; readers isolate all `Fb*`.
- **`EmberTern.Core.Trace`** (pure): `TraceEvent` (record), `TraceEventKind` enum, `TraceSessionConfig` (the preset — a plain DTO, so V2 config is additive), `TraceLogParser` (the native trace **text → `TraceEvent`** parser — the heart; fully unit-testable against captured `trace.txt` fixtures, no live server), `TraceStatementFingerprinter` (normalize SQL → dedup key), `TraceEventGrouper` (chronological / by-transaction / by-fingerprint + parent-child hierarchy). **The parser is the load-bearing, highest-value-per-risk Core class.**
- **`EmberTern.Core.Diagnostics`** (pure, new shared): the lifted shared value types (`SqlStatementText`, `TableAccessStat`/`Profile`, and re-exported `PlanTree`) — see the shared-foundation section.
- **`EmberTern.Firebird`**: `FirebirdTraceService` — starts/stops/pauses a Services-API trace session on a dedicated service attachment, streams output lines via the driver's `ServiceOutput`-style callback into a bounded channel, resolves EmberTern's own attachment ids for self-exclusion, exposes trace-privilege detection + graceful degradation. Wraps driver exceptions in a domain `TraceException`. **One-way dependency preserved: it returns raw lines / Core DTOs, never Avalonia.**
- **`EmberTern.App`**: `WorkspaceTabKind.TraceMonitor` + `WorkspaceTabViewModel.CreateTraceMonitor(...)` factory (same pattern as `CreateSecurityManager`) + `TraceMonitorTabViewModel` (session lifecycle, the event `ObservableCollection` fed by a UI-thread batch pump, grouping/filter/follow-tail state, selected-event → detail) + row/detail child VMs (`TraceEventRowViewModel`, `TraceEventDetailViewModel` reusing the Performance access-bar VM + the SQL highlight) + `TraceMonitorTabView` (the 3-zone AXAML). ### ADR — Database Activity Monitor
1. **Acquire via the managed Services Trace API, NOT a shell-out to `fbtrace`/`fbsvcmgr`.** Rejected: spawning the native tool (reintroduces the `fbclient.dll` dependency EmberTern deliberately avoids + fragile process/stdout management). Consequence: a hard dependency on the managed provider exposing Services trace — the M1 gate. If M1 fails, reassess (managed-only is a product principle).
2. **Trace Monitor is a Workspace TAB, not a bottom-panel sub-tab (unlike Performance).** Rejected: bottom sub-tab (too cramped for a long-lived 5000-row live grid + detail + its own toolbar). It's a primary, full-screen, long-lived module like Security Manager.
3. **Separate acquisition from Performance; SHARE the domain model via `Core.Diagnostics`.** Rejected: (a) folding trace into Performance — wrong (different privilege/scope/lifecycle/data source); (b) a fully parallel model — duplicates TableAccess/Plan/Statement and forks the advisor. Consequence: a small, behaviour-preserving lift of shared value types out of `Core.Performance`.
4. **V1 ships ONE opinionated preset, no config UI.** Rejected: exposing IBExpert's config matrix (the explicit anti-goal). The preset: statement-finish + procedure/function/trigger finish + errors + perf/per-table + exclude self, threshold 0. Config editing is V2.
5. **Bounded ring buffer, drop-oldest, with a visible dropped counter.** Rejected: unbounded (OOM on a busy ERP DB) and blocking backpressure (stalls the trace service / server). Honesty over silent loss — the dropped counter is surfaced.
6. **Exclude EmberTern's own attachment(s) by default** (resolve own `CURRENT_CONNECTION` ids for lanes #1/#2). Rationale: the point is watching OTHER processes; self-noise (incl. our own metadata reads) drowns the signal — and the user's ERP audit-commit trigger would flood it.
7. **Grouping + fingerprinting + call hierarchy is THE differentiator** over IBExpert's flat grid — it's the workflow-quality win, not a nice-to-have.
8. **ONE Timeline-ready event model behind three views (Grid · Call Tree · Timeline).** `TraceEvent` carries a span (`StartTime`/`EndTime`/`Duration` → computed `SpanEnd`) and a hierarchy link (`ParentEventId`/`Depth`) from day one, so a future Chrome-DevTools/SQL-Profiler-style Timeline is a *new view on the same model*, never a model migration. Rejected: a grid-only model with timeline fields bolted on later (would force a breaking model change + re-parse). Timeline is NOT built now — only its data prerequisites are frozen into the model.

### M1 — VERIFICATION RESULT (2026-07-03) — GATE PASSED (reflection); Core model built
**Trace-API gate: PASSED.** Reflection over the referenced `FirebirdSql.Data.FirebirdClient` **10.3.4** assembly (via a net9 `MetadataLoadContext`-style probe — Windows PowerShell 5.1 can't load a net9 DLL) confirms the managed Services Trace API exists and fits EmberTern (managed wire, **no `fbclient.dll`, no `fbtrace.exe`**):

### M2 — PARSER (2026-07-03) — the module's most critical class, built + tested against real captures
Parser-first, on byte-exact real ERP trace snippets (not idealised strings). Two Core types + the parser, all in [src/EmberTern.Core/Trace/](src/EmberTern.Core/Trace/):
- **`RawTraceRecord`** (+ `RawTraceParam`, `RawTableRead`) — a faithful, loss-free parse of ONE raw trace block (a `*_START` and its `*_FINISH` are two separate records). The detail-panel source of truth: attachment (ATT/user/role/charset/addr), process, transaction (TRA/params), statement id + SQL, object name, trigger event, input params + function return values, records/duration/page-reads/writes/fetches/marks, and the **per-table access block** (`RawTableRead`: Natural/Indexed/Update/Insert/Delete/Backout/Purge/Expunge + `RecordReads`). Error text is best-effort (no real error event was in the capture — see gaps).
- **`TraceLogParser`** (pure, static, stateless-per-call): `ParseRecords(text) → RawTraceRecord[]` (faithful) and `Parse(text[, selfAttachmentIds]) → TraceEvent[]` (the curated pipeline the user drew: `trace.txt → parser → TraceEvent`). Design:
  - **Header-anchored block splitting** (`^TS (pid:token) EVENT$`) — tolerates the `IBE>` config preamble, banners, and mid-stream trace-infra junk (the "Error creating trace session…" lines) by discarding anything not under a header.
  - Line state-machine body parse: attachment / process / tx lines; `Statement N:` + `-----`(skipped) + **multi-line SQL** (terminates at the first param/records/perf/table line — handles SQL directly followed by `records fetched` with no blank line); `Procedure/Function/Trigger` headers; `paramN = type, "val"` (`<NULL>`→null) split into inputs vs `returns:`; `N records fetched`; the perf line `N ms[, R read(s)][, W write(s)][, F fetch(es)][, M mark(s)]`; and the **whitespace-sensitive per-table block parsed by header-word end offsets** (numbers are right-aligned under their column, so a lone `1` lands in Index vs Natural correctly — the KONFFIRMY-indexed vs FILTRDEF-natural distinction is regression-pinned).
  - **START/FINISH folding**: a per-(ContextToken + kind) LIFO stack pairs a `*_START` with its `*_FINISH`; the FINISH becomes the one `TraceEvent` (authoritative result/duration), the START supplies the span begin. Statement/trigger are FINISH-only → emitted directly (span = timestamp − duration). Dangling STARTs are dropped.
  - **Foundation, not completed** (per the M2 brief): the parser does NOT compute the call hierarchy or fingerprints — it only *preserves their inputs* (`ContextToken`, `TransactionId`, arrival order) so those later passes need no re-parse. "Slow" severity is a UI/session concern; the parser sets only Error/System/Normal.
- Timestamp parsed offset-0 (stream has no tz) for deterministic deltas; CRLF/LF tolerant.
- **Tests** ([TraceLogParserTests.cs](tests/EmberTern.Tests/TraceLogParserTests.cs), +15) run against real snippets in `tests/EmberTern.Tests/Fixtures/Trace/*.trace` (statement+per-table, multi-line-SQL-natural-scan, procedure pair, function pair with returns+`<NULL>`, trigger, preamble+junk, mixed sequence): faithful field extraction, offset-based per-table columns, folding, self-activity flagging, monotonic sequence/delta, ContextToken preserved, empty/headerless → nothing. **Build 0/0, 23/23 trace tests green** (8 model + 15 parser).
- **Second consumer for the `Core.Diagnostics` lift is now IDENTIFIED but NOT yet lifted:** `RawTableRead` (Natural/Indexed record reads) is the exact shape of Performance's per-table `TableAccessStat`. Per the "no abstraction before the second consumer / do the lift only when it exists — not earlier" rule, the lift is the next deliberate step, done as its own change with the parser + Performance both compiling against the shared type. Not done in the parser milestone to keep the critical class focused.
- **Known gaps (documented, honest):** (a) no real ERROR-event fixture in the capture → error parsing is best-effort and needs a real error trace to harden; (b) only ONE Firebird version's text format was captured (gds32/FB-era) → the parser is written tolerantly (optional fields, header-anchored) but multi-version fixtures (FB 2.5 vs 3/4/5) should still be gathered; (c) statement→trigger association (a trigger fired by a FINISH-only statement) is NOT reconstructed — the model supports it (`ParentEventId`/`Depth`) but it needs a later heuristic pass (same-tx + adjacency), out of scope for the parser.

## Session Manager V1 — COMPLETE (M1–M4 + final polish, branch `feat/session-manager`, merged to `master` 2026-07-05)

A **sixth pillar** alongside SQL Editor · Metadata Explorer · Performance Analysis · Activity Monitor. This is the "Diagnostics Center → Sessions/Transactions" the Activity Monitor roadmap named. It is a live, **diagnose-first** view of database attachments + transactions built on `MON$*`, deliberately **complementary** to Activity Monitor (which is SQL/statement/trace-centric): Session Manager is **attachment + transaction + health** centric. **Do not merge the two — separate acquisition, shared `Core.Diagnostics` model, reuse of the Performance verdict/finding patterns and the Activity Monitor shell.** Design frozen below; extend it, do not redesign.

**The founding thesis (do not water down):** this is a *health* tool, not a `MON$ATTACHMENTS` grid viewer. The differentiator over IBExpert / the ERP admin panel is that EmberTern **does the diagnosis** — it names *which session is problematic*, *which transaction blocks garbage collection*, and *which user generates the most load* — using the same measured-first, scale-before-alarm, investigation-oriented language the Performance advisor and Activity Monitor already ship. The single most important computed signal is the **transaction gap (OIT/OAT/OST)**: in Firebird, garbage collection and record-version bloat are governed by the **Oldest Active Transaction**; one long-lived snapshot transaction pins the OAT and blocks GC of every record version created since, while everything "looks fine." Session Manager surfaces that.

### V1 scope (one sprint — rides existing infrastructure)
- **A separate `WorkspaceTabKind.SessionManager` module** next to Activity Monitor (near-singleton per connection, gated on `IsConnected`, **not persisted** — wiring mirrors `CreateSecurityManager`/`CreateTraceMonitor` exactly).
- **The Activity Monitor 3-zone shell**, reused 1:1: toolbar → grid → splitter-resizable / collapsible / double-click-maximize bottom-tab panel (the `ToggleResultsMaximized` code-behind pattern).
- **Health Bar** (above the grid): verdict dot + word + clickable counters (Sessions · Transactions · ⚠ Long Tx · ☣ GC Risk · 🔥 Heavy · OIT→OAT gap). Each counter is a filter chip (symptom → culprit in one click). Reuses the Performance **verdict** concept (`VerdictViewModel` shape) — worst active finding drives the dot.
- **Sessions Grid** (sortable — sorting by risk/load is the point, unlike the sacred trace grid). Default ~10 columns: ● Risk stripe · ID · User · Application · Host · State · Idle · Active Tx · Oldest Tx age · Load.
- **Bottom tabs:** `[Transactions] [Session Details] [Warnings]` (+ **no** Locks tab in V1 — see Deferred). Selecting a session **auto-filters** Transactions (the "Filtered by session N ✕" chip, like Activity Monitor). Double-click session → Session Details; double-click transaction → Session Details scrolled to its Transactions row with the "Why it matters" block expanded (**no separate Transaction Details window in V1**).
- **Transactions Grid** default ~8 columns: ● Impact stripe · Tx ID · Session (hidden when filtered) · State · Age · Isolation (decoded to words) · Read Only · GC Impact (the `newestTxId − thisTxId` gap count — one honest number).
- **Three health detectors** (each a `SessionHealthFinding`, Performance-`Finding`-shaped): **(A) Long-Running Transaction** — age > threshold AND (`isolation = Snapshot` OR it holds the OAT); **(B) Garbage-Collection Risk** — the transaction(s) pinning the OAT, with the blocked-GC gap count as impact; **(C) Heavy User** — surfaced ONLY as the Health-Bar counter + a 🔥 mark on the top-Load session row (**not** a Warning card — keeps detector count at two cards).
- **Warnings tab:** flat accordion cards (severity icon only, **no confidence label in V1**), Explanation / Evidence / Impact / What-to-check / Actions. Clean state = one green `✓ No health issues detected`. Investigation language, never imperative.
- **Administrative actions** (Firebird-accurate): **Cancel Statement** = `DELETE FROM MON$STATEMENTS WHERE MON$STATEMENT_ID = ?` (soft — interrupts the SQL, keeps the connection); **Disconnect / Kill Session** = `DELETE FROM MON$ATTACHMENTS WHERE MON$ATTACHMENT_ID = ?` (hard — its work rolls back). Both run via `FirebirdConnectionService.ExecuteAdminBatchAsync` (autonomous per-statement attachment, auto-commit) and go through the existing `ConfirmDialog` (`IsDestructive`, target named). Plus **Copy** (shared clipboard channel) and **Analyze** (bridge the session's current statement into Performance / SQL Editor). **There is deliberately NO "Kill Transaction"** — Firebird has no such command; the honest mapping is Cancel Statement (if active) or Disconnect Session.
- **Session Details** (in the bottom panel, not a modal): General (identity + one-line verdict) · Current statement (syntax-highlighted via the Firebird XSHD + Analyze/Open-in-SQL-Editor bridges) · Transactions (its rows, with full OIT/OAT/snapshot + the plain-language **"Why it matters"** GC-impact block) · Activity (two lines of snapshot totals — reads seq/idx, ins/upd/del) · Warnings scoped to the session.
- **Correctness rules (non-negotiable):** every refresh is a **fresh short read tx on the metadata lane** (MON$ snapshot rule — a long-lived reader silently freezes the view); **self-exclusion** default-ON toggle (EmberTern's own data + metadata attachments carry a "self" chip); a **privilege banner** when the view is self-only (a non-SYSDBA / non-`MONITOR ANY ATTACHMENT` user sees only their own attachments in `MON$`).

### Deferred V2 features (explicitly OUT of V1 — do not build now; each with WHY)
All V2 must extend this design on the same `Core.Diagnostics` foundation.
- **Heavy-user detection** — needs an **inter-poll activity RATE** (delta of `MON$RECORD_STATS` between two snapshots). V1 has only a single snapshot, so the available number is the CUMULATIVE total since connect, which misleadingly flags a long-lived idle session as "heavy" (caught in live smoke → removed from V1). Revive together with the rate/sparkline infra. The `Load` column stays as an honest lifetime total meanwhile.
- **Cancel Statement** (`DELETE FROM MON$STATEMENTS`) — cut because it's Firebird-internals-y and easy for an admin to misread as safe when it can abort someone's in-flight work; **Disconnect** is the one clear, well-understood V1 action. The reader method `CancelStatementAsync` is kept dormant (+ its unit test) for a V2 revival with clearer framing.
- **Locks tab** — Firebird `MON$` has **no clean lock table**; lock ownership/waits live in the lock manager (lock print), so a real blocking/blocked graph is its own acquisition module, not a `MON$` view. Deferred rather than shipped half-built. (A lightweight "Waiting" indicator derived from `MON$STATEMENTS` state is the most V1 could have done; we shipped nothing rather than a misleading partial.)
- **Watch mode** (pin a session so it stays visible across refreshes/sort/filter) — pure convenience; not needed to diagnose. Adds selection/pinning state to every rebuild; defer until there's demand.
- **Batch session operations** (e.g. disconnect all idle sessions of a user/app via the batch-results dialog) — powerful but higher-blast-radius; V1 keeps admin actions to one session at a time (deliberate, safe). The batch-results dialog is reusable when it lands.
- **Historical trend analysis** — sparklines, per-second rates, the gap-timeline **over time**, regression/anomaly detection. All require retaining snapshot history (a store + a time axis) — a genuinely separate capability. V1 is strictly a live single-snapshot view.
- Also deferred: elaborate **scoring systems + confidence levels** on the detectors (V1 uses a simple 🔴/🟠 severity, no ranking math) · advanced/historical **statistics** panels · a separate **Transaction Details** window (folded into Session Details in V1) · **column chooser / saved sessions / config presets**.

### Architecture decisions (frozen)
- **Layering** obeys the existing rules: **Core** (`EmberTern.Core.Diagnostics`, zero Avalonia / zero `Fb*`) holds `SessionInfo`, `TransactionInfo`, `SessionHealthFinding` + `SessionHealthKind`/`SessionHealthSeverity`, and the pure detectors (`SessionHealthAnalyzer` over small rule functions; **not** an `IPerformanceRule`-style interface unless a 2nd impl appears — two detectors + one heavy-user marker don't justify it, but keep them as separate pure methods so a rule interface is a cheap later lift). **Firebird** (`FirebirdSessionReader`) does all `MON$` acquisition, returns Core DTOs, holds all `Fb*`. **App** hosts the tab + VMs + view.
- **Reuse, do not rebuild:** `FirebirdDiagnostics` already reads `MON$TRANSACTIONS` + `MON$ATTACHMENTS` with `DecodeIsolationMode`/`DecodeTransactionState`/`DecodeAttachmentState`/`DecodeLockTimeout` — `FirebirdSessionReader` follows its exact access pattern (metadata lane, **capture the command lock once** — gotcha #120, attach to `_transactionService?.ActiveTransaction` or run implicit) and extends the SELECT set (add `MON$USER`/`MON$ROLE`/`MON$REMOTE_PROCESS`/`MON$REMOTE_ADDRESS`/`MON$TIMESTAMP`/`MON$GARBAGE_COLLECTION`/`MON$STATE`, `MON$STATEMENTS.MON$SQL_TEXT` for the current statement, `MON$RECORD_STATS` for Load, `MON$TRANSACTIONS.MON$TIMESTAMP`/`MON$OLDEST_TRANSACTION`/`MON$OLDEST_ACTIVE`/`MON$SNAPSHOT_NUMBER`). The MON$-snapshot-per-poll discipline is already proven in `FirebirdPerfStatsReader`. Kill/cancel reuse `ExecuteAdminBatchAsync`. The health cards reuse the `FindingViewModel` shape; the verdict reuses the `VerdictViewModel` shape. The grids reuse the shared DataGrid framework + `GridLayoutBehavior`; icons use `SvgIcon`/`IconBrushConverter`; colors are theme tokens only.
- **`MON$` semantics baked in:** `MON$ISOLATION_MODE` 0=consistency 1=concurrency(snapshot) 2=read-committed rec_version 3=no_rec_version 4=read_consistency; `MON$STATE` 0=idle 1=active; killing = `DELETE FROM MON$ATTACHMENTS`; cancelling = `DELETE FROM MON$STATEMENTS` (FB 2.5+); there is no per-attachment CPU counter (label any load proxy **Load**, not CPU — honesty, like the Performance "reads heatmap not cost heatmap").
- **No new infrastructure.** No new dialog framework (reuse `ConfirmDialog`), no new grid, no new toolbar pattern, no parallel metrics world. Same test discipline: Core detectors + reader SQL shape are unit-pinned; the live `MON$` read + kill/cancel are the user's manual smoke (privileged login, like the FbTrace path).

### UX decisions (frozen)
- **Diagnose-first, four principles** (inherited from Performance + Activity Monitor): (1) answer at the top (Health Bar verdict), rows at the bottom; (2) **scale before alarm** — never a magnitude without its scale (age alone is not a finding; age + snapshot + is-OAT + gap count is); (3) **one selection model** across the window (session → filters transactions, lights warnings, scopes details); (4) **honesty chips + investigation language** (self chip, privilege banner, "Cancel Statement vs Disconnect" truth, "no Kill Transaction", "Load not CPU"; warnings read "investigate…").
- **Reject the ERP right-side narrow transaction panel** (the user's explicit complaint): transactions live in a full-width bottom tab, auto-filtered by session — comparison-friendly, resizable, exactly the Activity Monitor layout.
- **Readability over density:** ~10 session columns + ~8 transaction columns by default; everything else → Session Details / (future) column chooser. Heavy-user stays a counter + a 🔥 row mark, not a third warning type, to keep the surface calm.

### Session Manager — MON$ poll failed after a SQL-Editor execute (bugfix, shipped 2026-07-05)

Live-found regression: after executing any query in the SQL Editor, opening the Session Manager showed **Sessions 0 / Transactions 0** and the status *"Execute requires the Command object to have a Transaction object when the Connection object assigned to the command is in a pending local transaction."*

**Root cause.** `FirebirdSessionReader` hardcoded `cmd.Transaction = null` on every read, and the poll's FIRST step — `GetOwnAttachmentIdsAsync` → `ReadCurrentConnectionAsync(ConnectionRole.Data)` — runs `SELECT CURRENT_CONNECTION` on the **Data** connection to identify EmberTern's own attachment. A SQL-Editor execute auto-begins the data working transaction (never autocommitted), so the data connection has a **pending local transaction** — and FirebirdClient rejects a null-transaction command there. The exception aborted the whole poll (hence 0/0). Every other reader avoids this by borrowing `_transactionService?.ActiveTransaction`; `FirebirdSessionReader` was written without a `TransactionService` (an M2 oversight — it assumed `cmd.Transaction = null` always works).

**Fix.** The reader now takes the data + metadata `TransactionService`s and sets `cmd.Transaction = TxFor(role)` (a pure `SelectTransactionService(role, data, metadata)` router) on every read. The common case is unchanged: the metadata lane has no working tx → `TxFor(Metadata)` is null → an implicit per-command tx → a **fresh MON$ snapshot each poll** (the snapshot rule holds). Only the data-lane id read now attaches to the pending data tx (the attachment id is transaction-invariant, so this is safe and side-effect-free). Degraded single-connection mode is covered too — the metadata service forwards to the data service, so its `ActiveTransaction` is the data tx. Regression-pinned by `SelectTransactionService_RoutesEachLaneToItsOwnService` (offline routing pin; the live MON$ read stays the user's manual smoke, per the module convention). **2481 → 2482 main + 9 probe green**, build 0/0, smoke clean.

**Gotcha — promote to architecture lore.**

173. **A reader must NEVER hardcode `cmd.Transaction = null` — always borrow the lane's working transaction (`TxFor(role)` / `_transactionService?.ActiveTransaction`).** `cmd.Transaction = null` runs in an implicit per-command transaction ONLY when the connection has no pending local transaction; if it does (the DATA connection always does after a SQL-Editor execute auto-begins the working tx, since there's no autocommit), FirebirdClient throws *"Execute requires the Command object to have a Transaction object when the Connection object assigned to the command is in a pending local transaction."* This is the read-side mirror of gotcha #22-revised: attach to the active working tx when the connection has one (null only when it genuinely doesn't). For a MON$/CURRENT_CONNECTION read this is still correct — the metadata lane normally has no working tx so `TxFor` is null → a fresh snapshot; the only read that hits the pending-tx data connection is the self-attachment-id lookup, and an attachment id is transaction-invariant. Any new reader that touches the shared connection with `cmd.Transaction = null` is a latent crash the moment the user has an open transaction.
