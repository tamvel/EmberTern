### Refresh storm — root cause + fix + the rule (do not violate)
- **Root cause:** after a transaction settle, `MainWindowViewModel.OnTransactionStateChanged` ran a **blanket refresh of ALL open TableDetail tabs** (`foreach (WorkspaceTabs) RefreshAfterTransactionAsync()`), each tab triggering ~7 heavy `RDB$` structure queries. On a DB with an `ON TRANSACTION_COMMIT` trigger, every implicit-tx commit re-fired the trigger → a transaction storm over tabs unrelated to the action.
- **Fix:** **object-scoped refresh only** — a pure `SelectRefreshTargets` selector. Metadata rollback → only the **active** TableDetail tab; data rollback → only tabs with **pending data edits**; commit → nothing. Plus a `_postTxRefreshInFlight` re-entrancy guard.
- **gotcha #119 remains load-bearing and must not be violated.** **Never iterate all open workspace tabs and refresh metadata after a transaction settle. Refresh only the object affected by the originating action.**

### Issue #1 — Procedure lock after Execute → Rollback → Compile
- **Status:** OPEN — needs investigation in a future session.
- The **refresh storm (#119) is FIXED** — metadata refresh of unrelated tabs no longer occurs, and the trace spam is gone.
- **However**, the sequence Execute Procedure → Rollback → Compile can **still** produce an `"object … is in use"` lock.
- **Important:** the original diagnosis was incomplete. The refresh storm and the procedure lock are **two separate issues**. The refresh storm is solved; the remaining lock is a distinct problem still to be root-caused. **Do NOT revisit the already-solved refresh problem when investigating this** — start fresh on the lock itself (likely a transaction still holding the procedure "in use" at Compile time; `EMBERTERN_TX_DIAG=1` dumps MON$TRANSACTIONS ⋈ MON$ATTACHMENTS on an in-use DDL failure — gotcha #118).
- **Audit update (2026-06-18, R2 — see the Transaction Architecture Audit section below):** the Execute→Rollback→Compile path was traced end-to-end in code. Procedure Execute runs `SELECT * FROM proc(...)` / `EXECUTE PROCEDURE` on the **Data lane** (`_executor`), leaving the **Data working tx Active and referencing the proc** (no autocommit). The unified Rollback (`RollbackAllAsync` → `DecideRollbackLanes` → `RollbackLaneAsync` → `TransactionService.RollbackAsync`) genuinely ends + disposes that Data tx ([TransactionService.cs:244](src/EmberTern.Firebird/TransactionService.cs)). So in the clean path the proc-holder is released and Compile *should* succeed. Compile runs `ALTER PROCEDURE` via `_ddlExecutor` → `FirebirdConnectionService.ExecuteAutonomousAsync` on a **third, transient attachment** → so the engine's metadata in-use check is **always cross-attachment** (gotcha #118). Because the rolled-back Data tx is provably gone, the residual holder must be one of: (a) a **metadata working tx still open** (only begun by a prior raw F5 of a DDL/DCL statement in the SQL editor, which routes to `_metadataExecutor` and auto-begins the metadata working tx that proc-reads then attach to); (b) an **in-flight implicit metadata read of the proc on attachment #2 racing the ALTER**; (c) **engine-level OAT/OIT lag** under rec_version read-committed when the fresh transient attachment computes its snapshot. Static analysis **cannot** disambiguate these — **the next step is to capture the live MON$ dump** (procedure recorded in the audit section). NO architecture/lock change until that dump names the attachment + transaction.

## Transaction Architecture Audit (2026-06-18)

Audit-first review of the whole transaction subsystem, prompted by the same class of problem recurring under different symptoms (refresh storms, object-in-use locks, compile/apply regressions, ownership confusion). Deliverables were architecture summary + transaction matrix + lock analysis + risk assessment + remediation plan. Outcome: **one confirmed bug fixed now (R1); two issues root-caused but NOT yet code-changed (R2 awaits live MON$ evidence; R3 cleanup deferred per decision above).**

**Three coexisting transaction mechanisms (the umbrella cause of the recurring symptoms):**
1. **Data working tx** (`_transactionService`, connection #1) — SQL F5 of DML/SELECT, Dane inline edits, Procedure Execute. Auto-begin, never autocommit, user Commit/Rollback.
2. **Metadata working tx** (`_metadataTransactionService`, connection #2) — now begun **only** by a raw F5 of a DDL/DCL statement in the SQL editor (`_metadataExecutor`). Post-Phase-A it is otherwise **vestigial**. Metadata browsing attaches to it when active, else uses implicit per-command read tx.
3. **Autonomous transient tx** (`FirebirdConnectionService.ExecuteAutonomousAsync`, a throwaway 3rd attachment) — **every** structural DDL + View/Procedure Compile + New Table/View/Proc. One begin→batch→commit, auto-committed. `ExecuteAdminBatchAsync` is the per-statement-autocommit sibling (SET STATISTICS).

**Readers never open their own tx** (gotcha #22-revised) — verified across all readers (`cmd.Transaction = laneTx-or-null`). Lane/connection plumbing (two connections, two command locks, role resolution, degraded-mode aliasing, `TransactionService` delegation) verified correct. `ExecuteAutonomousAsync` acquires neither command lock (independent at the lock level; can still contend at the server in-use level — that's R2).

### R1 — command-lock leak in `FirebirdTableDetailReader` (CONFIRMED, FIXED this session)
All 10 read methods (8 Metadata-lane: Fields/Indexes/Constraints/Description/ProcedureDescription/ProcedureParameters/ProcedureDependencies/Dependencies; 2 Data-lane: GetDataPreviewAsync/GetRowCountAsync) called `MetaLock()`/`DataLock()` **twice** — once at `WaitAsync`, again at `Release()` in `finally`. `MetaLock()` resolves through `MetadataIsIndependent`, which can flip mid-call (metadata attachment drops / degraded mode). Re-evaluating at Release then releases a **different** `SemaphoreSlim` than was acquired → the held one **leaks permanently** (and the other is over-released, corrupting its count upward → later allows concurrent commands on the data connection). Both semaphores live on the long-lived `FirebirdConnectionService`, so a leak **survives reconnect; only a process restart clears it** — a prime suspect for the "metadata corrupted / only restart helps" symptom family. This **violated the already-documented gotcha #98 fix**, which had been applied only to `FirebirdMetadataReader` / `FirebirdDdlReader` / `FirebirdDiagnostics` — `FirebirdTableDetailReader` (the most-used reader) was missed. **Fix:** capture `var commandLock = MetaLock();` / `DataLock();` once before `WaitAsync` and release that captured variable, exactly like the other readers. 1274/1274 tests still green; build clean.

### R2 — Issue #1 procedure-lock (OPEN — awaiting live MON$ evidence; see Known Open Issues #1 above)
Cross-attachment in-use from the autonomous-3rd-attachment Compile design. Root cause cannot be proven statically. **Diagnostic procedure (run on the live FB5 DB; nothing else changes until this is captured):**
1. **Enable diagnostics:** set the environment variable `EMBERTERN_TX_DIAG=1` for the EmberTern process (any non-empty value works — the code only checks `GetEnvironmentVariable("EMBERTERN_TX_DIAG") is null`). E.g. in the launching shell: `$env:EMBERTERN_TX_DIAG=1` then run `src\EmberTern.App\bin\Debug\net9.0\EmberTern.exe`, or set it as a user env var and relaunch. It must be set **before** EmberTern starts.
2. **Reproduce:** connect → open a procedure → **Execute** it (fill params, run) → click the unified **Rollback** → click **Compile**. Trigger the `"object … is in use"` failure.
3. **Find the log:** `%TEMP%\EmberTern-debug.log` — on this machine `C:\Users\grzegorz.gronski\AppData\Local\Temp\EmberTern-debug.log`.
4. **What to send back:** the **last** block beginning `DDL-IN-USE failure:` through the end of its `--- active MON$TRANSACTIONS ... ---` list (the indented `tx=… att=… state=… isolation=… user=… process=…` lines), **plus** all `TX-BEGIN tx=… isolation=[…] lock=[…] readOnly=…` lines from the same run (so we can see what the Data/Metadata lanes began).
5. **How to recognize the right capture:** (a) a `DDL-IN-USE failure:` line is present (the ALTER really failed in-use, not some other error); (b) in the MON$TRANSACTIONS list there is ≥1 row with `state=1` (active) on an attachment whose `process` is EmberTern's own exe **other than** the transient diagnostic connection issuing the dump — that row's `att`/`tx` is the holder. Decode: `state` 1=active/0=idle; `isolation` 0=consistency, 1=concurrency(snapshot), 2=read_committed rec_version, 3=read_committed no_rec_version, 4=read_committed read_consistency. The holding `att` tells the lane — cross-check against the `TX-BEGIN` lines and the title-bar Data/Meta chips. If the only active rows are the transient dump connection itself, capture again (we missed the window). **Once the holder is named, the fix is selected: route Compile through the metadata working connection instead of a 3rd attachment (if a metadata-lane/implicit-read holds it), or settle/serialize the Data lane before DDL (if the Data tx or engine-lag holds it).**

Decision recorded: keep apply-immediately + auto-commit uniformly for all metadata objects; transactions for data only. Remove the dead staged-Compile machinery in a future session.

### gotcha #119 as the canonical "excess-refresh" lesson (verified still in force)
The refresh-storm fix is intact and is the reference example of this whole problem class: **never blanket-refresh open tabs after a transaction settle — scope refresh to the object actually touched.** A COMMIT triggers **no** refresh (`DecidePostTransactionRefresh` → `None`); only a ROLLBACK refreshes, and only the active tab (metadata) or tabs with pending data edits (data), via `SelectRefreshTargets` (no `foreach (WorkspaceTabs)` blanket reload), guarded by `_postTxRefreshInFlight` + per-tab `_refreshInFlight`. Excess refreshing is what amplified earlier symptoms (each refresh = ~7 implicit-tx RDB$ reads × N tabs, each commit re-firing the user's `ON TRANSACTION_COMMIT` audit trigger). Treat any new "refresh after X" code against this gotcha.

### gotcha — promote to architecture lore

120. **A lane-resolving lock accessor (`MetaLock()`/`DataLock()`/`LaneLock()`) MUST be captured into a local ONCE per acquire/release pair — never re-invoked at `Release()`.** These accessors resolve through `MetadataIsIndependent`, which can flip mid-call (metadata attachment drops, degraded-mode aliasing engages). If `Release()` re-invokes the accessor it can target a *different* `SemaphoreSlim` than `WaitAsync` acquired, permanently leaking the held one (it lives on the long-lived connection service → survives reconnect, only a process restart clears it) and over-releasing the other (count corruption → later concurrent commands on one connection). This is the same defect as gotcha #98; R1 of the 2026-06-18 audit found `FirebirdTableDetailReader` had been missed by the original #98 fix. **Rule:** `var commandLock = MetaLock(); await commandLock.WaitAsync(ct); try { … } finally { commandLock.Release(); }`. Audit every reader/executor that does `await Something().WaitAsync(...)` to confirm the `Release()` targets the captured variable, not a re-evaluated call.

### Table Designer — buffered model restored (shipped 2026-06-18, commit `7e17061`)

Priority-1 regression fix: the structure designer is **buffered** again — *edit the working model → ⚡ Compile/Apply → auto-commit* — NOT *edit → immediate ALTER TABLE*. Code objects (views/procedures/functions/triggers/packages) are unchanged (*edit → Compile → auto-commit*). **1274 → 1284 tests** (+10). Build clean (0/0), all green. This does NOT touch the C2 lanes / locks / transaction architecture (Issue B stays parked on MON$ evidence) — it's a VM + grid-projection change only.

**What broke it (git-confirmed).** `47b1c75` (2026-06-12) made the Pola toolbar ops execute DDL immediately; `3729fb9` (Phase A) routed `FirebirdDdlExecutor.ExecuteAsync` → autonomous auto-commit. Net: every structural op auto-committed on click, and the `PendingChanges`/`CompileAsync` scaffolding was fed only by the test-only `AddMovePending` + (inconsistently) inline edits, so the Compile button was dead. The model was *half-buffered* (inline cell edits queued; toolbar ops didn't) — the inconsistency the user hit.

**The restored model.**
- **No structural op runs DDL.** Every `Execute*Async` (`ExecuteAddFieldAsync` / `ExecuteDropFieldAsync` / `ExecuteMoveAsync` / `ExecuteEditFieldAsync` / `ExecuteCreateForeignKeyAsync` / `ExecuteAdd{PrimaryKey,Unique,Check}Async` / `ExecuteDropConstraintAsync` / `ExecuteAddIndexAsync` / `ExecuteDropIndexAsync` / `SaveDescriptionCoreAsync`) now QUEUES a `PendingDdlChange` and mutates the in-memory working model — it no longer calls `_ddlExecutor.ExecuteAsync` or `RefreshStructureAsync`. The ONLY structural-DDL execution site left in `TableDetailTabViewModel` is `CompileAsync`. (Verified by grep: the sole other executor call is `RecomputeStatisticsForAsync` → `ExecuteAutonomousBatchAsync`, which is admin `SET STATISTICS` maintenance, not a structure edit — deliberately left immediate/auto-commit.)
- **Grids reflect the working model, not the catalog.** Pola: a pending-Added field appears as a new row, a Dropped field stays visible + tinted, an edited field shows new values; via `FieldRowViewModel.PendingKind` (new `[ObservableProperty]`) projected onto `EditableFields`. Ograniczenia/Indeksy: pending-Added rows are inserted, Dropped rows marked; via a new settable `PendingChangeKind PendingState` on Core `ConstraintInfo`/`IndexInfo`. Dropping a not-yet-compiled pending-Added row un-adds it (removes the row + un-queues its statement).
- **⚡ Compile is atomic.** `CompileAsync` joins ALL queued statements into ONE `_ddlExecutor.ExecuteAsync(batch)` → one autonomous, auto-committed transaction (`FirebirdDdlExecutor` splits on top-level `;`, BEGIN/END-aware). On success → `RefreshStructureAsync` (clears the queue + re-reads the catalog, dropping pending tints). On failure → `ErrorMessage` + the queue is retained for retry. (Previously Compile looped per-change = N separate autonomous commits — now atomic.)
- **Discard.** New `DiscardPendingChangesCommand` (`CanDiscardPending => HasPendingChanges`) clears the queue and reprojects every grid back to the catalog state **without a DB round-trip** (rebuilds `EditableFields` from `Fields`; removes pending-Added constraints/indexes + un-marks Dropped ones; resets `EditableDescription`).
- **No metadata Commit/Rollback for the designer.** DDL auto-commits on Compile; there is no manual metadata Commit/Rollback step in this flow.

**New core model** ([TableDetail.cs](src/EmberTern.Core/Metadata/TableDetail.cs)): `enum PendingChangeKind { None, Added, Dropped, Modified }`; settable `PendingState` on `ConstraintInfo` + `IndexInfo` (UI-transient, never read from the catalog).

**Classes changed.** [TableDetailTabViewModel.cs](src/EmberTern.App/ViewModels/TableDetailTabViewModel.cs) (all `Execute*Async` rewritten to buffer + new `DiscardPendingChangesCommand`/`CanDiscardPending` + helpers `BuildDisplayFieldInfo`/`RemovePendingByMarker`/`StageConstraintAddAsync`/`ConstraintListFor`/`MarkConstraintDropped`/`RuleLabel`; atomic `CompileAsync`), [FieldRowViewModel.cs](src/EmberTern.App/ViewModels/FieldRowViewModel.cs) (`PendingKind` + `IsPendingAdded`/`IsPendingDropped`/`HasPendingChange`), [TableDetail.cs](src/EmberTern.Core/Metadata/TableDetail.cs), [MainWindowViewModel.cs](src/EmberTern.App/ViewModels/MainWindowViewModel.cs) (`ShowStructureCompileTools` — Compile/Discard visible on every TableDetail sub-tab), [MainWindow.axaml](src/EmberTern.App/Views/MainWindow.axaml) (Discard button + re-gated Compile), [TableDetailTabView.axaml](src/EmberTern.App/Views/TableDetailTabView.axaml)(.cs) (pending-row tint: `pending-added`/`pending-dropped` row classes for all three grids via code-behind `LoadingRow` + extended `UpdatePendingClass`), [Colors.axaml](src/EmberTern.App/Themes/Colors.axaml) (`RowAddedBrush`/`RowDroppedBrush`, both themes), [UiStrings.cs](src/EmberTern.App/UiStrings.cs) (`FieldEditDiscardTooltip`).

**Tests.** New [TableDesignerBufferedTests.cs](tests/EmberTern.Tests/TableDesignerBufferedTests.cs) (+10: each structural op queues-not-executes + reflects in the grid with no error; pending-Added un-add on drop; atomic Compile retains queue on failure; Discard reverts to catalog). Updated the 9 disconnected-executor tests in `ConstraintManagementTests`/`IndexManagementTests`/`TableEditorGapFixTests` from "executes → ErrorMessage" to "queues → no error". `InlineFieldEditTests`/`PendingDdlVmTests` (already queue-based) unchanged except a stale comment.

**Known limitations (documented, by design).** Move on a pending-Added row is disabled (the display row isn't in `Fields`, so the index-based Move gate is off) — acceptable; reorder the live columns. Mixed pending add + move can produce an off-by-one server-side `POSITION` since statements apply in queue order — Compile + the post-Compile refresh shows the true result. Recompute Statistics is NOT buffered (admin maintenance, auto-commits).

**Gotcha — promote to architecture lore.**

121. **A "designer" surface (grids that show pending edits before Apply) buffers in the VM — the grids must project the WORKING MODEL, not the live catalog.** The bug was a *half-buffered* state: inline cell edits queued (`EnqueueRowEdits` → `PendingChanges`) while toolbar ops executed immediately, so the shared ⚡ Compile button looked dead (nothing fed the queue from the toolbar path). The fix is uniformity: EVERY structural op queues a `PendingDdlChange` AND mutates the bound collection with a pending marker (`FieldRowViewModel.PendingKind`; `ConstraintInfo`/`IndexInfo.PendingState`), `Compile` applies the whole queue in ONE autonomous transaction, `Discard` reprojects from catalog truth with no DB hit. Keep the catalog-truth collection (`Fields`) untouched so `RefreshStructureAsync`'s column-set comparison (gotcha #107) still skips the data-preview reload when columns are unchanged. Distinguish this from **code-object** surfaces (view/procedure source), which are *edit → Compile → auto-commit* (no buffering — there's a single text artifact, not a multi-row model).

### Single-attachment DDL + Developer Mode (Krok 1 + Krok 2, shipped 2026-06-18)

Two-step fix for the "object is in use" / transaction-profile mess, driven by FB5 traces + an isolated repro. Branch `feat/ddl-tpb-fix`. **1274 → 1289 tests.** Build clean.

**Krok 1 — DDL/Compile on the MAIN connection (commit `889c8d0`).** ROOT CAUSE (trace-confirmed): Compile ran via `FirebirdConnectionService.ExecuteAutonomousAsync`, which opened a **transient `FbConnection`** per call — a DIFFERENT attachment than the one that Executed the procedure. Firebird holds a procedure "in use" on the attachment that loaded it (by EXECUTE or COMPILE) until that attachment disconnects or itself ALTERs it; a *different* attachment's ALTER fails "object is in use" even after the executor committed (gotcha #122). Fix: `ExecuteAutonomousAsync` removed; new `FirebirdConnectionService.ExecuteDdlAsync(statements, FbTransactionOptions, ct)` runs the whole batch in ONE transaction on the **main (`_activeConnection`) connection** — same attachment as Execute → co-location → the holder ALTERs its own object → succeeds. The DDL path now passes **explicit `FbTransactionOptions`** (the old transient path passed none → silently ignored every configured profile). gotcha #89 (one tx per FbConnection): DDL begins its own autonomous tx, so the data working tx must be settled first — `FirebirdDdlExecutor` checks `TransactionService.IsActive` and throws a clear "Commit or roll back the active transaction before running DDL." instead of the raw "Parallel transactions…". Verified on FB5: Execute → settle → Compile now succeeds.

**Krok 2 — Developer Mode (commit `60b456a`).** Trace + two-IBExpert tests proved the lever for editing a procedure used by other sessions is **WAIT**, NOT `isc_tpb_write` or `isc_tpb_consistency` (gotcha #123). Replaced the per-lane TPB profile pickers with a single `ConnectionProfile.DeveloperMode` (default false): Standard → DDL `NOWAIT` (fail-fast); Developer → DDL `WAIT` + 10s lock timeout (waits for an in-use object to free instead of "object is in use"). **Only the DDL path is affected** — data ops AND both working-tx lanes are forced to `read_committed + rec_version + nowait + write` regardless of any stored profile, so a legacy CONSISTENCY profile can never make data work block or lock tables. `FirebirdDdlExecutor.BuildDdlTransactionOptions(developerMode)` is the pure NOWAIT-vs-WAIT+timeout builder (unit-pinned). UI: profile + SQL Dialect pickers removed from `NewConnectionDialog`; Developer Mode toggle + description added; title-bar profile chips → green **DEV MODE** badge (theme-aware text via `DevModeBadgeForegroundBrush` — dark `#0E2A1C` on the bright mint green in Dark for ~9:1 contrast, white on the dark green in Light; `ConnectedBrush` untouched). Dialect kept in the model (default 3, `Dialect=1` preserved) — just UI-less. Verified on FB5: Standard fail-fast, Developer waits.

**Deliberately out of scope (deferred, by user decision):** `TransactionProfile` enum/catalog + `Data/MetadataTransactionProfile` fields kept **vestigial** (ignored, not in UI) — full removal is a separate future refactor. Raw F5 DDL in the SQL Editor stays NOWAIT (Developer Mode covers only the Compile/structure path). The metadata attachment, degraded mode, and lane architecture are **kept** — Krok 1 removed the self-block (transient attachment), Krok 2 solved the business problem; further attachment simplification is a separate future refactor, not this task.

**Gotchas — promote to architecture lore.**

122. **Firebird holds a procedure (and likely function/package) "in use" at the ATTACHMENT level — DDL must run on the same attachment that used the object, or no attachment may be using it.** EXECUTE (or COMPILE) of a procedure loads it into that attachment's metadata cache; the cache is released only when the attachment disconnects or itself ALTERs the object. A *different* attachment's `ALTER`/`DROP` fails `object … is in use` even after the executing transaction committed (a transient per-call connection for DDL is the worst case — guaranteed cross-attachment). So Compile/structure DDL must run on the SAME connection as Execute (co-location — `ExecuteDdlAsync` on `_activeConnection`), never a transient. This supersedes the incomplete earlier gotcha #118 (cross-attachment in-use). gotcha #89 still applies: that one connection allows one tx at a time, so settle the working tx before the autonomous DDL tx.

123. **For "edit an object used by other sessions", the lever is dropping `isc_tpb_nowait` (i.e. WAIT) — NOT `write` or `consistency`.** Traces showed IBExpert and EmberTern both ALTER on identical `read_committed + rec_version + nowait + write` TPB; the difference that lets an in-use object be altered is WAIT, so the ALTER waits for the holder to release (lock-manager blocking AST) instead of failing immediately. `consistency`/table-stability is the dangerous red herring (locks whole tables — the historical production-blocking cause), so it is removed from the product entirely. EmberTern's Developer Mode therefore applies **WAIT + a bounded lock timeout to the DDL path ONLY**; data operations always stay NOWAIT (never make a client wait). Build the DDL `FbTransactionOptions` explicitly — the managed driver's default `BeginTransactionAsync(ct)` silently picked NOWAIT and ignored any configured profile (reinforces gotcha #85: never start a Firebird tx from a bare default/IsolationLevel — always explicit `FbTransactionOptions`).
