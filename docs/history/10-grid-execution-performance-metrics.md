### SQL Templates & Drag & Drop (shipped 2026-07-02, merged to `master`)

IBExpert-style SQL generation, redesigned around **Drag & Drop** as the single workflow (no modal, no "generate into a guessed active editor"). Drag a metadata object from the sidebar onto any SQL/PSQL editor → a flyout of applicable templates appears **at the drop point** → pick inserts the generated SQL exactly at the drop offset, first placeholder selected. **2049 tests** (engine + builder + preview fully unit-covered), build 0/0.

**Workflow: `drag → drop → click`.** The drag source is the sidebar (metadata leaves; folders/connections still reorder — no conflict, different row kinds). The drop target is every editable editor.

**Editors (drop targets):** SQL Editor · Procedure Editor · Trigger Editor · Function Editor · Package Editor · View Editor (source + body + cursor/subprogram editors where present; read-only DDL editors excluded).

**Objects (draggable):** Tables · Views · Procedures · Functions · Generators · Exceptions.

**Templates:**
- **Tables:** SELECT * · SELECT Columns · Field List · Parameter List · INSERT (skips computed + identity) · UPDATE (SET skips PK, PK-aware WHERE) · DELETE · UPDATE OR INSERT · **FOR SELECT** (cursor loop from columns) · **DECLARE VARIABLES** (`TYPE OF COLUMN` per column)
- **Views:** SELECT * · SELECT Columns
- **Procedures:** EXECUTE PROCEDURE · SELECT FROM PROCEDURE (selectable) · **FOR SELECT FROM PROCEDURE** (cursor loop; inputs in the call, outputs in SELECT/INTO)
- **Functions:** Function Call (`SELECT f(:args) FROM RDB$DATABASE`)
- **Generators:** NEXT VALUE FOR · GEN_ID
- **Exceptions:** EXCEPTION · EXCEPTION with message (`'message'` tab-stop; FB 2.0+)

**PlainSql vs PsqlBody context.** Every drop target carries a `SnippetInsertionContext` derived from the editor: the main SQL editor + View editors are `PlainSql`; procedure/trigger/function/package body editors are `PsqlBody`. Each template declares the contexts it's valid in (`SqlTemplateDescriptor.Contexts` / `SnippetContexts.Any` vs `PsqlOnly`). The PSQL scaffolds (FOR SELECT, DECLARE VARIABLES, FOR SELECT FROM PROCEDURE, EXCEPTION / EXCEPTION with message) are `PsqlOnly` → they appear only in body editors, never in a plain SQL editor. DML/call/sequence templates are `Any`.

**Tooltip preview.** Hovering a flyout item shows a lightweight monospace tooltip of the exact SQL to be inserted, truncated to 12 lines / 500 chars with an ellipsis, anchored to the **right** of the flyout (`PlacementMode.Right`) so it never covers the list. Deliberately not a preview pane / not a window.

**Lazy metadata loading.** The flyout is built from the object **kind only** — instant, zero catalog reads. Detailed metadata (columns / PK from the PRIMARY KEY constraint / procedure params / function signature) is loaded **once, on the first hover**, via `SnippetContextBuilder`, cached, and shared by every preview AND the final insertion — so the whole interaction costs a single catalog read (and none at all if the user drops-and-clicks without hovering, since the pick triggers the same one load).

**Shared template engine** ([EmberTern.Core/Sql/Templates/](src/EmberTern.Core/Sql/Templates/), zero Avalonia): `ISqlTemplate` (many small impls, no switch) + `SqlTemplateRegistry` + `SqlSnippet`/`SqlPlaceholder` (tab-stop offsets) + `SnippetContext`/`SnippetOptions`, composed by `SqlTemplateCatalog.CreateRegistry()`. Identifier quoting reuses `DdlGenerator.QuoteLight`. `DescriptorsForKind(kind, insertion)` powers the instant menu; `HasTemplatesForKind(kind)` is the drag-start gate; `AppliesTo(ctx)` (kind + context + data) gates generation. App side: [SnippetContextBuilder](src/EmberTern.App/Sql/SnippetContextBuilder.cs) (delegate-seam metadata loaders → the `FirebirdTableDetailReader`, testable without a live FB; PK from `GetConstraintsAsync` per gotcha #103) + [SqlSnippetDropTarget](src/EmberTern.App/Sql/SqlSnippetDropTarget.cs) (`DragDrop`/`DataTransfer` new Avalonia 12.0.3 API, `DataFormat.CreateInProcessFormat<MetadataObject>` in-process payload, flyout + truncated tooltip + insert). VM ([MainWindowViewModel](src/EmberTern.App/ViewModels/MainWindowViewModel.cs)) exposes `SnippetTemplatesFor(kind, insertion)` / `HasSnippetTemplates(kind)` / `BuildSnippetContextAsync` / `GenerateSnippet` (returns Core types only — no Avalonia in the VM contract).

**Full test coverage** ([SqlTemplateTests](tests/EmberTern.Tests/SqlTemplateTests.cs), [SnippetContextBuilderTests](tests/EmberTern.Tests/SnippetContextBuilderTests.cs), [SqlSnippetPreviewTests](tests/EmberTern.Tests/SqlSnippetPreviewTests.cs)): exact SQL per template, PK-aware / computed-identity-excluding / no-PK-placeholder edge cases, quoting, context filtering (PSQL hidden in PlainSql), registry applicability + drag-start gate, context-builder metadata loading per kind + PK-from-constraint, and preview truncation. The drag gesture / flyout / insert are view code-behind — manual smoke (DnD precedent).

**Gotcha promoted to architecture lore.**

159. **Avalonia 12.0.3 replaced the drag/drop data API — `DataObject`/`DragDrop.DoDragDrop`/`DragEventArgs.Data` are gone/obsolete; use `DataTransfer` + `DragDrop.DoDragDropAsync(PointerPressedEventArgs, IDataTransfer, …)` + `DragEventArgs.DataTransfer`.** For an intra-app drag that carries a live object (not OS-serialized), use `DataFormat.CreateInProcessFormat<T>(name)` + `DataTransferItem.Create(format, value)` / `dataTransfer.TryGetValue(format)` — the object travels by reference. `DoDragDropAsync` requires the originating `PointerPressedEventArgs`, so capture it at PointerPressed and start the drag from PointerMoved once past the movement threshold. Cross-control drag (sidebar → a single non-virtualized `TextEditor`) is the built-in API's happy path — distinct from the virtualized-`TreeView`-drop-target unreliability of gotcha #40; the sidebar's own reorder stays pointer-based.

### Data Grid UX — Etap 0 (localization) + Etap 1 (Record N of M) (shipped 2026-07-02)

First slice of the approved "Data Grid Filtering, Aggregations & Navigation" MVP (analysis + phased plan agreed with the user; **filters/aggregations for the materialized grids = Etap 2, next session**; tables/views push-down = a separate later etap the user deferred). **2049 → 2054 tests** (+5). Build 0/0, 8s smoke clean.

**The load-bearing analysis finding (drives every later etap):** the 5 data grids split into two data models — **materialized** (SQL Editor Results, Procedure Result, Function Execute Result: full result in memory, client-side paged/sorted) vs **server-paged** (Table Detail Data, View Detail Data: only the current 200-row page in memory, `GetRowCountAsync` capped at 50 000, sort pushed to SQL as `ORDER BY`). Client-side filter/aggregate on a server-paged grid would silently operate on one page → wrong; those must be pushed to SQL (`WHERE` + separate `SELECT agg()`), which is why the user split them into their own later etap. `QueryColumn.ClrType` is present → type-aware aggregation is feasible client-side. All 5 grids are 5 separate implementations (no shared component yet) — a future `DataGridPanel` + `IGridDataSource` (2 impls) unification is the eventual dedup, staged last.

**Etap 0 — localization.** The 6 Table Detail main-tab labels were Polish string *values* in `UiStrings` (`TableDetailTabFields="Pola"`, `Constraints="Ograniczenia"`, `Indexes="Indeksy"`, `Dependencies="Zależności"`, `Data="Dane"`, `Description="Opis"`) → English. **This reverses the earlier "keep tab names Polish" instruction** (the app is English). Audit (diacritics + Polish-word grep across App `.cs`/`.axaml`) found the only other user-visible Polish was the Folder/Connection/Query context-menu cluster in `UiStrings` (`FolderNewTooltip`/`FolderDialogTitle`/`FolderDialogNameLabel`/`FolderDialogCreate`/`FolderContextRename`/`FolderContextDelete`/`FolderDeleteConfirm*`/`FolderDefaultName`, `ConnectionContextSort`/`SortAscending`/`SortDescending`, `FolderContextAddConnection`, `QueryContextRename`/`QueryContextDelete`/`QueryRenameTooltip`) → all translated to English. `.axaml` files carry no hardcoded text (everything is `x:Static app:UiStrings.*`); remaining Polish is only in code comments (left as-is — not user-visible). Metadata/field/dependency/constraint-sub-tab strings were already English. No test asserted the old Polish values.

**Etap 1 — "Record N of M".** IBExpert-style record-position indicator on the three **materialized** grids (SQL / Procedure / Function). New `UiStrings.RecordPositionFormat = "Record {0} of {1}"` + `RecordCountFormat = "{0} rows"`. Each VM (`MainWindowViewModel`, `ProcedureDetailTabViewModel`, `FunctionDetailTabViewModel`) got a `…RecordInfo` getter + a `Set…SelectedRow(indexInPage)` sink + a `-1` reset in the page-rebuild path: absolute position = `(page-1)*pageSize + indexInPage + 1` over the full (sorted) row count; when rows exist but nothing is selected → `"{total} rows"`; empty when no rows. Views bind a subtle `TextBlock` next to the pagination hint and wire the grid's `SelectionChanged` → `Set…SelectedRow(grid.SelectedIndex)` (SelectedIndex is within the current page; the VM adds the page offset). Re-slicing a page drops grid selection, so the pointer resets to `-1` (falls back to the count). Pinned by 5 tests in `ResultPagingSortTests` (no-result → empty, rows-no-selection → count, first-page absolute position, second-page page-offset math, page-change clears selection).

**Record N of M for the two server-paged grids (Table Data / View Data) is intentionally deferred** into the tables/views etap — it ties into the same paging + cap (`≥50 000`) + selection-within-page code that etap reworks, so doing it there avoids editing that code twice.

**Gotcha — promote to architecture lore.**

160. **A `RadioButton` with a static `GroupName` inside a REUSED `UserControl` deadlocks the UI when >1 instance renders — a shared group across independent VMs fights the group manager in an infinite binding loop.** The first cut of `FilterPanelView` had two `RadioButton`s (`GroupName="filterCombine"`) for AND/OR with `IsChecked="{Binding !MatchAny}"` (one-way) + `IsChecked="{Binding MatchAny, Mode=TwoWay}"`. Avalonia scopes `GroupName` to the whole window, so when the same UserControl renders in several places (SQL Results + Table Data + View Data …) ALL the "AND" radios land in ONE group. The group manager permits only one checked member; it unchecks the others; each other's one-way `{Binding !MatchAny}` immediately re-asserts "checked"; the group unchecks again → an infinite check/uncheck loop that never lets `Dispatcher.UIThread.RunJobs()` settle → the app freezes the moment a detail view renders (and the headless probe hangs forever). A SINGLE instance is fine (self-consistent), which is why it slipped a solo build. **Fix:** don't put a grouped `RadioButton` in a shared UserControl — use a single `CheckBox` (unchecked = AND / checked = OR), which has no group and no cross-instance coupling. **Rule:** any control with window-scoped grouping (`RadioButton.GroupName`) is unsafe inside a control that can be instantiated more than once; prefer a `CheckBox`/`ToggleButton`/`ComboBox`, or generate a per-instance unique group name in code-behind. Diagnose a "renders once, hangs when reused / hangs in the headless probe that builds the real window" symptom by looking for shared window-scoped state in the reused view first.

### Data Grid Filtering & Aggregations — COMPLETE (shipped 2026-07-02, merged to `master`)

Consolidates + finalizes the whole feature (the earlier Faza 1–6 milestones above) after a live-testing bugfix/UX pass. One consistent filtering + aggregation + record-navigation experience across **all 5 data grids** — SQL Results, Procedure Results, Function Results, Table Data, View Data. **2113 → 2135 tests**, build 0/0, smoke clean.

**Supported grids + architecture.** Materialized grids (SQL / Procedure / Function results — the full result is in memory) filter + aggregate **client-side** (`GridFilterEvaluator` / `GridAggregator` over the materialized rows). Server-paged grids (Table Data / View Data — only the current 200-row page in memory) **push down to Firebird SQL** (`FirebirdGridSqlBuilder`: parameterized `WHERE` + a separate `SELECT agg()` over the whole filtered set). The UX is byte-identical; the client-vs-server split lives entirely inside each host's `ApplyRequested` / compute callbacks. Shared, host-agnostic VMs: `FilterPanelViewModel`, `AggregationBarViewModel` (+ `AggregationLineViewModel` chip), `GridColumnRef` / `GridFilterCatalog` / `GridColumnClassifier` / `GridValueConverter`. Shared views: `FilterPanelView`, `AggregationBarView`; shared cell helper `GridCellFilter`. No big `DataGridPanel` unification (functionality-first; the 5 grids stay separate hosts wired to the shared VMs).

**Filtering.** Filter panel (per grid, toggled by a filter `ToggleButton`): add/remove conditions, per-column type-aware operators, **AND / OR** combine (a single `CheckBox` "Match any (OR)" — never grouped RadioButtons, gotcha #160), **Apply / Clear**. Cell context-menu verbs via `GridCellFilter`: **Filter by value** (`=`), **Exclude value** (`≠`), **Contains** (text only). Operators: `= ≠ < ≤ > ≥`, CONTAINING / STARTING WITH / LIKE-suffix, IS [NOT] NULL. **Active-filter marker:** a small accent **dot** overlaid top-right of the filter icon (shared `Border.filter-active-dot` style) bound to the panel's `IsFilterActive` — visible whenever a non-empty filter is applied, **independent of whether the panel is open** (the `ToggleButton :checked` state = panel-open; the dot = filter-applied). No extra toolbar text (DataGrip/IBExpert convention). **Timestamp precision fix:** `GridCellFilter` formats a `DateTime` cell with a round-trippable invariant form (`yyyy-MM-dd HH:mm:ss.FFFFFFF`, fraction only when non-zero) instead of `Convert.ToString` "G" — the old format dropped sub-second precision so an exact `=` on a Firebird `TIMESTAMP` with a fraction found 0 rows (gotcha #161).

**Aggregations (chips, not a footer).** Deliberately NOT the IBExpert footer and NOT results-in-column-headers — a compact **chip** strip under the grid toolbar (evaluated: a true aligned footer needs internal-scrollbar sync + width mirroring in Avalonia 12.0.0 → fragile, rejected; column-header results also rejected by the user). **One-gesture add:** pick a column (persistent context) → pick a **function** → the chip appears + computes immediately (no separate "+ Add" button); the function picker resets to its "Add aggregate…" placeholder so the same function can be re-picked. Removal via **✕** on each chip. Functions (type-aware): **SUM, AVG, COUNT, COUNT DISTINCT, MIN, MAX**. `RecomputeAllAsync` re-runs every chip after a filter change (client) / re-queries (server).

**UX consistency.** All 5 grids share ONE layout: a self-contained grid toolbar row `[⏮ ◀ ▶ ⏭] · page hint · Record N of M · [Filter⧩] [Σ] [↻ refresh where applicable]`, then the filter panel, then the aggregation strip, then the grid. **Record N of M** on every grid (materialized: absolute position over the full/filtered set; Table/View: over the bounded `LastKnownRowCount`). Table Data's pagination + Refresh were moved out of the main app toolbar into the Dane sub-tab's own grid toolbar (previously the lone split grid); Refresh sits flush at the end of the icon group (it's a data-reload action, not navigation). **Filters and aggregations persist when their panels are closed** — the panels are pure UI; closing a panel never clears the filter or the chips (only the user does, via Clear / the chip ✕). ## Performance Analysis (APPROVED FEATURE — design is source of truth; Phase 1 on `feat/performance-analysis-phase1`)

A query/PSQL **performance analysis experience** for EmberTern. Status: **design approved and frozen** (UX, wireframes, MVP, domain model, roadmap). Future sessions **extend this design, do not redesign it.** **Phase 1 is COMPLETE + merged to `master` (2026-07-03)** — plan capture + parser + plan-tree + self-measured stats + `PerformanceReport`, auto-available after execution (Option B), with a plain-language summary and demoted plan (see the Current-state bullet for details). **Phase 2 MEASUREMENT SLICE is COMPLETE + merged to `master` (2026-07-03)** — MON$ per-table reads, sequential-vs-indexed, read amplification, measured findings, Table Access bars, and the Summary↔Verdict↔Findings consistency fix. The **advisor** (rule engine, predicate parser, sargability, R1–R5, **missing-index detection**, **recommendations**) and **"% of table scanned"** (catalog cardinality reader) are **deferred to a later advisor phase** — see the "Phase 2 measurement slice" milestone below.

### Vision
Every existing Firebird tool (IBExpert et al.) is information-rich but guidance-poor — it shows `NATURAL READS = 72`, a plan, and fetch counts, but never says *what's wrong* or *what to change*. EmberTern's differentiator is a **deterministic, evidence-backed advisor** that turns raw optimizer output into a ranked list of findings, each with a fix — while keeping every raw number one scroll away for experts. Two load-bearing ideas: (1) the answer is at the top, raw data at the bottom, nothing between them is required reading; (2) EmberTern **owns the connection and the cursor**, so it can capture per-statement per-table read stats that `isql` structurally cannot (isql destroys the statement before its stats can be read).

### Approved UX direction (frozen)
One **Performance surface** — the identical component hosted in the SQL Editor (a 4th bottom-panel sub-tab beside Results/Messages/Output) **and** in Procedure/Function/View Detail (a sub-tab). The only difference between hosts is how many statements feed it (editor = one; procedure/function = N internal cursors). **Progressive disclosure, four stacked zones** (NOT five sibling tabs — that repeats IBExpert's "which tab?" failure):
- **① Verdict bar** (always visible): severity dot + one-word grade (`Fast`/`Acceptable`/`Needs attention`/`Slow`) + headline metrics (time · rows returned, rows read, **amplification factor**) + one plain-language sentence = the beginner's whole answer. Right-side: `Re-run & profile`, `Export`, `Capture ▾`.
- **② Findings** (ranked advisor list): each an accordion → Explanation → Evidence → Fix → action buttons (`Test this index`, `Copy DDL`, `Show in plan`). Collapses to one green `✓ No issues` row when clean.
- **③ Access & Plan** (linked, splitter-resizable): left = **Table Access bars** (red=sequential/Natural, blue=index, **sorted by Natural desc**, offending table pinned, each bar annotated with absolute reads + **% of table scanned** so magnitude is never shown without scale — the fix for IBExpert's "72 looks scary" flaw); right = **Plan tree** cost-heat tinted, `Full Scan`/NATURAL flagged. Clicking a finding highlights the table in both panes (one selection model across ①②③).
- **④ Details** (expert drawer, collapsed): timings (prepare/execute/fetch, cold-cache badge), I/O counters (with accuracy label), full per-table counters, raw plan text (selectable/copyable), transaction/TPB context, capture method. Everything selectable + exportable.

**Redesigned Execution Log** (replaces `285 rows in 1020 ms`): a structured, **selectable/copyable/exportable** list of collapsible per-run records — timestamp · severity dot · statement (elided) · headline metric, expanding to Rows / Timing / I/O / Access / Tx / Finding, with honesty chips (cold-cache, counter-accuracy) and a `↦ Open in Performance` deep-link. Metadata-lane/internal reader statements suppressed by default. No memory/buffer noise.

**Procedure panel:** ② becomes a **Cursor Breakdown grid** (# · Statement · Access badge · Time · Reads · Finding dot), sorted by Time desc, NATURAL pinned; ③ adds a **cursor cost ranking** bar ("which of the N statements to fix first" — the thing IBExpert never ranks). **Function panel:** adds a **Call Summary strip** (Deterministic yes/no, per-call time, and a **per-row → per-query projection**: "0.9 ms/call ≈ 90 s in a 100k-row query" — the function blind spot) + `Execute ×N` for a stable average.

Wireframes for all four surfaces (SQL Editor Performance Panel, Procedure Performance Panel, Function Performance Panel, Execution Log) are the approved layout. Cross-screen UX principles: one reading order everywhere; scale before alarm; one selection model; every finding ends in an action with before/after proof; honesty chips (cold-cache, accuracy, capture method, confidence/"candidate") surfaced not hidden; same component across all object types.

### Phase 2 — investigation findings (VERIFIED on live FB 5.0.3, 2026-07-03)

These are **connection-level (group 1)** counters. Probe result: `SEQ_BEFORE=0` → `SELECT COUNT(*)` full scan of 5 rows → `SEQ_AFTER=5, IDX=0`. **The before/after delta is exact and attributes reads to the specific table.**
- **Full scan → `MON$RECORD_SEQ_READS`; index access → `MON$RECORD_IDX_READS`** (verified: `PLAN (P2T INDEX …)` gave `IDX=1, SEQ=0`). This is the Natural-vs-Index signal the Table Access bars + R1/R2 need.
- **MON$ snapshot rule confirmed:** the snapshot freezes at first MON$ access within a transaction — so the two reads MUST come from a transaction we can COMMIT between (COMMIT+restart refreshes). **Design consequence:** read the stats from the **metadata connection (#2)** in its own short txs (before-read → commit → data query runs on #1 → after-read), filtering to connection #1's attachment id. This never touches the user's data working tx (which we must not commit — manual-tx rule) and reuses the existing C2 metadata lane. Cache the data attachment id (`SELECT CURRENT_CONNECTION FROM RDB$DATABASE` on #1) at connect.
- **Index selectivity** `RDB$INDICES.RDB$STATISTICS` reads fine (probe: 0.2 = 1/5 distinct after `SET STATISTICS INDEX`); `RDB$INDEX_SEGMENTS.RDB$STATISTICS` gives per-segment. `SET STATISTICS INDEX` works (already the app's Recompute-statistics path).
- **Privilege:** a user sees their **own** attachments in MON$ with no special right (SYSDBA/`MONITOR_ANY_ATTACHMENT` only needed to see *others*). Embedded connects as the OS user, so the lab-DB user tables aren't readable by it — the probe used a fresh owned DB; production connects as the user's (privileged) profile, so this is a probe-only artifact.

**Gotchas — promote to architecture lore.**

167. **An App per-host owner type must NOT share a name with a Core domain type — `EmberTern.App.ViewModels.HostPerformanceContext` vs `EmberTern.Core.Performance.PerformanceContext`.** The App file imports `EmberTern.Core.Performance` (for `PerformanceReport` etc.), so a same-named App type resolves by same-namespace-first and *compiles*, but it's a live confusion trap (a future session reading `PerformanceContext` in an App VM can't tell which is meant, and the two are unrelated — one is the advisor's analysis context, the other owns a panel + captured run). **Gotcha — promote to architecture lore.**

166. **To reuse the SAME shared VM/panel across multiple host views, set the child's `DataContext` from code-behind via `FindAncestorOfType<Window>()` — do NOT reach the window from XAML with `{ReflectionBinding DataContext.X, RelativeSource={RelativeSource AncestorType=Window}}` unless that pattern already exists in the codebase.** The one PerformancePanelView is hosted in three places (SQL Editor bottom panel + Procedure + Function detail sub-tabs), all bound to the single `MainWindowViewModel.Performance`. In the SQL Editor it's a direct `DataContext="{Binding Performance}"` (the host IS MainWindow). In the detail UserControls (whose own DataContext is the detail VM) the panel must reach the window's DataContext. The XAML `RelativeSource AncestorType=Window` + `ReflectionBinding DataContext.Performance` COMPILES and doesn't crash, but if it silently fails to resolve you get an empty panel — and a headless/8-second smoke can't catch it (it needs a live connection + Execute + tab-switch). The codebase has NO precedent for that XAML shape, but it DOES have a proven one: the detail code-behinds already do `this.FindAncestorOfType<Window>()?.DataContext is MainWindowViewModel mainVm` in `OnAttachedToVisualTree` to wire editor services. Reuse it: give the hosted panel an `x:Name`, `FindControl` it in the ctor, and assign `panel.DataContext = mainVm.Performance` in `OnAttachedToVisualTree`. **Rule:** prefer the established code-behind ancestor-walk for cross-DataContext wiring in a reused control; only use a `RelativeSource`/`$parent` XAML binding when the same shape is already proven elsewhere in the app.
