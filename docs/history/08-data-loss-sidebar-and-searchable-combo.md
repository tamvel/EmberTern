### Data-loss protection — Increment 1: WorkGuard + ChoiceDialog (shipped 2026-06-19)

First of a two-increment data-loss-prevention model (Increment 2 = auto-draft, separate session). One unified guard replaces the scattered, partial confirmations so the user can't silently lose work on **tab close**, **disconnect**, or **app close**. **1338 → 1356 tests** (+18). Build clean (0/0), smoke OK.

**Two distinct kinds of "work to lose"** (the design's foundation):
- **Unsaved CODE** (lives only in the tab VM): a New Table form, a New View/Procedure source, a modified-but-not-compiled View/Procedure source, or a TableDetail designer with queued `PendingChanges`. Lost on tab/app close. Can only be "saved" by Compile (or, in Increment 2, by an auto-draft).
- **Active transaction** (lives on the server, dies with the session): any data/metadata working tx. **Cannot** survive a restart, so it always needs a conscious Commit/Rollback **now**.

**`ChoiceDialog`** ([ChoiceDialogViewModel.cs](src/EmberTern.App/ViewModels/ChoiceDialogViewModel.cs) + [ChoiceDialog.axaml](src/EmberTern.App/Views/ChoiceDialog.axaml)) — the N-button sibling of the binary `ConfirmDialog`. `ChoiceRequest { Title, Message, ChoiceOption[] }` → `Task<string?>` (chosen `ChoiceOption.Id`, or null when dismissed = cancel). Each option carries `IsDefault` (primary style + Enter), `IsCancel` (Esc / window-close maps here), `IsDestructive`. **Additive** — the binary `ConfirmDialog` and its 12 callers are untouched (extending it would have broken their `Task<bool>` contract; gotcha — see #131). Wired via `MainWindowViewModel.ChoiceRequested` (no handler → null = cancel; safe because the branches using it only fire with a live transaction, which tests never have).

**Unified unsaved-work model** ([IUnsavedWorkSource.cs](src/EmberTern.App/ViewModels/IUnsavedWorkSource.cs)) — `IUnsavedWorkSource { UnsavedWorkItem? GetUnsavedWork(); }` implemented by NewTable / ViewDetail / ProcedureDetail / TableDetail VMs (4 impls → interface justified). `UnsavedWorkItem(UnsavedWorkKind {NewObject, ModifiedSource, PendingStructure}, string Label)` — Label is a ready-to-show summary line (object name included). `WorkspaceTabViewModel.UnsavedWork` switches on `Kind` and delegates to the child. TableDetail reports only **structural** `PendingChanges` (pending DATA edits are transaction work, surfaced by the tx guard — closing one table tab doesn't lose them; the tx keeps them).

**Dirty tracking for View/Procedure** (they had none). An **explicit `IsDirty` flag + `_suppressDirty` guard** (the project's `_suppress*` idiom), NOT a baseline string-compare — the editable source has two representations (Source text vs. the Easy structured model) and a pure Source⇄Easy toggle must NOT read as an edit. Programmatic writes (LoadAsync / RefreshAsync / `OnEasyModeChanged`) are wrapped in `_suppressDirty`; genuine user edits flip it via `MarkDirty` (hooked to `OnSourceTextChanged` / `OnEditableViewName|ProcedureNameChanged` / `OnEditableBody|ExecutableBodyChanged` + the Easy collections' `CollectionChanged` + each added row's `PropertyChanged`). Cleared on load and after a successful compile. The ctor starts suppressed (so ctor field assignments don't mark dirty) and releases at ctor end. A fresh **New** View/Procedure is dirty after the template seed, so `NewView`/`NewProcedure` call `detail.ClearDirty()` after seeding → an untouched new tab is clean and won't prompt; the first real edit flips it back.

**One `WorkGuard`** on [MainWindowViewModel](src/EmberTern.App/ViewModels/MainWindowViewModel.cs), three entry points, one `CollectUnsavedWork()` aggregation over the open tabs:
- **Tab close** (`RequestCloseTabAsync`) — was NewTable-only; now prompts **Discard / Cancel** (binary `ConfirmDialog`) for ANY tab whose `UnsavedWork` is non-null. Clean tabs (and DDL / read-only tabs, reopenable from the tree) close silently. Programmatic closes (post-compile, delete-table cleanup) call `CloseTab` directly and never prompt. Per the user's call: tab close NEVER auto-compiles — Compile is a conscious DB op, Close is a UI op.
- **Disconnect** (`ConfirmDisconnectAsync`) — active transaction → `ChoiceDialog`: **Commit / Roll back / Cancel**, **default Roll back** (settles the chosen lanes via the existing `CommitAllAsync`/`RollbackAllAsync` before disconnecting; "Force" was dropped — disconnect ends the session and Firebird rolls back anyway, so it added only confusion). Uncompiled tab work with no tx → binary Discard / Cancel (Increment 2's drafts will make this survive, at which point disconnect won't lose code).
- **App close** (`TryCloseApplicationAsync`) — `OnWindowClosing` is now `async void`: it sets `e.Cancel = true`, awaits the guard, and re-closes (via a `_forceClose` flag) only if allowed. Active tx or unsaved code → `ChoiceDialog`: **Cancel** (default/Esc) / **Discard and exit** (rolls back active transactions). No "Commit all on exit" — a blind whole-session commit is dangerous; the user commits deliberately per-connection. Nothing unsaved → closes immediately (no dialog).

**Strings** — a `Data-loss WorkGuard` block in [UiStrings.cs](src/EmberTern.App/UiStrings.cs) (Unsaved*Format summary lines, CloseTabUnsavedConfirm*, DisconnectChoice*, DisconnectUnsaved*, ExitUnsaved*). The legacy binary `DisconnectConfirm*` consts are kept but unreferenced (noted in place).

**Tests** ([DataLossGuardTests.cs](tests/EmberTern.Tests/DataLossGuardTests.cs), +18): ChoiceDialog Choose/flags; per-VM `GetUnsavedWork` (NewTable content gate, TableDetail PendingChanges, View/Procedure existing-modified → ModifiedSource, new-untouched-after-ClearDirty → clean, new-edited → NewObject, mode-toggle not dirty); `CollectUnsavedWork` lists only dirty tabs; tab-close clean/dirty-cancel/dirty-confirm; app-close nothing/discard/cancel/dismiss; disconnect-with-uncompiled-no-tx prompts. (Disconnect-with-tx and the dialogs' runtime binding need a live FB / display — smoke-deferred.)

**Increment 2 (auto-draft) — NOT YET BUILT (next session).** Approved design + the 5 user corrections: crash/power-loss-safe debounced autosave of uncompiled work to a separate **`drafts.dat`** (reusing `SettingsFileContainer` + DPAPI), `IDraftSource` on the 4 VMs, **TableDetail `PendingChanges` ARE drafted** with on-restore validation against the current schema + a warning for changes that can't be applied (#1), **draft stores the baseline object DDL/version** → warn "draft created on an older version" if the DB object changed since (#4), **draft auto-deleted after a successful Compile** (no historical accumulation, #3), and — explicit (#2) — **NO recovery screen**: silently re-open the drafted tabs on startup, show a one-shot toast **"Recovered N draft(s) from the previous session"**, and mark recovered tabs with a `●` / "Recovered" marker until their first Compile or manual close. Once drafts exist, the app-close guard relaxes so uncompiled code no longer blocks exit (only transactions do); disconnect likewise stops losing code. Hooks already in place: the same `IsDirty`/`MarkDirty` edit points feed both the guard and (next) the autosave debounce.

**Known minor gap** (closed by Increment 2's same hooks): a *rename-only* edit of a View column row / Procedure local row flips dirty via the row `PropertyChanged` subscription — covered; a missed signal would only drop one prompt, never cause silent loss.

### Data-loss protection — Save-and-close / Save-and-disconnect (shipped 2026-07-17)

Closes the "only Discard, never Save" gap the WorkGuard shipped with: previously, unsaved
metadata editors could be **listed and discarded** at close/disconnect but not saved — the user
had to cancel, re-open each editor, Compile by hand, and close again. Now the guard offers to
**compile every dirty editor in one pass** (IBExpert-style), and — critically — **reuses the
existing group-recompilation pipeline** rather than standing up a second save mechanism.

- **One save mechanism.** The actual save of one object stays in each editor's existing compile
  (`ExecuteCompileAsync` / Table's `CompileAsync` / New Table's owner-driven create). A new thin
  adapter interface [`ISavableObjectEditor`](src/EmberTern.App/ViewModels/ISavableObjectEditor.cs)
  (`Task<EditorSaveResult> SaveAsync(ct)`, `EditorSaveResult(bool Success, string? Error)`) wraps
  that compile and returns a structured pass/fail (the editors swallow server errors into
  `ErrorMessage` rather than throwing, so the adapter reports `ErrorMessage is null`). Implemented
  by every object editor (Source base = Procedure/Trigger/Function, View, Package, Table, NewTable,
  Domain, Generator, Exception, Index). `WorkspaceTabViewModel.SavableEditor` exposes it per tab,
  paired with the **existing** `IUnsavedWorkSource.UnsavedWork` for dirtiness (no second dirty flag).
- **One pipeline, launched differently.** `RunBatchWithReportAsync` gained an optional
  `executeAsync` execution-strategy delegate (default = today's `ExecuteAutonomousBatchAsync` SQL
  path, so recompile/activate/recompute are byte-for-byte unchanged). `SaveDirtyEditorsAsync`
  passes an executor that drives each dirty editor's `SaveAsync` — same batch-results dialog, same
  live per-object rows, same continue-on-error, same Cancel.
- **Continue-and-report, not stop-on-first-error** (user decision). Every dirty editor is
  attempted; the app/connection closes only if **all** succeed. On any failure the close is
  aborted, the first failed tab is selected (its `ErrorMessage` already in view), and the user
  fixes + retries. Because DDL auto-commits per object (Ddl lane), a mid-batch failure does **not**
  undo the ones already saved — only the failing objects remain, so retries shrink.
- **Save order = tab order.** A deliberate v1 simplification. Dependency-derived ordering is a
  possible future refinement but is **not required**: under continue-and-report a dependency error
  merely keeps the app open, and a retry after its dependency saved succeeds.
- **Guard wiring.** App close (`TryCloseApplicationAsync`) adds a **Save and exit** option
  (Cancel default / Save / Discard). Disconnect (`ConfirmDisconnectAsync`) is now **two phases**:
  Phase 1 = unsaved metadata (**Save / Discard / Cancel**, default Save), Phase 2 = the unchanged
  data-transaction Commit/Rollback/Cancel. The old binary no-tx discard confirm and the tx-dialog's
  unsaved-discard note are removed (Phase 1 owns unsaved metadata now).
- **Scope includes new objects** (user decision): a new View/Procedure/Function/Package compiles
  via its `IsNew` path; a New Table draft creates via the owner path; an incomplete/invalid new
  object fails validation → aborts the close until fixed or its tab closed.
- **Side-effect suppression.** `_bulkSaveInProgress` gates `OfferRecompileDependentsAsync` so the
  per-compile "recompile dependents?" offer never pops mid-shutdown.
- **Tests** — `DataLossGuardTests` (+ save-flow cases: 3-option app-close dialog, save-all-succeed
  → close allowed, New-Table-invalid → stay open + failed tab selected, phased disconnect dialog,
  `SavableEditor` mapping, adapter pass/fail). Build 0/0; full suite green.

**User-confirmed (2026-07-17):** manual testing verified Save-and-exit, Save-and-disconnect, saving
existing + new objects, compile-error handling, the progress dialog, and first-failed-tab selection.

**Gotchas — promote to architecture lore.**

130. **To prompt asynchronously during window close, make `OnWindowClosing` `async void`, set `e.Cancel = true` BEFORE the first `await`, run the guard, then re-`Close()` behind a `_forceClose` flag.** Avalonia reads `e.Cancel` when the synchronous portion of the handler returns — an `async void` handler runs synchronously up to the first await, so setting `e.Cancel = true` there keeps the window open while the awaited guard/dialog runs. If the guard allows the close, set a `_forceClose` field and call `Close()` again; the re-entrant handler skips the guard and runs the persist path. Never try to await inside a synchronous closing handler without cancelling first — the window tears down underneath you.

131. **For a >2-outcome confirmation, add a parallel `ChoiceDialog`, don't widen the binary `ConfirmDialog`.** `ConfirmDialog` is `Task<bool>` with 12 callers; changing its result type or button model to express Commit/Rollback/Cancel would touch every caller and lose the clean boolean semantics. The N-button `ChoiceDialog` (`ChoiceRequest` → `Task<string?>` of the chosen option Id; null = dismissed = cancel) sits beside it via its own `ChoiceRequested` event, exactly mirroring the `ConfirmationRequested` wiring. Reuse-before-create still holds: only reach for `ChoiceDialog` when the decision genuinely has three+ outcomes (disconnect Commit/Rollback/Cancel; app-close Cancel/Discard) — keep binary confirms on `ConfirmDialog`.

### UI-state persistence tightening — per-tab editor state + globals (shipped 2026-06-20)

Audit-driven sweep of workspace/settings persistence after the reported bug "View set to Easy Mode reopens in Source after restart". The audit found the bug was one instance of a class: `WorkspaceTab` had no slot for any per-tab editor UI state, so Source/Easy mode + active sub-tabs were lost across restart (Procedure papered over it with a *global* preference; View had nothing). Fixed with a **hybrid model** (user-chosen): a global preference seeds a freshly-opened object; a workspace-restored tab restores its own per-tab value. **1338 → 1366 tests**. Build clean (0/0), smoke OK.

**Schema** ([WorkspaceState.cs](src/EmberTern.Core/Workspace/WorkspaceState.cs)):
- `WorkspaceTab` gained nullable per-tab UI fields — `EasyMode` (View+Procedure), `ActiveSubTabIndex` (all three detail editors' main tab), `ActiveInnerSubTabIndex` (Procedure's Easy-collection tab Input/Output/Variables/Cursors/Subprograms; Table's Constraints sub-tab PK/FK/Check/Unique), `GridEditMode` (Table Pola edit toggle). Nullable ⇒ a legacy tab falls back to the global default.
- `WorkspaceState` gained globals — `ViewEasyMode` (hybrid default for new views, mirrors the existing `ProcedureEasyMode`), `ResultsMaximized`, `BottomPanelTabIndex` (Results/Messages/Output).

**Hybrid wiring** ([MainWindowViewModel.cs](src/EmberTern.App/ViewModels/MainWindowViewModel.cs)): new `ViewEasyModePreference` + `OnViewDetailPropertyChanged` (mirror of the Procedure preference). `CreateViewDetail` seeds the global preference for freshly-opened views. `SnapshotCurrentTabs` writes each detail tab's live UI state; `LoadWorkspaceFor` re-applies it after creating the VM — **per-tab value wins over the global default**. `CaptureWorkspace`/`RestoreWorkspace` round-trip `ViewEasyMode` + `BottomPanelTabIndex` (`SelectedBottomTabIndex`); `ProcedureEasyMode` + `QueryPanelVisible` already did.

**Results-maximized** ([MainWindow.axaml.cs](src/EmberTern.App/Views/MainWindow.axaml.cs)): captured in `OnWindowClosing` (`state.ResultsMaximized = _resultsMaximized`), restored in `ApplyLayoutFromPendingRestore` (sets `_resultsMaximized` + `SetResultsMaximized`; row sizing applies via `ApplyResultsRowForActiveTab` when the Query tab activates). Same code-behind-owned-layout pattern as `WindowBounds` / `SidebarWidth` / `ResultsPanelHeight`.

**Dead code removed**: `AppearanceSettings` (the `ThemeVariant`/`AccentColor` stub + `UserSettings.Appearance` + its round-trip test assertions). It was persistable-but-never-read/written (the theme toggle just flips `RequestedThemeVariant` with no persistence); the user opted not to wire theme persistence, so it's gone. `UserSettings` now holds only `GridProfiles`. JSON back-compat is automatic (an old `"Appearance"` key is ignored on read).

**Audit verdict (Capture/Restore symmetry + dead fields):** every `WorkspaceState` field is now both captured and restored. No asymmetry, no dead fields. `WorkspaceTab.ConnectionProfileId` is threaded to the factory but not yet consumed for behavior (V2 source-connection chip) — intentional metadata, not dead.

**Deliberately NOT persisted** (confirmed out of scope with the user): caret / scroll position, Data/Result pagination page+sort (re-fetched), metadata-category expansion inside a connection (eager-loaded), auto-reconnect (user logs in manually), uncompiled New-object / pending-designer content (Increment 2 auto-draft territory).

**Tests** ([WorkspaceUiStatePersistenceTests.cs](tests/EmberTern.Tests/WorkspaceUiStatePersistenceTests.cs) + [WorkspaceStoreTests.cs](tests/EmberTern.Tests/WorkspaceStoreTests.cs)): store-level round-trip of the per-tab + global fields; VM capture for View/Procedure/Table; VM restore-apply for View/Table; per-tab-beats-global override; global-prefs round-trip; fresh-open-uses-global; and a full **end-to-end disk round-trip** (`EndToEnd_FullScenario_SurvivesDiskRoundTrip`) that builds the user's exact smoke scenario — 2 views (Easy+Source), 2 procedures (Easy on Variables + Source), a table (Constraints→Unique, Grid Edit on), Messages bottom tab, Results maximized — persists through the real `WorkspaceStore`, reloads in a fresh VM, asserts every state came back. Verification caveat: Procedure's restore-apply is covered with the Query tab kept active (the detail tabs' lazy load + procedure domain-load need a live `FbConnection`, so a headless test can't activate them); the true GUI click-through against the live FB is the user's manual check.

**Gotcha — promote to architecture lore.**

132. **Per-tab editor UI state belongs in `WorkspaceTab`, not in a global preference — use the hybrid rule (global seeds new, per-tab restores reopened).** When an editor surface (View/Procedure/Table detail) has view-state the user expects to survive restart (Source/Easy mode, active sub-tab, grid-edit toggle), add nullable fields to `WorkspaceTab`, write them in `SnapshotCurrentTabs`, and re-apply them in `LoadWorkspaceFor` AFTER the factory applied the global default — so a restored tab keeps its own state while a freshly-opened object uses the latest global preference. A single global preference (the original Procedure approach) cannot represent two open objects in different modes and silently rewrites what every reopened tab restores as. Code-behind-owned *layout* flags (window bounds, sidebar, results height/maximized) stay in `WorkspaceState` globals set in `OnWindowClosing` / read in `ApplyLayoutFromPendingRestore`, separate from VM-owned per-tab state.

### Object Explorer performance — Etap 1: lazy COUNT-only load + debounce + local filter + type-ahead (shipped 2026-06-20)

Audit-first sprint on the metadata tree's lag/scroll/filter behaviour for large schemas (the user's FB5 ERP: ~2356 tables + thousands of indexes/domains/etc.). **Diagnosis came before code** (see the audit in the session): the felt lag was ~80 % self-inflicted (eager full-load + per-keystroke full-tree filter), and only the **scrollbar** problem is a genuine `TreeView` control limitation. Etap 1 fixes the self-inflicted costs without a control migration; the `TreeDataGrid` question is **parked** for a separate architectural sprint (decision: measure after Etap 1, migrate only if scroll still misbehaves on very large expanded categories). **1366 → 1401 tests** (+35). Build clean (0/0), 8s smoke OK.

**Root causes found (with locations):**
- **Eager full-load on connect** — [ConnectionNodeViewModel.LoadCategoriesAsync](src/EmberTern.App/ViewModels/ConnectionNodeViewModel.cs) loaded ALL 13 categories' full leaf lists sequentially, creating one `MetadataNodeViewModel` per object → ~5–15k VMs at connect before anything was usable; `SqlFor` has no row cap. Plus [LoadGroupAsync](src/EmberTern.App/ViewModels/MetadataExplorerViewModel.cs) called `ApplyFilter()` after EACH category → ~13× full sweeps during connect.
- **Per-keystroke full-tree filter** — `TextBox.Text` (TwoWay) writes on every char → `OnFilterTextChanged → ApplyFilter` with no debounce; `ApplyFilter` iterated all loaded leaves AND auto-expanded every matching loaded group → realize-storm. The eager-load made ALL groups loaded, so filtering expanded everything.
- **Scrollbar jump** — nested `VirtualizingStackPanel` inside `TreeView` (`TreeView.ItemsPanel` + `TreeViewItem.ItemsPanel` styles in [MainWindow.axaml](src/EmberTern.App/Views/MainWindow.axaml)). Avalonia estimates the outer scroll extent across nested VSPs; a 2000-child expanded category makes the estimate wrong → thumb size/position wrong, jumps. **Control-level, not fixable in our code** — only mitigated by fewer realized rows (which lazy-load delivers).

**What shipped:**
- **COUNT-only on connect, lists on first expand.** New [FirebirdMetadataReader.CountAsync](src/EmberTern.Firebird/FirebirdMetadataReader.cs) + `CountSqlFor` (a `SELECT COUNT(*)` mirror of `SqlFor`, no ORDER BY/TRIM). `LoadCategoriesAsync` now loops `metadata.LoadCountAsync(cat)` (one scalar per category) → the user sees `Tables (2356)`, `Views (215)`, … immediately; the leaf list for a category loads on its first expand via the pre-existing `OnIsExpandedChanged → LoadGroupAsync` path. **Domain count must exclude anonymous backing-domains** (`NOT STARTING WITH 'RDB$'`) or it reports thousands more than the displayed user-domain list (which `IsSystemName` strips client-side) — gotcha #133. `RefreshAsync` now reloads loaded/expanded groups in full and just re-fetches the COUNT for the rest (`ResetGroupToPlaceholder` removed).
- **Filter debounce ~350 ms.** `MetadataExplorerViewModel` schedules `ApplyFilter` through a lazily-created `DispatcherTimer`, with a try/catch fallback to synchronous apply when there's no dispatcher loop (unit tests / headless). `ApplyFilter` + `ApplyFilterToGroup` made `internal` for deterministic testing.
- **Local filter, no whole-tree auto-expand.** With lazy-load, on a fresh connect zero categories are loaded, so filtering can't realize a storm; `ApplyFilterToGroup` only auto-expands LOADED groups that have matches (cheap — only user-opened categories) and **never force-loads/expands an unloaded category** (it stays visible so the user can expand it to load+filter). `ApplyFilter` cost is now ∝ loaded leaves, not total objects.
- **IBExpert-style type-ahead.** Filter-independent: with focus on the tree, typed letters accumulate into a transient buffer (~900 ms idle-reset, Escape cancels) and jump to the next node whose name starts with it, searching forward from the current selection and wrapping. Pure logic in the VM ([BuildTypeAheadIndex](src/EmberTern.App/ViewModels/MetadataExplorerViewModel.cs) / `FindTypeAheadIndex` / `NodeSearchText` — unit-tested); the View ([MainWindow.axaml.cs](src/EmberTern.App/Views/MainWindow.axaml.cs) `OnSidebarTypeAhead`) tunnels `TextInput`/`KeyDown`, expands the match's ancestor path, selects + `BringIntoView` + focus (posted at Background priority so the container is realized). Search scope = every LOADED node (descends into loaded-but-collapsed categories so a leaf there is reachable and its path expands); unloaded categories have no real leaves to find. Fresh single letter searches exclusively (repeating a letter cycles); extending the buffer searches inclusively (refine keeps the current match). **Known limit:** `BringIntoView` on a far-off virtualized item is best-effort (the container may not be realized) — selection still updates.
- **Before/after instrumentation.** New [PerfTrace](src/EmberTern.App/Diagnostics/PerfTrace.cs) (env-gated by `EMBERTERN_PERF_DIAG`, logs to `%TEMP%\EmberTern-debug.log`): `category-load` line = connect→usable-tree time (all COUNTs) + managed-heap KB; `group-load` line = first-expansion cost + leaf count + heap. Procedure to quantify the gain on the live FB schema is in the file header. Can't be run from this environment (needs the live DB); the analytical gain is ~10k leaf-VMs-at-connect → 13 scalar COUNTs, lists realized on demand + virtualized.

**Tests** ([MetadataReaderTests.cs](tests/EmberTern.Tests/MetadataReaderTests.cs) +9 `CountSqlFor`/`CountAsync` shape; [TreePerfTests.cs](tests/EmberTern.Tests/TreePerfTests.cs) +12 type-ahead find/index/NodeSearchText, local-filter `ApplyFilterToGroup`, lazy `LoadCountAsync` no-op). The type-ahead View wiring + scroll are code-behind (not unit-tested, per precedent).

**Deferred to a future architectural sprint (parked, not abandoned):** if the scrollbar still jumps on very large expanded categories after Etap 1, migrate the sidebar from `TreeView` to **`TreeDataGrid`** (`HierarchicalTreeDataGridSource` flattens visible rows into one virtualized stream → accurate extent, smooth scroll). Cost: NuGet (verify Avalonia 12.0.x compat), rewrite templates (mixed Folder/Connection/Metadata node types), drag&drop (gotcha #40), context-menus, selection, expand persistence. Also a future candidate: a real cross-category **server-side search** (the filter currently only searches loaded categories — type-ahead + lazy-load are the Etap-1 answer to "find an object fast").

**Gotchas — promote to architecture lore.**

133. **A `SELECT COUNT(*)` shown before the list must replicate the list's client-side filters, or the count diverges from what the user later sees.** `ListAsync` strips `RDB$`/`MON$`/`SEC$`-prefixed names client-side (`IsSystemName`). For most kinds the `COALESCE(RDB$SYSTEM_FLAG,0)=0` predicate already excludes those, so a plain `COUNT(*)` matches — but **Domain** reads `RDB$FIELDS`, which holds one anonymous `RDB$xxx` backing-domain per inline column type; a plain count there reports thousands more than the displayed user-domain list. The count query must add `AND RDB$FIELD_NAME NOT STARTING WITH 'RDB$'`. `LoadGroupAsync` overwrites `Count` with the real list size on expand, so any residual hair-thin edge (null/empty names) self-corrects — but the *pre-expand* count must still be honest. Rule: when adding a COUNT-before-list, mirror every filter the list applies, and prove the catalog table doesn't carry extra rows the list hides.

134. **Lazy COUNT-only load is what makes the existing filter safe — the filter code was never the real problem, the eager-load was.** The metadata filter already (a) cost ∝ loaded leaves (unloaded groups hold one placeholder child) and (b) only auto-expanded LOADED groups. The "filter expands the whole tree and lags" symptom came entirely from eager-load making ALL categories loaded at connect. Once connect fetches only counts (groups stay unloaded with a placeholder), the same filter touches almost nothing and can't realize a storm. Lesson: before rewriting a hot path, check whether an upstream eager-materialization is what makes it hot — fixing the materialization can fix the symptom without touching the path. (Avalonia `TreeView` + nested `VirtualizingStackPanel` still estimates scroll extent poorly for huge expanded branches — that's the one piece lazy-load only mitigates, not cures; `TreeDataGrid` is the cure if ever needed.) **Superseded in part by the Etap 1 follow-up below** — gotcha #134's "lazy-load makes the filter fine as-is" was incomplete: with lazy-load the filter has *nothing loaded to search*, so it needed a session name cache to show per-category match counts. See #135.

### Object Explorer performance — Etap 1 follow-up: IBExpert filter + incremental type-ahead + expand-bug fix (shipped 2026-06-20)

Four UX corrections after live testing of Etap 1. **1366 → 1402 tests.** Build clean (0/0), 8s smoke OK. The unifying insight: lazy-load means **nothing is loaded to search**, so both the filter and type-ahead need a **session object-name cache** (object NAMES only — strings, not VMs; cheap memory, no layout cost) built lazily on first filter/search via `ListAsync` per category, cached for the session, invalidated on disconnect / reload / refresh ([MetadataExplorerViewModel.EnsureNameCacheAsync / InvalidateNameCache](src/EmberTern.App/ViewModels/MetadataExplorerViewModel.cs)). Connect itself stays COUNT-only (cache builds only when the user actually filters or types — not at connect).

1. **Filter — IBExpert behaviour (per-category match counts, hide zeros).** `ApplyFilterAsync` ensures the name cache, then per category sets a new `MetadataNodeViewModel.FilterMatchCount` and `IsVisible`: a category with matches shows `Views (1)` and stays visible; a category with **zero matches hides**. Match count for an un-expanded category comes from the cache (no list load); a loaded category also hides its non-matching leaves in place. `DisplayLabel` shows the **match** count while filtering, the **total** when cleared (base `Count` is untouched). So typing `wid` immediately shows e.g. `Views (1)` / `Procedures (3)` with everything else hidden — no manual expanding to discover where matches are. `CountMatches` is the pure, unit-tested counter.
2. **Type-ahead — true incremental search.** Replaced the per-char "find next from current selection" (which read like independent jumps) with **one growing buffer matched from the top of the tree-ordered index every keystroke** (`FindFirstMatch`): `K → KO → KON → KONT → KONTR` keeps converging on `KONTRAHENCI`, never an independent jump. ~1 s idle reset; Escape cancels. (Same model as Explorer/VS incremental search; the "repeat-a-letter-to-cycle" behaviour was intentionally dropped — the user wanted incremental, not cycling.)
3. **Type-ahead searches the WHOLE structure, incl. never-expanded categories.** The searchable index (`BuildFullTypeAheadIndexAsync`) is built from the name cache (all object names) + connection/category labels — so a match in a category that was never expanded is found. `ResolveTypeAheadAsync` then **loads only the owning category** (on-demand `LoadGroupAsync`), and the View expands ONLY the ancestor path (folder/connection/category) + selects + `BringIntoView` — the rest of the tree is untouched. Resolution is async (the View guards with a generation counter so a stale keystroke's result is dropped).
4. **Bug fix — expanding one category no longer expands others (while filtering).** Root cause: `LoadGroupAsync` ended with a **global** `ApplyFilter()`, which auto-expanded every LOADED matching group. So expanding `Functions` re-ran the global filter and re-expanded its already-loaded siblings. Fix: (a) `LoadGroupAsync` now filters ONLY the group it just loaded (`ApplyFilterToGroup(group, …)`), never the whole tree; (b) the filter **never auto-expands** anything — a category opens only by the user's explicit action. Opening one branch can't change another branch's expand state.

**Tests** ([TreePerfTests.cs](tests/EmberTern.Tests/TreePerfTests.cs) rewritten): `FindFirstMatch` (incremental convergence, case-insensitive, no-match), `CountMatches`, `NodeSearchText`, `BuildFullTypeAheadIndexAsync` (connection rows when disconnected), `ApplyFilterToGroup` (loaded → match count + hide non-matches + **no auto-expand**; no-match hides; clear restores total label; unloaded never auto-expands), lazy `LoadCountAsync` no-op. **Gotchas — promote to architecture lore.**

135. **Lazy tree-load means filter and type-ahead have nothing loaded to search — give them a shared session name cache (names, not VMs).** Deferring leaf-VM creation to first-expand is right for connect speed, but it leaves the search features blind: a filter can't show `Views (1)` for an un-expanded category, and type-ahead can't find an object you never expanded. The fix is a `Dictionary<categoryVM, IReadOnlyList<string>>` of object NAMES, built lazily on first filter/type-ahead (one `ListAsync` per category, strings only — no layout cost), cached for the session, invalidated on disconnect/reload/refresh, deduped via an `EnsureNameCacheAsync()` task (gotcha #23). The filter counts matches from it; type-ahead builds its searchable index from it and loads only the matched category's leaf VMs on a hit. Connect stays COUNT-only — the cache builds only when the user actually searches. This corrects gotcha #134: lazy-load alone did NOT make the filter "fine"; it made it blind, and the cache is what restores cross-category search without re-introducing the eager VM-load.

136. **Contextual type-ahead = match the growing buffer INCLUSIVE-from-anchor with wrap, NOT from the top of the index.** (Supersedes the original "from the top" advice — that was a stepping stone, kept only as the no-anchor fallback.) The incremental growing buffer (`K→KO→KON→KONT→KONTR`, ~1 s idle reset, no repeat-a-letter cycling) is correct and stays. What was wrong was the SEARCH SCOPE: scanning from index 0 every keystroke means the globally-first match wins, so a keystroke flings the user out of the category they're in (Procedures → Tables). Fix = anchor the search on the current position and search forward with wrap: `FindFromAnchor(index, buffer, anchorIndex)` starting AT `anchorIndex` (inclusive) modulo count. Inclusive is mandatory — the first keystroke must check the current selection FIRST and stay if it still matches (IBExpert/VS feel), not advance to the next match (Windows-Explorer feel; explicitly rejected by the user). Two subtleties: (a) map the selected node to an index via a pure `FindAnchorIndex` (structural → reference on `DirectNode`; leaf → `(group, name)` + `Group.Children.Contains` to disambiguate duplicate names; not found → -1 → from-top fallback); (b) a GROWING buffer must anchor on a View-held `_typeAheadAnchor` (the previous match), NOT `tree.SelectedItem`, because selection is applied asynchronously (`Dispatcher.Post`) and a fast refine would otherwise read a stale selection — only a FRESH buffer re-reads `tree.SelectedItem` (to honour a manual click). The search domain is still the FULL flat index (keeps cross-category reach into never-expanded categories via the name cache — #135); only the start point moved from 0 to the anchor.

### Contextual type-ahead search (IBExpert-style anchor + wrap) — shipped 2026-06-20

Replaced the from-top type-ahead with an **anchored** search: typing starts at the user's current selection, searches forward, and wraps — so a keystroke can no longer fling the user from a Procedures node into Tables. Closes the deferred follow-up. **1402 → 1415 tests** (+13). Build clean (0/0), 8s smoke OK. Scope: the type-ahead finder + View wiring only — lazy-load, the name cache, the filter, and `BuildFullTypeAheadIndexAsync` are untouched.

**1. Anchor.** The search domain is still the full flat tree-order index (`BuildFullTypeAheadIndexAsync` over the name cache + structural rows — finds objects in never-expanded categories, loads only the matched category on a hit). What changed is the **start point**: `ResolveTypeAheadAsync(buffer, anchor)` now maps the anchor node to its index position via the new pure `FindAnchorIndex(index, selected)` (structural node → reference match on `DirectNode`; object leaf → `(owning group, name)` with `Group.Children.Contains` disambiguating duplicate names across categories; not found / placeholder / null → -1 → from-top fallback), then searches from there.

**2. Wrap-around.** New pure `FindFromAnchor(index, buffer, anchorIndex)` — first entry (case-insensitive prefix) searching FORWARD from `anchorIndex` **inclusive**, wrapping to the top via `(start + offset) % count`; `anchorIndex < 0` starts at 0 (≡ `FindFirstMatch`, kept as the no-anchor fallback + its existing tests). So from a Procedures selection the search exhausts Procedures-forward, then later categories, then wraps to the top — only ever leaving the current category when there's genuinely no later match.

**3. First keystroke = inclusive (check current FIRST).** Per the user's explicit correction (NOT Windows-Explorer advance): a fresh `K` on a selected `KONTRAHENCI` STAYS on `KONTRAHENCI` because it still matches — it does not jump to the next K-item. Inclusive-from-anchor delivers this for free (the search always begins AT the anchor).

**4. Growing buffer.** `K → KO → KON → KONT → KONTR` stays pinned on `KONTRAHENCI` while it matches; the moment it stops (e.g. `KONTRAHX`) the search advances forward-from-anchor with wrap to the next match (or none). Race-safe: the View anchors a **growing** buffer on its own `_typeAheadAnchor` field (the previous match), not `tree.SelectedItem`, because selection is applied asynchronously (`Dispatcher.Post`) — a fast refine must not read a not-yet-applied selection. A **fresh** buffer (was empty) re-reads `tree.SelectedItem` instead, so a manual click between searches is honoured. `_typeAheadAnchor` is cleared on idle-reset (~1 s) and Escape.

**5. Difference vs. the old global implementation.** Old: `FindFirstMatch` scanned from index 0 every keystroke → the globally-first match won → from a Procedures node, typing jumped to the first matching Table. New: `FindFromAnchor` scans from the selection with wrap → the search is local to where the user is and only crosses categories as a last resort. The incremental growing-buffer semantics and the lazy name cache are preserved exactly; only the start index moved from 0 to the anchor.

**Tests** ([TreePerfTests.cs](tests/EmberTern.Tests/TreePerfTests.cs), +13): `FindFromAnchor` (anchor-matches-stays, incremental-stays-pinned, anchor-stops-matching-advances, wrap-to-top, anchor-at-last-wraps, negative-anchor-from-top, no-match, empty) + `FindAnchorIndex` (null, structural by reference, leaf by group+name, duplicate-name disambiguated by group, stray leaf → -1). View wiring (`_typeAheadAnchor`, fresh/grow anchor selection) is code-behind, not unit-tested (precedent).

**Follow-up bugfix — "after clicking an object, typing does nothing" (shipped 2026-06-20).** Reported on the live DB: click a leaf, start typing → nothing. Diagnosed with a **headless Avalonia probe** (gotcha #39/#94 — added to `ConnectionExpandBindingProbe`), NOT by guessing. The probe builds the real `MainWindow`, focuses a real leaf `TreeViewItem`, injects a keystroke, and observes (a) whether the production `OnSidebarTypeAhead` fires (it sets `e.Handled=true`) and (b) whether selection moves. Result: with a **fresh** buffer the whole path works (handler fires for a focused leaf; `AKTYWA` + `k` → selection moves to `KONTRAHENCI`) — so the event layer / focus / anchor were all fine. **Root cause:** the type-ahead buffer was cleared ONLY by the 1 s idle timer + Escape, never by a click — and every keystroke appends to the buffer *regardless of a match*. So clicking a node within ~1 s of any prior typing left a stale buffer; the next keystroke produced a garbage search string anchored on the stale `_typeAheadAnchor` → `result == null` → nothing, and each failed keystroke grew the buffer further (self-perpetuating). **Fix:** `ResetTypeAhead()` (buffer + `_typeAheadAnchor` + stop timer) now also runs on a left-button tree click (`OnSidebarPointerPressed`), so every click starts a fresh search anchored on the clicked node — Escape and the idle timer route through the same helper. Pinned by the probe's regression leg (poison buffer with a non-matching key → click a leaf → a matching key must still resolve; without the reset the final selection would stay on the clicked leaf). Added `MetadataExplorerViewModel.PrimeNameCacheForTest` (internal seam) so the probe can exercise resolution without a live DB. **1402 → 1416 tests.**

137. **A type-ahead / incremental-search buffer MUST be reset on the user's repositioning gesture (a click), not only on an idle timer + Escape.** Each keystroke appends to the buffer regardless of whether it matched, so a buffer that only clears after N seconds of inactivity will carry a stale search string into the user's next interaction: click a node, type, and the keystroke is appended to garbage → no match → "nothing happens", and every failed keystroke makes it worse. A click is "I'm here now, start fresh" — reset the buffer (and the search anchor) on it. The diagnosis discipline that found this: when "typing does nothing", do NOT guess the layer — build a headless probe (gotcha #39) that focuses the real control and injects the real keystroke, and check (a) does the handler fire (`e.Handled`), (b) does the outcome apply. Here the probe proved the handler fires and a *fresh* buffer resolves correctly, which pointed squarely at buffer *state between interactions* rather than events/focus/anchor. (Add the probe to the existing headless class — one session per process, gotcha #94.)

### Sidebar type-to-filter (replaces type-ahead) — shipped 2026-06-20

At the user's explicit request, the IBExpert-style contextual type-ahead was **abandoned** (too much TreeView/focus fiddliness for the value) and replaced with a simpler, robust **type-to-filter**: while the tree has focus and the user starts typing, focus jumps to the sidebar filter box and the first character lands there; subsequent typing is handled natively by the now-focused `TextBox`. Plus **Ctrl+F** focuses the filter and **Escape** clears it and returns focus to the tree. **1416 → 1396 tests** (removed the type-ahead unit tests + probe; added one type-to-filter probe). Build clean (0/0), 8s smoke OK.

**Mechanism** (all View code-behind in [MainWindow.axaml.cs](src/EmberTern.App/Views/MainWindow.axaml.cs); the filter `TextBox` got `x:Name="SidebarFilterBox"`):
- **Type-to-filter** — a single tunnel `TextInput` handler on `SidebarTree` (`OnSidebarTreeTextInput`). It only fires while the tree (or a tree item) is focused — once the filter box is focused, input no longer routes through the tree, so the redirect is self-limiting. On a printable char it `Focus()`es the filter box, inserts the char at the caret (`box.Text` is TwoWay-bound to `FilterText`, which drives the existing debounced `ApplyFilterAsync`), and marks the event handled.
- **Ctrl+F** — a window-level tunnel `KeyDown` handler (`OnWindowKeyDown`) focuses + selects the filter. Tunnel so it wins before any editor's own Ctrl+F (the user wants the sidebar filter to own Ctrl+F app-wide).
- **Escape** — `OnFilterBoxKeyDown` on the filter box clears `FilterText` and calls `FocusSidebarTree()`, which focuses a real `TreeViewItem` (selected row, else the first realized row) — the `TreeView` container itself doesn't accept keyboard focus, it delegates to items (gotcha #138).

**Removed** (type-ahead): View `_typeAheadBuffer`/`_typeAheadAnchor`/`_typeAheadResetTimer`/`OnSidebarTypeAhead*`/`ResetTypeAhead`/`SetNodeExpanded` + the reset-on-click hook; VM `ResolveTypeAheadAsync`/`BuildFullTypeAheadIndexAsync`/`AddTypeAheadNode`/`NodeSearchText`/`FindFirstMatch`/`FindFromAnchor`/`FindAnchorIndex`/`TypeAheadEntry`/`TypeAheadResult`/`PrimeNameCacheForTest`; the type-ahead unit tests in `TreePerfTests` + the type-ahead probe. **Kept**: the session name cache + the whole filter (`ApplyFilterAsync`/`ApplyFilterToGroup`/`CountMatches`/lazy COUNT load).

**Tests**: [TreePerfTests.cs](tests/EmberTern.Tests/TreePerfTests.cs) trimmed to filter/count/lazy-load only; new headless probe `ConnectionExpandBindingProbe.TypeToFilter_TreeTyping_RedirectsToFilterBox` proves all three behaviours against the real `MainWindow` — (a) typing while a tree item is focused fills the filter + moves focus there, (b) Ctrl+F focuses the filter, (c) Escape clears it + moves focus off the box.

**Gotcha — promote to architecture lore.**

138. **The Avalonia `TreeView` container does not accept keyboard focus — focus a `TreeViewItem` instead.** `tree.Focus()` is a no-op in practice (and headless-provably so: the focused element stays unchanged); the TreeView delegates keyboard focus to its item containers. To "return focus to the tree", focus a real `TreeViewItem` — the selected row's container (`FindTreeViewItemFor(tree, tree.SelectedItem)`) if there is a selection, else the first realized `TreeViewItem` descendant. Corollary for routed-event handlers attached to the TreeView: input only routes through the TreeView (so a tunnel handler on it fires) when a descendant **item** is focused — which is the normal case after a click, and the basis of the type-to-filter redirect.

### TreeView limitation + potential TreeDataGrid migration (observation, parked)

The sidebar is still an Avalonia `TreeView` with a nested `VirtualizingStackPanel` (`TreeView.ItemsPanel` + `TreeViewItem.ItemsPanel`). Avalonia estimates the outer scroll extent across the nested VSPs, so when a single category with thousands of children is expanded the scrollbar thumb is mis-sized and the position can jump — a **control-level limitation we cannot fix from our code**, only mitigate by keeping fewer rows realized (which lazy-load + COUNT-only does). If, after living with Etap 1, the scroll behaviour on very large expanded categories is still unacceptable, the cure is migrating the sidebar to **`TreeDataGrid`** (`HierarchicalTreeDataGridSource` flattens the visible rows into ONE virtualized stream → accurate extent, smooth scroll, 100k+ rows). Migration cost (medium-large): verify the `Avalonia.Controls.TreeDataGrid` NuGet's compat with Avalonia 12.0.x, rewrite the per-type templates (mixed Folder/Connection/Metadata node types), drag&drop (gotcha #40), context menus, selection wiring, and expand-state persistence. Parked as its own architectural sprint — measure first (`EMBERTERN_PERF_DIAG=1`), migrate only if the scroll is still a real problem.

### Trigger Editor — pre-merge fixes (shipped 2026-06-20)

**1. **Gotchas — promote to architecture lore.**

140. **DDL statement splitting must treat a PSQL `CREATE/ALTER/RECREATE {PROCEDURE|TRIGGER|FUNCTION|PACKAGE}` as one unit — its DECLARE-section semicolons are at block-depth 0, BEFORE the BEGIN.** A BEGIN/END-depth splitter (gotchas #55/#128) correctly keeps body semicolons together but still cuts at a top-level `DECLARE VARIABLE …;` because that `;` precedes the first BEGIN (depth 0) → the server gets a truncated `CREATE … AS DECLARE VARIABLE x` → "Unexpected end of command". The fix is statement-shape detection: when a statement starts with a PSQL header, scan it whole — skip to `AS` (skipping balanced parens so `CAST(x AS y)` doesn't false-match), then ignore all `;` and terminate at the `END` that closes the outermost `BEGIN` (CASE-aware; peek past a subprogram's `END`); a header `;` before any `AS`/`BEGIN` terminates a no-body declaration (UDR/EXTERNAL). Views (`CREATE VIEW … AS SELECT`) are NOT PSQL — they split on `;`. The managed FbCommand runs a single CREATE-with-internal-`;` fine (no SET TERM); the splitter only needs to avoid over-splitting.

141. **EmberTern coerces user-typed object names to UPPERCASE on input — the one consistent convention.** Firebird folds unquoted identifiers to uppercase, so a name entered as `stanmag_bu99` becomes `STANMAG_BU99` in the catalog anyway; coercing in the editor keeps the displayed name honest and the DB free of accidental mixed-case (which would require quoting forever). The pattern: a `_settingNameUpper` re-entrancy flag + uppercase-and-reassign in the `[ObservableProperty]` change handler, gated on `!_suppressDirty` so programmatic ctor/load/parse sets aren't coerced (and the field is read-only for existing objects anyway). Applied to every editable object-name field (Trigger/Procedure/View names; New Table name; field/variable names). Any future object creator (generator/exception/function/etc.) MUST adopt the same handler — don't leave a creator that writes a lowercase name.

143. **Every object editor must ship a Revert/Discard button beside Compile, and it must confirm.** Two correct shapes: a *buffered* designer (Table) discards its in-memory pending model + reprojects to catalog truth (no DB hit); a *source* editor (View/Procedure/Trigger/future Function/Package) reloads from the DB via `RefreshAsync` and is gated `IsDirty && !IsNew` (no DB state exists for a not-yet-created object — disable, don't no-op). The confirmation is non-negotiable (an accidental click loses uncompiled work): raise the VM's `ConfirmationRequested` (destructive `ConfirmRequest`, default-true with no handler for tests) and wire it in the editor's factory. A plain-field `IsDirty` won't drive the button's enabled state — route dirty transitions through a `SetDirty` that raises `PropertyChanged` + `RevertChangesCommand.NotifyCanExecuteChanged()`. When adding the next editor: command + `ConfirmationRequested` event + factory wiring + one `Icon.Undo` toolbar button gated on the editor's `IsXxxTabActive`.

144. **`SelectionChanged` BUBBLES — a `TabControl.SelectionChanged` handler also fires for every inner ItemsControl's selection bubbling up; never react to it unguarded, and never change an `ItemsSource` synchronously inside a selection-model update.** In the popup of a tabbed picker (`SearchableComboBox` with a `TabControl` over per-tab `ListBox`es), `tabs.SelectionChanged` caught the inner domain-`ListBox`'s SelectionChanged; the handler re-applied the filter (set the ListBox `ItemsSource`), which (a) synchronously threw `InvalidOperationException: Cannot change source while update is in progress` from a routed-event handler → unhandled → silent process death, and (b) once deferred with `Dispatcher.Post`, formed an ∞ bubbling loop (set source → re-fire ListBox SelectionChanged → bubble → re-post → …, seen as a flickering highlight). Two rules: **(1)** guard a container's routed-event handler to the container itself — `if (ReferenceEquals(e.Source, theTabControl))` — so bubbling child events are ignored; **(2)** any `ItemsSource` mutation triggered from a selection-changed path must be deferred via `Dispatcher.UIThread.Post` (it's illegal during the selection-model's batch update). The same `ItemsSource`-during-selection hazard applies to a plain `ListBox.SelectionChanged` that rebuilds another list (`TableColumnPicker.OnTableSelected` → defer the column load). Headless can't reliably test the Post path (gotcha #94) — verify by live smoke; a global fatal-crash logger in `Program.cs` (`%TEMP%/EmberTern-debug.log` `FATAL`) captures any future silent UI-thread crash.

145. **A function editor has TWO distinct "Result" concepts — never merge them.** Easy-mode **Result** = the function's return-TYPE metadata: a single, unnamed `RETURNS <type>` row (+ a `Deterministic` flag) that the user edits and that drives the generated DDL. The **Execute Result** tab = the runtime OUTPUT of running the function (`SELECT fn(…) FROM RDB$DATABASE` on the Data lane). They share no state and no control: the Easy Result sub-tab is a one-row field grid (no Add/Remove/Move — `IsEasyCollectionEditable` is false there so the toolbar's collection section hides), while the Execute Result tab is a dynamic-column read-only grid fed by `ExecResult` + the persistent exec-info bar. Procedure's single top-level "Result" tab (execution output) does NOT map 1:1 onto a function — for a function the execution-output tab is renamed **"Execute Result"** so the word "Result" is free for the return-type metadata. Keep the two strictly separate in the VM, the view, and the labels.
