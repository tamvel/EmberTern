Etap 6 (live-FB smoke: connect → open function → Source/Easy → edit → Compile → Execute → New Function → restart) is the user's manual pass against a real Firebird, per the codebase's DB-path precedent.

**Gotcha — promote to architecture lore.**

146. **`RDB$GENERATORS.RDB$INITIAL_VALUE` / `RDB$GENERATOR_INCREMENT` don't exist on Firebird 2.5 — version-gate the SELECT, don't issue it and catch.** Those columns were added in FB3 (empirically confirmed present on FB3 and FB5). Issuing a SELECT that references them on FB 2.5 throws `FbException` ("column not found"), and a failed command mid-transaction can mark an active working tx for rollback (readers attach to the working tx when one is open). So gate on `FirebirdDdlReader.ParseServerMajor(connection.ServerVersion) >= 3`: read the columns on FB3+, default initial=0 / increment=1 below. The current value (`GEN_ID(name, 0)`) is version-independent (best-effort try/catch for system sequences). Same "don't run a doomed catalog query" discipline as the FB-version gates for procedure/function source.

### Generator Detail — bugfix sprint (semantics, shipped 2026-06-29)

Five real-DB bugs in the just-shipped Generator Detail, **verified empirically against local FB3 + FB5 databases via `isql`** (no guessing — the prior implementation conflated a sequence's *definition* with its *runtime counter*). **1626 → 1635 tests.** Build 0/0, smoke OK.

**Empirically verified Firebird semantics** (the truth the fix is built on):

| Operation | FB3 `GEN_ID(,0)` | FB5 `GEN_ID(,0)` |
|---|---|---|
| `CREATE SEQUENCE G` | 0 (first `NEXT`=1) | 0 (first `NEXT`=1) |
| `CREATE SEQUENCE G START WITH 10000` | 10000 (first `NEXT`=10001) | **9999** (first `NEXT`=10000) |
| `ALTER SEQUENCE G RESTART WITH v` | v | **v−1** (version-DEPENDENT) |
| `SET GENERATOR G TO v` | v | v (version-INDEPENDENT) |
| `RDB$INITIAL_VALUE` after `START WITH 10000` | 10000 | 10000 |

So: FB4+ adopted SQL-standard `START WITH`/`RESTART WITH` (the stored counter is `logical − increment`, so the first generated value equals the typed number); FB3 stores the counter = the typed number (first generated value is `+increment`). `SET GENERATOR … TO` sets the raw counter directly and behaves identically on both.

**Root cause of Problems 1/2/3 (one bug).** The New-generator `BuildSaveSql` appended `ALTER SEQUENCE … RESTART WITH <CurrentValue>` after the `CREATE … START WITH <InitialValue>`. With the default `CurrentValue = 0`, that emitted `RESTART WITH 0`, which on FB5 set the internal counter to `0 − 1 = −1` AND discarded the `START WITH` initial value. Net on FB5: `Current Value = −1`, first generated value `0`, `Initial Value = 10000` silently lost. End-to-end proof (FB5): old SQL → peek `−1` / first `0`; fixed SQL (`CREATE … START WITH 10000` only) → `RDB$INITIAL_VALUE` 10000 / first value 10000.

**Fixes.**
- **New flow emits the DEFINITION only** ([GeneratorDetailTabViewModel.BuildSaveSql](src/EmberTern.App/ViewModels/GeneratorDetailTabViewModel.cs)): `CREATE SEQUENCE name [START WITH initial] [INCREMENT BY inc]` (+ `COMMENT`). The spurious RESTART is gone. `BuildCreateSequence` still omits `START WITH` for 0 / `INCREMENT BY` for 1, so a default new generator is a plain `CREATE SEQUENCE` → first value 1 (Problem 2). Both `START WITH` and `INCREMENT BY` in `CREATE SEQUENCE` verified working on FB3 + FB5.
- **Current Value edit uses `SET GENERATOR name TO v`** (new `DdlGenerator.BuildSetGenerator`), NOT `RESTART WITH` — version-independent, so `GEN_ID(,0)` becomes exactly the typed value on FB3 and FB5. `BuildAlterSequenceRestart` is kept + shape-pinned (with a doc comment explaining why it's not used for "set current value").
- **De-conflated definition vs runtime (Problem 4)**: Initial Value + Increment are editable only when **creating** (`IsDefinitionEditable => IsNew`); Current Value is editable only on an **existing** generator (`IsCurrentValueEditable => !IsNew`) since it's a consequence of the definition. The View gates the `NumericUpDown`s' `IsEnabled` accordingly. Existing-generator Save therefore emits only `SET GENERATOR` (current) and/or `COMMENT ON SEQUENCE` (description) — never an `ALTER SEQUENCE START WITH/INCREMENT BY`.
- **−1 → 0 display normalization (Problem 3)**: `NormalizeDisplayCurrentValue(raw) => raw < 0 ? 0 : raw` maps Firebird's negative pre-first-use sentinel to 0 for display (and baselines the normalized value so an untouched generator emits no SET on Save). The reader still returns the technically-correct raw value; only the presented value is normalized.
- **Refresh Current Value button (Problem 5)**: `RefreshCurrentValueCommand` + new lightweight reader `FirebirdTableDetailReader.GetGeneratorCurrentValueAsync` (just `GEN_ID(name,0)`). Re-reads ONLY the live counter — no full reload, no dirty flip, no overwrite of Initial/Increment/Description; updates the baseline so the refresh isn't seen as a pending change. Gated `_reader is not null && !IsNew`. For a generator in active ERP use, the user can re-check its value without closing the tab. (`Icon.RefreshCw` button beside the Current Value field.)

**Follow-up — Current Value must equal Initial Value on creation (shipped 2026-06-29).** After the above, the user reported that creating a generator with Initial Value 10000 left **Current Value 9999** (one less) on FB5 — because FB4+ `START WITH n` stores the counter at `n − increment` (the *first generated* value is n, but `GEN_ID(,0)` reads n−1). The user (Firebird-3 ERP dev) wants the classic model where **Current == Initial right after creation** (and the first allocation is Initial + increment), consistently across FB3/FB5. Fix: the New flow now emits **two** statements — `CREATE SEQUENCE name START WITH <initial> [INCREMENT BY <inc>]` (`forceStartWith: true` so `RDB$INITIAL_VALUE` is recorded even for 0) **followed by** `SET GENERATOR name TO <initial>`, which pins the runtime counter to the initial value version-independently. Verified on real FB3 **and** FB5 (incl. one-transaction execution, matching the DDL executor): for initial 10000/0/100-inc5 → `GEN_ID(,0)` = `RDB$INITIAL_VALUE` = 10000/0/100 on both versions, first `NEXT VALUE FOR` = initial+increment. This is NOT the old −1 bug (that appended a RESTART to the *unrelated* default 0, destroying the initial value); here the SET pins to the *same* initial value, intentionally. `BuildCreateSequence` gained an optional `forceStartWith` (default false preserves the portable "plain CREATE for 0" used elsewhere).

**Tests** ([GeneratorDetailTests.cs](tests/EmberTern.Tests/GeneratorDetailTests.cs)): `BuildSetGenerator` shape; New-with-initial emits `START WITH <n>` + `SET GENERATOR … TO <n>` (Current==Initial) and **no** RESTART (the regression pin); New default emits `START WITH 0` + `SET GENERATOR … TO 0`; New-with-increment emits `INCREMENT BY`; `BuildCreateSequence(forceStartWith)` emits `START WITH 0`; existing current-change emits `SET GENERATOR` (not RESTART); `NormalizeDisplayCurrentValue` clamps negatives; `IsDefinitionEditable`/`IsCurrentValueEditable` per new/existing; `CanRefreshCurrentValue` gating. (`RESTART WITH` shape still pinned.) Real-DB behavior (CREATE/SET/RESTART/defaults + Current==Initial after create) verified via isql on FB3 + FB5 — the live app flow against the user's FB3/FB5 is the user's manual confirmation.

**Gotcha — promote to architecture lore.**

147. **Firebird sequence `START WITH` / `RESTART WITH` changed semantics in FB4 — and a sequence has TWO distinct numbers (definition vs runtime). Set the runtime counter with `SET GENERATOR … TO`, never `RESTART WITH`.** FB3: the stored counter equals the typed `START WITH`/`RESTART WITH` value (first generated value is `+increment`). FB4+ (SQL standard): the stored counter is `typed − increment`, so the first *generated* value equals the typed value, but `GEN_ID(,0)` reads `typed − increment` (a fresh `START WITH 10000` reads 9999; `START WITH 0` reads −1). `SET GENERATOR name TO v` sets the raw counter directly to `v` on ALL versions — the only version-independent "make `GEN_ID(,0)` exactly v". The two numbers: **definition** = `START WITH` / `INCREMENT BY` / `RDB$INITIAL_VALUE` (set at CREATE, read-only after — FB3 can't ALTER them) vs **runtime** = `GEN_ID(name,0)` (changeable via `SET GENERATOR`). To make a new generator's runtime Current Value equal its Initial Value across versions (the classic Firebird model the user expects), the New flow emits `CREATE … START WITH <initial>` (forceStartWith, so `RDB$INITIAL_VALUE` is recorded even for 0) **then** `SET GENERATOR … TO <initial>` — pinning the counter to the SAME initial value is correct and intentional. The earlier −1 bug was different: it appended a RESTART/SET to an UNRELATED value (the default 0, not the initial), which destroyed the initial value — never do that. A negative `GEN_ID(,0)` (pre-first-use sentinel) must still be displayed as 0. Verify any sequence-DDL assumption against BOTH FB3 and FB5 with `isql` (incl. single-transaction execution) — they genuinely differ.

### Domain Detail — dedicated 4-tab surface (shipped 2026-06-29)

Domains (user-defined types) open in a dedicated **Domain Detail** experience instead of a plain DDL tab: four tabs — **Domain** (the definition form: Name / Data type / Length / Precision / Scale / Sub type / Character set / Collation / Default value / Check constraint / Not null), **Description** (editable `COMMENT ON DOMAIN`), **Used By** (a SINGLE dependency tree of the table/view columns + PSQL objects that use the domain), **DDL** (read-only reconstructed `CREATE DOMAIN`). **1636 → 1691 tests** (+55). **Architecture decision — a focused form-based `DomainDetailTabViewModel`, NOT a `SourceObjectDetailTabViewModel` subclass.** A domain has no PSQL body, no Source/Easy mode, no params/variables. **Firebird `ALTER DOMAIN` — verified empirically on FB3 + FB5 (`isql`, scratch DBs), per the spec's "don't assume, verify on a real DB":**

| Operation | Supported? |
|---|---|
| `SET DEFAULT` / `DROP DEFAULT` | ✅ both versions |
| `ADD [CONSTRAINT] CHECK (…)` / `DROP CONSTRAINT` (the single check) | ✅ both versions |
| `SET NOT NULL` / `DROP NOT NULL` | ✅ FB3+ |
| `TYPE <newtype>` / `TO <newname>` (rename) | ✅ both versions |
| `COMMENT ON DOMAIN … IS …` | ✅ both versions |
| **change `CHARACTER SET`** | ❌ no syntax → SQL error -104 (Token unknown) |
| **change `COLLATION`** | ❌ no syntax → SQL error -104 |

**EmberTern's editable scope = Default / Check / Description** (per spec). On an existing domain everything else is **read-only**: Name / Data type / Length / Precision / Scale / Sub type / Not null are editable only in the New flow (the `IsDefinitionEditable => IsNew` gate); **Character set + Collation are read-only ALWAYS** — that's a hard Firebird limitation (can never be ALTERed), not just a scope choice. The decision is enforced in the UI (`IsEnabled`/`IsReadOnly` gates) and documented in `DomainInfo` + `DomainDetailTabViewModel`.

### Package Detail follow-up — Description labels + PACKAGE BODY formatter fix (shipped 2026-06-29)

Two manual-test findings. **1764 → 1769 tests** (+5). Build clean, lab-verified on FB5.

**1. "Table description" in every source editor's Description tab.** The shared `UiStrings.TableDescriptionEditLabel = "Table description"` was reused as the Description-tab mini-header by 6 editors (Table, View, Procedure, Function, Trigger, Package) — correct only for Table. **2. CRITICAL — Auto Format corrupted PACKAGE BODY source into non-compilable PSQL.** The PSQL formatter (`SqlFormatter.FormatPsql` → `EmitPsqlUnit`) had no case for a **bare leading `FUNCTION`/`PROCEDURE`** (a packaged subprogram definition). A `PACKAGE BODY`'s top-level items are `FUNCTION name(...) [RETURNS …] AS [DECLARE …;]* BEGIN … END` / `PROCEDURE …` — NOT statements, NOT terminated by `;`. The formatter fell to `CollectPsqlStatement` (collects only to the first inner `;`, e.g. after `RETURN A + B;`), then the routine's own `END` was taken as the package-body `END`, so the body loop exited early and **dropped the trailing `END`s** → invalid PSQL (won't compile). Fix: `EmitPsqlUnit` now detects a packaged subprogram definition (`IsSubprogramDefinition` — a top-level `AS` before any top-level `;`, keyed on `AS` not `BEGIN` so a DECLARE-section `;` doesn't misclassify it) and handles it like the existing local-`DECLARE PROCEDURE/FUNCTION` case: emit the header up to the body `BEGIN`, then recurse for the `BEGIN…END`. The package-body loop now stops only at the package's own `END`. A package-header forward declaration (`FUNCTION/PROCEDURE … ;`, no `AS`) still falls through to the statement path (unchanged). Verified empirically: the formatter's actual output for the PKG_ORDERS-shaped header + body compiled cleanly on FB5 (package created with both members). Standalone procedure/trigger/function formatting is unaffected (the branch only fires on a bare leading FUNCTION/PROCEDURE, which is a syntax error outside a package body). Tests: +5 in `PsqlFormatterTests` (BEGIN/END preserved + balanced + single-statement-to-splitter, idempotent, header forward-decls stay one statement, standalone proc unaffected).

**Gotcha — promote to architecture lore.**

152. **The PSQL formatter must treat a bare leading `FUNCTION`/`PROCEDURE` inside a PACKAGE BODY as a subprogram DEFINITION, not a statement.** A packaged routine (`FUNCTION name(...) [RETURNS …] AS BEGIN … END`) has no terminating `;` and its own nested `BEGIN…END`; collecting it as a statement-to-`;` stops at the first inner `;` and then mistakes the routine's `END` for the package-body's `END`, dropping the remaining `END`s → non-compilable PSQL. Detect it by scanning at paren-depth 0 from the keyword: a top-level `AS` ⇒ definition (emit header-to-BEGIN, recurse the BEGIN…END — same shape as a local `DECLARE PROCEDURE/FUNCTION`); a top-level `;` before any `AS` ⇒ a package-header forward declaration (statement path). Key the discriminator on `AS`, NOT `BEGIN`, because a routine body may have a `DECLARE` section whose `;` precedes `BEGIN` at depth 0. This is the same defect family as the DDL splitter's package handling (gotcha #140) — both must understand that a PACKAGE BODY is a sequence of subprogram definitions, not statements. Verify formatter changes by compiling the actual output on a live FB5 engine (a scratch DB with the referenced objects), not just by eyeballing structure.

151. **A Firebird package has TWO source artifacts and is NOT a relation — give it a focused two-editor VM, not the source-object base.** `RDB$PACKAGES.RDB$PACKAGE_HEADER_SOURCE` + `RDB$PACKAGE_BODY_SOURCE` each store the text after `AS` (like `RDB$PROCEDURE_SOURCE`, gotcha #114), so reconstruction is `CREATE OR ALTER PACKAGE name AS <header>` / `RECREATE PACKAGE BODY name AS <body>` (FB has no `CREATE OR ALTER PACKAGE BODY` — RECREATE is the idempotent body form), with `StripLeadingAs` as the defensive guard (gotcha #139). Members are catalog rows (`RDB$FUNCTIONS`/`RDB$PROCEDURES` WHERE `RDB$PACKAGE_NAME`) — never parse the source for the list; only *locate* a known member for navigation. The `SourceObjectDetailTabViewModel` base assumes one source + an Easy toggle, which a package can't satisfy — model it on `ViewDetailTabViewModel` (focused, reuse at the reader/helper level) and treat the package as one logical object: a single Compile that does header-then-body and stops if the header fails.

**Evidence chain (all from the logs + code, no guessing):**
1. **VS Output, dozens of times** (lines 136–235): `An error occurred binding 'IsVisible' to 'IsVisible' … 'Could not find a matching property accessor for 'IsVisible' on 'EmberTern.App.ViewModels.ConnectionNodeViewModel''` (and `FolderNodeViewModel`), each on a `TreeViewItem`.

3. **[MainWindow.axaml](src/EmberTern.App/Views/MainWindow.axaml):345–347** — ONE global `<Style Selector="TreeViewItem">` sets `IsVisible` on **every** container via `{ReflectionBinding IsVisible, FallbackValue=True}` (the single-style-with-ReflectionBinding pattern from gotcha #38).

**Mechanism.** Every time the `VirtualizingStackPanel` realizes/recycles a connection or folder container during a scroll, the `IsVisible` ReflectionBinding fails (no accessor), resolves to `FallbackValue=True`, and **re-asserts the container's `IsVisible` mid-measure** → the panel re-invalidates measure → re-enqueues → the 10× cycle cap trips → the scroll extent never settles → the ScrollViewer's committed `Offset` reverts → the thumb "snaps back". The `IsVisible` setter is a **leftover of the IsVisible→collection filtering migration** (gotcha #154): filtering no longer hides leaves via `IsVisible`, and only the metadata *group* node still toggles `IsVisible` — but the container-level setter was left applying to all three node types, two of which never had the property.

**Why the scroll diagnostics captured nothing** (debug log: only `SCROLL [rebuild] scroll diagnostics hooked`, zero `SCROLL offsetY=` lines). The hook subscribed **only to `ScrollChanged`**. A thumb drag whose offset never *commits* (the layout cycle reverts it — the very symptom) raises **no net `ScrollChanged`**, so there was nothing to log. This is itself corroboration: the offset was churning inside layout but never settling. (Secondary: `FirstOrDefault()` could pick a nested ScrollViewer.) The diagnostic is now hardened — targets `PART_ScrollViewer` by name + observes `Offset`/`Extent` **property changes** directly (captures churn even when no committed `ScrollChanged`) — so the post-fix state can be re-measured.

**Fix.** Give `ConnectionNodeViewModel` + `FolderNodeViewModel` a stable `public bool IsVisible => true;` — making all three node types satisfy the shared container style's binding contract, exactly as they already all satisfy `IsExpanded`. This eliminates the per-realization binding failure and the mid-measure visibility re-assertion, breaking the feedback loop that fed the VSP layout cycle. `MetadataNodeViewModel` keeps its real observable `IsVisible` (zero-match category hide unaffected). Connection/folder rows are never filter-hidden, so always-true is correct.

### FlatTree Sidebar Migration — Object Explorer on a single-VSP ListBox (shipped 2026-07-01, branch `feat/flattree-sidebar`)

Self-contained handoff for the Object Explorer sidebar rewrite. If you know nothing about this work, read this whole section. **All 5 phases + review fixes are complete on `feat/flattree-sidebar`; build 0/0; 1996 tests green.** Awaiting the user's final visual/DnD smoke before merge to `master`.

#### Problem
- **Original issue:** the metadata sidebar was an Avalonia `TreeView` with a **nested `VirtualizingStackPanel`** (a VSP on `TreeView.ItemsPanel` AND on each `TreeViewItem.ItemsPanel`). On a large schema (the user's FB5 ERP: ~2400 tables, ~8200 indexes, thousands of procedures/triggers/etc.) scrolling was broken.
- **Symptoms:** dragging the scrollbar thumb "fought" the user, the thumb jumped back to the top, scrolling felt unstable, and dragging near the end of a big expanded category produced an **empty tree**.
- **Investigation history (the dead ends matter — don't repeat them):**
  - **Hypothesis 1 — the filter left hidden items in the collection (IsVisible=false rows still measured).** Fixed separately (collection-based filtering, gotcha #154) — improved responsiveness but the scroll symptom persisted with no filter. Not the cause.
  - **Hypothesis 2 — a dead `IsVisible` ReflectionBinding on the shared `TreeViewItem` container style feeding a `VirtualizingStackPanel` layout cycle (gotcha #156).** REAL bug, fixed (added `IsVisible => true` to `ConnectionNodeViewModel`/`FolderNodeViewModel`); the binding-error flood + `[Layout]Layout cycle detected` warnings went away — **but the scroll symptom was unchanged.** A contributor, not the root cause.
  - **Hypothesis 3 — non-uniform row heights making the VSP's average-height extent estimate swing (gotcha #157).** Tried pinning a uniform row height; **DISPROVEN and reverted** — telemetry showed a far more severe pattern than a gentle drift.
  - **Diagnostics:** an env-gated `ScrollTrace` (`EMBERTERN_SCROLL_DIAG`, now opt-in again) logging `offsetY / extentH / viewportH / dExtent / realized` per scroll change to `%TEMP%\EmberTern-debug.log`. First run "captured nothing" because the env var wasn't set (lesson: default-ON during an active investigation).
- **Final proven root cause (from telemetry, not assumption):** Avalonia's **nested `VirtualizingStackPanel` inside a `TreeView` cannot do stable random-access thumb scrolling** over a large expanded subtree. On a thumb drag the extent **hard-collapses to `== viewport` (`realized`≈4), the offset clamps to 0, then rebuilds to tens of thousands of px** — a re-realization/reset cycle (`dExtent` swings 30k–135k), with matching `[Layout]Layout cycle detected … Track/Grid/VirtualizingStackPanel`. Verified in code that **no EmberTern collection / expansion / itemsource is recreated during the drag** — it's the control derealizing the subtree. Control-level limitation, no XAML/data fix.

#### Solution
- **Why not `TreeDataGrid`** (the obvious "flattened virtualization" control): `Avalonia.Controls.TreeDataGrid` 12.0.3 is version-compatible **but a COMMERCIAL/licensed Avalonia "Accelerate" control** — the POC build failed `AvaloniaUI.Licensing error AVLIC0001` (no license key). Rejected (gotcha #158). Community forks (Caly/Beardmouse) exist but carry trust/maintenance risk.
- **Why the hand-rolled flat single-VSP `ListBox`:** free, owned, no dependency, and it IS the actual fix (a single-level VSP over a flat list has an exact, stable extent and correct random-access scrolling). Validated first by a throwaway POC (branch `feat/flattree-poc`, kept until accepted) against the production DB — scroll stable, no collapse.
- **Architecture — two new types (both in `src/EmberTern.App/ViewModels/`):**
  - **`SidebarRow`** — a thin wrapper around one existing node VM (`Node` = `ConnectionNodeViewModel` / `FolderNodeViewModel` / `MetadataNodeViewModel`) + `Depth` (indent) + observable `IsExpandable` (chevron) + observable `IsExpanded` (chevron glyph). The node stays the source of truth for icons, colors, labels, context menus, expansion, children, persistence.
  - **`SidebarFlatController`** — projects the node hierarchy into a flat `ObservableCollection<SidebarRow> Rows` (the ListBox `ItemsSource`). Delegate-based (childrenSelector / isContainer / hasChildren / isExpanded / setExpanded / isVisible) so the projection logic is unit-testable without real VMs or a DB (13 tests). Owned by `MetadataExplorerViewModel` (created once in its ctor; survives `ReloadConnections` by tracking `RootNodes.CollectionChanged`). Exposed as `Metadata.SidebarRows` + `Metadata.ToggleSidebarRow(row)`.
  - **Two distinct node notions (important):** `isContainer` (structural — can host children; drives subscriptions + recursion; a category is a container even while empty) vs `hasChildren` (currently has children; drives the chevron). Conflating them leaves empty categories unsubscribed.
- **Expand/collapse:** driven by each node's own `IsExpanded` — user chevron clicks (`Toggle` → flips `Node.IsExpanded`), double-click a category, and programmatic expansion (auto-expand-on-connect, restore-expand-state) all flow through the same path. The controller observes `IsExpanded` on container nodes only (never leaves) and **splices incrementally** (insert the node's visible subtree / remove the contiguous deeper block) — the hot path never does a full rebuild.
- **Filtering:** unchanged engine (`ApplyFilterAsync` → per-group `ApplyFilterToGroup`: sets `group.IsVisible`, `FilterMatchCount`, rebuilds `Children` to matches; name cache for un-expanded categories; **no auto-expand**). The flat projection respects `IsVisible` (zero-match categories excluded) and shows the (filtered) children; match counts render via the node template's `DisplayLabel`. The filter wraps its group loop in `SidebarFlatController.BeginUpdate()/EndUpdate()` (nesting-safe suspend + one re-projection) so `ApplyLeafFilter`'s item-by-item `Children` rebuild doesn't splice per item (O(n²) when clearing a filter with a big category expanded).
- **Lazy loading / prefetch:** **prefetch on connect** — `ConnectionNodeViewModel.LoadCategoriesAsync` loads the FULL object list for every category (was count-only) via `LoadGroupAsync`, sequentially (single `FbConnection`). "Lazy rendering, not lazy loading": data is ready up front so expand is instant; UI virtualization means only visible rows realize (safe now — the old nested-VSP TreeView froze because it realized ~2k TreeViewItems per category). `LoadGroupAsync` marks the category loaded, so expand never re-queries. Bulk leaf-populate doesn't thrash the controller (leaf `Add`s carry non-container items → skip the subscription re-walk; a collapsed category's populate only refreshes its chevron).
- **Drag & drop:** the existing pointer-based DnD (gotcha #40) retargeted from `TreeView`/`TreeViewItem` to `ListBox`/`ListBoxItem`, unwrapping `SidebarRow.Node`. `ExecuteDrop`, folder state, `IsDragging`/`IsDropTarget`, and the before/after/into computation are unchanged. Only Folder/Connection rows are drag sources/targets.
- **Persistence:** UNCHANGED — expand-state persistence (`FolderState.ExpandedNodeIds` via `Node.IsExpanded` → `MainWindowViewModel.OnNodeExpansionChanged` → `RestoreExpandState`, gotchas #36/#37) works as before because the flat controller is driven by `Node.IsExpanded`; restoring expansion projects into the flat list automatically.

### Trigger context menu — scoped submenus + multi-select analysis (shipped 2026-07-01, branch `feat/flattree-sidebar`)

The trigger-category context menu was reorganized from four flat items (Activate visible / Deactivate visible / Activate all / Deactivate all) into two **action → scope** submenus in [MainWindow.axaml](src/EmberTern.App/Views/MainWindow.axaml): **Activate → {Visible, All}** and **Deactivate → {Visible, All}**. Functionality is unchanged — the four leaf items bind the same `ActivateVisibleCommand`/`DeactivateVisibleCommand`/`ActivateAllCommand`/`DeactivateAllCommand`; the parent `MenuItem`s are command-less headers gated on `IsTriggerGroup`, reusing the existing `MetadataContextActivate`/`Deactivate` strings (also used by the single-trigger leaf items). Two new scope strings `MetadataContextScopeVisible`/`ScopeAll` replaced the retired `MetadataContext{Activate,Deactivate}{Visible,All}` strings (dead after the reorg; only ever referenced by this menu). The submenu shape is deliberately left open for a **Selected** scope to drop between Visible and All. 1996/1996 tests green, build 0/0.

**Multi-select (Ctrl/Shift) feasibility — analyzed, NOT implemented (verdict: MEDIUM risk, deferred to a separate task).** The sidebar `ListBox` is `SelectionMode="Single"`; selection has two single-item consumers — `OnSidebarListSelectionChanged` → `Metadata.SelectedConnection` (titlebar Edit/Copy/Delete/Connect), and `DetectFolderContext` → the "+" add-connection folder. Sidebar selection is NOT persisted. Drag & drop is pointer-based and **decoupled** from selection (reads the pointed row via `FindRowVmAtPointer`, never `SelectedItems`; only Folder/Connection rows drag — trigger leaves don't), so DnD is largely unaffected: the only effect of `Multiple` mode is the Avalonia default press-collapse (can't drag a *group* of connections — not a requested feature). The real sharp edge is **selection volatility on full re-projection**: `SidebarFlatController.RebuildRows()` (fired by `ApplyFilter`'s `EndUpdate` / root reload) does `Rows.Clear()` + recreates `SidebarRow` instances → the ListBox drops `SelectedItems`, so a multi-selection evaporates on a filter keystroke or reconnect (incremental expand/collapse splices *should* preserve it — unverified, needs a headless probe). "Selected trigger operations" are cheap once selection exists — the bulk pipeline is already name-list-shaped (`TriggerBulkRequest(Kind, activate, visibleOnly, names)`), so "Selected" is just a third name source + gating. Implementing multi-select needs: `SelectionMode="Multiple"`, `SelectedItems`→`SelectedConnection` reconciliation, a "Selected" command + `TriggerBulkRequest` variant + owner plumbing + gating + unit tests + a **headless probe** characterizing selection survival across splice vs. full rebuild. Not high-risk, but above the do-it-inline bar — recommended as its own scoped follow-up.

### Metadata refresh — Layer 1 (the bulk guard) + a targeted in-place tree update (shipped 2026-07-27, branch `feat/data-import`)

A session sandwiched between Data Import's I8 and I9, opened by the user with a deliberately narrow scope:
fix the reported bug, apply **Layer 1** of the measurement report
([docs/design/metadata-refresh-analysis.md](../design/metadata-refresh-analysis.md)), re-measure, update
the docs — and **do not** start the Metadata Explorer infrastructure rebuild (Layer 2), which the user
scheduled as its own stage after the import module closes. Build 0/0, suite **5717 green** (+13), smoke
clean.

**The reported bug.** Data Import creates a table on the Ddl lane, the import succeeds, the rows are there
— and the Object Explorer does not show the new table until the user refreshes by hand. No mystery in the
cause: the module never told the tree anything. Every other DDL path in the app calls
`Metadata.RefreshAsync()`; there are twenty such calls.

**⭐ The decision that shaped the fix — and it reversed the report's own recommendation.** The report had
advised leaving this symptom for Layer 2, on the grounds that it is cosmetic (a manual refresh works) and
that a twenty-first `RefreshAsync()` would deepen the very cause of the *other* symptom. The user rejected
the deferral — it is an ordinary UX bug and should be fixed now — while keeping the ban on the blind
refresh. Both halves turned out to be satisfiable at once, because **the import knows the name of the
table it just created**. So it says so: `DataImportEnvironment.TableCreated` / `TableDropped` carry a
name, and `MetadataExplorerViewModel.ApplyObjectAddedInPlace` / `ApplyObjectRemovedInPlace` insert or
remove **one leaf at its sorted position**. Measured: **1.3 ms and no catalog round trip**, against 13
queries (~164 ms) plus a full re-projection for the refresh.

Three details separate a correct targeted update from a naive one, and each was pinned by a test:
it is **idempotent** (a later refresh may already have the object); an **active filter** means `Children`
holds only matches, so the leaf enters the master list always and the displayed list only when it matches,
with the category's match count and zero-match visibility re-derived; and an **unloaded** category has no
leaves to insert into but does have an `(N)` label, so its count moves instead. The name index that feeds
the filter and type-ahead is **patched** rather than dropped — invalidating it would have cost 13 catalog
reads on the next keystroke, to forget one name we were holding.

⚠ Scope, stated so a future session does not mistake it: this is a **narrow precedent**, the sibling of the
existing `ApplyTriggerActiveStateInPlace`, not a general change protocol. The other twenty DDL paths were
not touched.

**Layer 1 — the guard that already existed, on the path that never had it.** `SidebarFlatController` has
carried an explicit `BeginUpdate`/`EndUpdate` bulk guard for a long time, with a comment naming the exact
failure it prevents (*"an O(n²) storm"*) — wired to the FILTER rebuild only. The other mass mutation,
`MetadataNodeViewModel.SetLeaves` (`Children.Clear()` then one `Add` per object), ran unguarded, so every
`Add` re-spliced the owner's whole child block while the category was expanded. The fix was to call the
existing pair from `LoadGroupAsync` (so every caller is covered wherever it is invoked from),
`RefreshAsync` (collapsing 13 re-projections into one) and the connect-time prefetch. Nesting is safe, so
the inner and outer guards compose.

**Re-measured with `tools/probes/MetadataPerfProbe`, extended with a before/after column:**

| expanded categories | before | after |
|---:|---:|---:|
| 0 | 6 ms | 2 ms |
| 1 | **1 424 ms** | **2 ms** |
| 2 | **1 733 ms** | **4 ms** |

⚠ **Startup did not improve, and that is measured rather than assumed.** `RestoreExpandState` restores
folder and connection expansion but **not** category expansion, so at connect every category is collapsed
and the projection already had an early exit — the "0 expanded" row above. Layer 1 removes the pain of
*refreshing*, not of *starting*. The startup cost stays unresolved, with the instrument already in the
app (`EMBERTERN_PERF_DIAG=1`) and the remaining suspects named in the report: the semantic-model rebuild
after `NotifyMetadataReady`, and workspace tab restore.

⚠ **One accepted trade-off, and it broke a test in a useful way.** `EndUpdate` re-projects the whole list,
so `SidebarRow` objects are recreated and the ListBox scrolls to the top. That was already true of every
refresh (it ends in `ApplyFilterAsync`, which does exactly this), but
`ConnectionExpandBindingProbe.AutoExpandOnConnect_ReflectedInFlatList` had captured a row **instance**
before connecting and asserted on it afterwards. The probe now re-resolves the row: what it is about is the
projection *mirroring* the node's state, not a row's identity. Removing the tree's "jumping" is Layer 2's
job, and the report says so.

**Left for the Metadata Explorer stage:** Layer 2 (a first-class "what changed" concept across all DDL
paths, incremental splicing, scroll/selection preserved), Layer 3 (reconcile the prefetch with
`RefreshAsync`'s dead `LoadCountAsync` branch; the `Domain` category's 79 ms `RDB$FIELDS` scan; the `User`
category's security-database round trip), and the unmeasured startup cost. Gotchas **#266** and **#267**.
