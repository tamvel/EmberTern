## 1. What L7 turned out to be

§32's brief listed five things: clock high-water, the `%PROGRAMDATA%` fallback, the `maint` gate, the real
key ceremony, and documentation.

⭐ **Three of the five were already built.** The reconnaissance measured them rather than trusting the
plan: `UserSettings.LicenseClockHighWater` with `EffectiveNow() = max(systemNow, highWater)`,
`LicenseLocation`'s two-path search order, and the maintenance gate in `LicenseVerifier` all shipped in
**L4a** and the plan had never been updated. So the stage was not "hardening"; it was **the ceremony and
its executor**, plus the documentation debt.

⚠ One genuine hardening gap survived: the clock-rollback **warning** has no surface. `ClockLooksRolledBack`
is computed and used, and nothing displays it. Ratified as backlog (decision **C2**) rather than pulled in,
because the enforcement — which is what matters — is live.

## 2. ⭐⭐ The finding that shaped the stage

`KeyCeremony.Perform` had produced the public key, its SHA-256 fingerprint and a paste-ready `TrustedKey`
entry **since L2**, and `KeyCeremonyTests` proved all three. `SigningSession.Create` — its only caller in
the application — kept the keystore bytes and **discarded the other three**. `KeyCeremony.VerifyRestore`
had no caller at all outside the suite.

So §24.1 step 5 (*"verify the restore — a backup that has never been restored is a hypothesis"*) and step 7
(*"record the fingerprint"*) had **no executor anywhere in the product**, for five stages, with a fully
green build.

⭐ **A function whose result nobody receives is a function that does not exist**, and no test says so
because the function is correct and its own tests pass — gotcha **#410**. L7.1 closed it with
`SigningKeyFacts` and a third task in the Storage window.

The design property worth keeping: **`SigningKeyFacts.VerifyBackup` has no parameter for the expected
key.** It supplies the running session's own public half, so no call site can pass the wrong one — and a
backup of a *different* key, which opens and carries the right `kid`, cannot pass as good.

## 3. What the ceremony actually did

| | |
|---|---|
| Environment | ⚠ Measured first: `%APPDATA%` **cannot be redirected** — .NET reads the Win32 known-folder path, so the environment variable is ignored. Isolation is a machine or an account, nothing else. The owner then ratified **this** machine as the issuing environment and removed the QA keystore themselves |
| Kit | `Release`, self-contained, built from a `git archive` **export of the exact commit** — not from the working tree — with its file list compared against the commit's, and the binaries' SHA-256 recorded |
| Key | `R1`, ECDSA P-256, generated by the application's own path. ⛔ Never `openssl`: `LicenseIssuer.Issue` verifies its own output, and that check is the reason to stay on this path |
| Passphrase | Generated and held by the owner alone. ⭐ It never entered this session, the repository, a log or a test |
| Backups | Two offline copies, each proved with `VerifyRestore` — which opens the file, checks it holds the **same** key, signs a probe licence and verifies it |
| Fingerprint | Compared across four independent readings before anything was written to the repository |
| Shipping | The public key pasted from the **generated** entry, never transcribed |

⚠ **The one narrowing, ratified and recorded:** both backups were verified on this machine; §24.1's *"on a
second computer"* was not performed. Portability is confirmed at the first real migration. It is written
into §35.4 so the register attests what was done and no more.

## 4. ⭐ Retiring a guard on the day its promise expires

`TheShippedTrustedKeyTableIsStillEmptyAtThisStage` had been right and load-bearing for five stages. On the
day the table stopped being empty it would have gone red reading *"you broke the key table"* rather than
*"this promise expired"* — gotcha **#407**, met here in its purest form.

It was replaced **in the same change that added the key**, by one test asserting **both halves**: the
table's shape (one entry, `R1`, not revoked, a usable P-256 key) *and* its identity — the fingerprint
recomputed from the pasted key against the value recorded in §35.4. ⛔ Not `Assert.NotEmpty`, which passes
for any key including a development one pasted by mistake.

⭐ The fingerprint is recomputed with `SHA256.HashData` rather than read from `KeyCeremony.Fingerprint`,
because `EmberTern.Tests` cannot reference the issuing assembly and must never be able to. A second
independent implementation of the same definition is a property here, not a duplication.

## 5. ⚠ Four measurement mistakes, all mine, all caught by cross-checking

Recorded because the pattern is the lesson, not the individual slips. Every one produced a **false
negative about key material**, and every one was caught by a second, differently-shaped check.

1. **`find … 2>/dev/null` reported 0 `.etkeys` files while the production keystore existed** — Git Bash
   cannot descend into much of `%APPDATA%`, and 1 910 access errors were being suppressed. Reported to the
   user twice before the contradiction surfaced. Gotcha **#411**.
2. **A regex swept the doc-comment word `SubjectPublicKeyInfo` into a base64 match**, producing a wrong
   fingerprint for a perfectly good file.
3. **A search for the key inside the compiled DLL failed** because the C# compiler *folds* constant string
   concatenation: the IL holds one 124-character literal, not the two fragments the source shows.
4. **A pattern without `(?s)` missed a sentence that wrapped across a line break** and reported a required
   phrase as absent.

⭐ The habit that saved each of them: when a check about a secret returns *"nothing found"*, **verify the
instrument before believing the answer.** A false negative here is the expensive direction.

⚠ A fifth, of a different kind: an injection-revert script added a **UTF-8 BOM** to `TrustedKeys.cs`, which
had none. It was caught only by diffing against a byte-copy taken before the injection. ⭐ Keep that copy —
a defect-injection harness must be able to prove it restored *byte for byte*, and ⛔ it must never restore
with `git checkout` (gotcha #383).

## 6. The exit criterion that had been deferred since L4

§32 asked L4 for *"all eight states reachable and verified in the running app"*. §38.6 recorded honestly
that `Valid`, `Grace` and `ExpiringSoon` were **not** walked by hand and could not be — with
`TrustedKeys.Production` empty, no licence anyone could produce verified in a shipped build.

L7 closed that line: a real licence, issued with `R1`, seen **`Valid` in a `Release` build**, and
corroborated by running the real `LicenseVerifier` against the shipped table on the same assembly the
application had loaded (SHA-256 matched).

## 7. Verification, and what stayed red

Builds **0/0** across both solutions and both configurations. License Manager **777 / 777** in Debug and
Release (was 767 — seven L7.1 tests plus three terminology assertions). EmberTern **9 092 total, 9 090
green**, unchanged from the entry state — the guard replacement was 1:1, and the total is what proves no
test was lost.

⛔ The same two pre-existing failures throughout, neither touched: `CharsetGuardSeamTests` (matches a
comment in a `.csproj`, gotcha #396) and `DatePresentationTests` (two invariant date formats in the License
Manager).

⚠ A third failure appeared in roughly 3 of 11 runs and was **refused classification for most of the stage**
because its stack had not been captured — CLAUDE.md is explicit that the known Avalonia headless race is
identified by the stack, never by the test name. In the final verification the stack was caught, and it
matched the documented signature exactly (`VerifyAccess` → `DefaultRenderLoop.Add` →
`AvaloniaHeadlessPlatform.Initialize` → `EnsureIsolatedApplication`), with the failure occurring *before*
the test body. A re-run with no change went green, as the rule prescribes. ⭐ The discipline is worth more
than the answer: a plausible classification without evidence is how an upstream race becomes an excuse.

## 8. What L7 deliberately did not do

⛔ No bulk sending (its own stage, §14.1). ⛔ No clock-rollback surface (decision C2). ⛔ No rotation and no
second ceremony. ⛔ `ManagerFixture`'s leftover keystores in `%TEMP%` — measured at 310 files before the
ceremony, recreated by every suite run since — left to the backlog. ⛔ Nothing in `EmberTern.App` beyond the
four stale comments the key entry made untrue.
